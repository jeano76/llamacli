# laya 빠른 판단 (System 1 사이드킥) — 사용법·설정·설치/모드

이 머신은 `laya`라는 작고 추론 없는 CPU 모델을 함께 돌립니다 (`convaiinnovations/laya`,
ModernBERT-base 421M). HTTP로 `http://127.0.0.1:8000`에 노출되어 있으며, 좁고 정형인
질문(`choice` / `score` / `noul`)을 **0.5초 안쪽**으로 답합니다. 반면 주 모델
(Ornith)으로.full reasoning 턴 한 번은 수십 초~90초걸립니다. laya는 **권고용 단축경로**로
쓰고, 결정적으로 중요한 일의 유일한 근거로 절대 쓰지 마세요.

> 목적: main model(Ornith)이 답변하는 짧은 질문들에 대해 더 짧은 turn으로 답함 (shortcircuit).

## 언제 써야 하는가

정말的快速 분류/트리지만지판단일 때만 — 그렇지 않으면 full slow-model 턴이 필요할such한
judgment. 예:
- 이 error message / output가 당장 고칠 문제인가, 흘려보낼 노음인가?
- 진행 전에 알리고 싶은 urgency/risk 수준인가?
- 짧은 option 목록 중 상황에 가장 잘 맞는 것은?

real reasoning이나 code 이해, 결과에 따른 판단이 필요한 곳에서는 쓰지 마세요.
(파괴적 명령 실행 여부, fix가 맞는지, 보통 당신이 스스로 생각해볼 일을 laya에게 맡기지 마세요.)
its answer는 extra data point로만 보고 결정하지 마세요.

## 호출하는 법

shell tool로, **항상 `--no-check`와 함께** (안 그러면 missing/offline된 laya server가
interactive install prompt를 띄 endlessly hang함 — 답변할 terminal이 없기 때문):

```bash
python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py fastcheck \
  --text "<짧고 자기완정적인 yes/no 또는 다지선다 질문>" \
  --no-check
```

- Exit 0 + answer to stdout = laya가 답함. chosen option (확률) 또는 0–1 score, 그리고
  어떤 checkpoint가 왜 답했는지 포함.
- Exit 1 (server not running/unreachable / request failed/timed out) = laya가 지금
  안 씂. 당연한 것이고 report/retry할 error 아님 — silently reasoning으로 넘어가 계속.
- 내부적으로 ~12초 hard cap, turn을 의미 있게 stall시킬 수 없음.

### short-circuit 확인 (Option B)

`fastcheck`는 답과 함께 **short-circuit verdict**도 같이 냅니다 — "이 질문은 laya만으로
충분히 결정해도 좋은가"를 Ornith와 비교한 것:

- `VERDICT: short_circuit` = 확률·신뢰도가 임계값 이상이라 laya 단독으로 결론지어도 됨.
  이 때는 (Option B) **Ornith를 호출하지 않고** laya 답으로 끝내도 됩니다 — 속도 이득 최대.
- `VERDICT: proceed_with_ornith` = 답이 애매하거나(moderate confidence) 확률이 낮음 →
  laya 결과를 참고하되 Ornith로 진짜 답변을 받는 것이 안전.

short-circuit는 **기본 off**입니다 (`config.yaml`의 `laya.enabled`, `laya.shortCircuit`).

## 적용할 위치 (Option A — merge-style gate)

`fastcheck` 커맨드를 사용자가 직접 부르는 것(C option)과 달리, **A option**은 turn 루프에
자동으로 개입합니다. `cmd_gate()` (`scripts/laya_integration.py`)이 맡고, `--merge`로
불러줍니다:

```bash
python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py gate --text "<현재 conversation context>" \
  --action "<주요 action>" --role "<사용자 역할>" --no-check
```

출력은 두 블록:
- `DECISION_GATE` — 위험도·긴급도·의도 분류 (Ornith가 응답 컨텍스트에 얹을 힌트).
- `MERGE_NOTES` — Ornith 프롬프트로 넘길 짧은 merge 조언 (경고/우선순위 등).

merge gate는 **실패하면 전부 Ornith로 우회**되므로 기존 llamacli를 손상시킬 위험이 거의
없습니다 — 문서 권고(MVP 주축)와 일치.

## 설정 (`config.yaml`의 `laya:` 섹션)

`~/.llamacli/config.yaml`:

```yaml
laya:
  enabled: false          # 전체 on/off开关. off이면 laya로 아무것도 안 함 (health probe도 안 함)
  shortCircuit: false     # Option B 활성화. 기본 off
  timeoutSeconds: 3       # fastcheck/gate 호출 timeout(초). 넘으면 Ornith 우회
  questionType: noul      # fastcheck가 만들 기본 질문 타입: choice | score | noul (기본 noul)
  actProbabilityThreshold: 0.85   # short-circuit에 필요한 최소 확률 (0–1)
  confidenceThreshold: 0.7        # short-circuit에 필요한 최소 신뢰도 (0–1)
```

- `enabled: false` — **완전히 꺼짐**: laya server로의 health probe조차 시도하지 않음.
  CPU/메모리 오버헤드 + log noise 방지. off일 때 "상태만 조용히 확인"도 금지.
- 토글은 **시작 시 1회 읽기 충분** (런타임 토글은 add-on 철학에 맞지 않은 불필요한 복잡도).
- `questionType`이 `choice`일 때는 laya가 choice 질문을 만들 때 `labels`를 붙이지 않습니다
  (laya는 choice + labels를 거부함). `score` 타입은 등급/순서 질문에 적합.

## absence — laya가 이 환경에 없을 때

llamacli가 이 스킬을 쓰려 하는데 해당 환경에 laya 자체가 없으면, 감지→동의→설치→기동
플로우로갑니다 (검토 안 6-1항). 기본은 **안전한 쪽**(사전 동의 없는 자동 설치 배제):

- **감지**: venv 경로 존재 여부 + `http://127.0.0.1:8000/health` 응답 **둘 다** 확인
  (신호 하나만信하면 안 됨 — venv 있어도 server 안 떠 있을 수 있음).
- **설치 트리거**: (a) 사용자에게 물어보 동의 시 설치. (b) 조용히 백그라운드 자동 설치는
  "사용자 모르게 venv+pip+수GB 다운로드"가 일어나므로 배제. 기본 N / off default와 일관.
- **설치 위치**: **프로젝트별**(`<project>/.llamacli/laya-venv/`)로 시작. shared는 버전
  충돌 관리가 어려우니 나중에 검토.
- **설치 실패 시**: layA 기능 계층에서 조용히 inactive + 원인 로그 (llamacli 본体 무손상).
- **기동 관리**: **독립プロセス** 권장 (systemd/detached) — llamacli 생명주기에 묶이면
  재시작마다 overhead.

설치 플로우: `<project>/.llamacli/laya-venv` 생성 → `uv pip install laya[serve]` →
HuggingFace 체크포인트(`convaiinnovations/laya`) 다운로드 (PyPI `laya` 패키지 최초 실행 시
`huggingface_hub`로 자동). 코드 업그레이드는 PyPI에서, 체크포인트(모델 가중치) 업그레이드는
HuggingFace Hub에서.

## GPU / CPU 구동 모드

설정 옵션: `gpu` / `cpu`(기본값) / `auto`. 기본값 **CPU**는 지난 사고 때문 — 정확히는
RAM이 아니라 **GPU VRAM 경합**: 8GB 중 Ornith가 7.4GB를 독점해서 laya를 올리면 context가
축소되는 연쇄 재현을 피하기 위함 (실제 제약은 swap/VRAM).

- `auto`: 가용 GPU VRAM이 laya 체크포인트(~400MB) + 여유보다 크면 GPU, 아니면 CPU 폴백.
  `run-server.sh`의 동적 재시도 패턴을 재사용할 수 있음. 초기 검증 후 검토 (post-MVP).
- 이 설정도 `.llamacli/config.yaml`의 `laya:` 섹션에 둘 것.

## 참고 명령

- 설치/기동 시도 안 함 (`--no-check`). laya가 이 머신에 있는지 read-only로 확인:
  ```bash
  python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py status
  # → {enabled, installed, running, swapFreeKb, ramFreeKb} JSON
  ```
- 이 스킬은 llamacli core 코드를 건드리지 않습니다. standalone script에 대한 plain shell
  호출이며, laya가 없으면 no-op으로 degrade합니다.
