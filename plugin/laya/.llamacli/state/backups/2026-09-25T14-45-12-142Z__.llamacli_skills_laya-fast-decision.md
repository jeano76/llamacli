# laya fast decision (System 1 sidekick)

This machine also runs `laya` — a small, non-reasoning model (`convaiinnovations/laya`,
ModernBERT-large ~421M). Today it is bound to **CPU** so it never competes with the main
reasoning model (Ornith) for GPU VRAM. It is served over HTTP at `http://127.0.0.1:8000`
and answers narrow, typed questions (`choice` / `score` / `noul`) in well under a second,
versus tens of seconds for a full reasoning turn on Ornith.

Use it as an **advisory shortcut**, never as the sole basis for anything consequential or
destructive. Its answer is one extra data point — not a decision.

## How this fits into llamacli (design review §4 / §5)

Per the integration-review spec, laya plays three roles, each mapped to a concrete spot in
llamacli:

1. **Merge-style gate before each turn (a).** Before spending a slow Ornith turn, ask
   laya for intent / urgency / risk classification and fold the result into Ornith's
   prompt/context. If laya fails or is low-confidence, Ornith still gets the full turn —
   this path never corrupts existing behaviour. **This is the default (always-on when
   `enabled`).**

2. **Short-circuit (b).** For questions that are genuinely binary / multiple-choice and
   where laya returns a *high* `probability`/`confidence`, you may stop after the gate and
   skip Ornith entirely. This gives the biggest speed win but is dangerous if misjudged
   ("is laya really sufficient here?") — so it is **off by default** (see `shortCircuit`).

3. **Explicit `/fastcheck` command (c).** Users who distrust auto-intervention call laya
   directly with this skill's command. Low barrier to try, full user control.

The Node wrapper that wires §4 into llamacli core lives in
`scripts/llamacli_laya_gate.js`. The Python script is the actual laya caller; the JS file
is only the thin adapter llamacli invokes.

## When to use this

Only for a genuinely quick classification/triage judgment that would otherwise cost a
full slow-model turn to reach — e.g.:
- Is this error message/output transient noise or something that actually needs fixing?
- Does this look urgent/risky enough to flag before proceeding?
- Given a short list of options, which one best matches the situation?

Do NOT use it for anything that needs real reasoning, code understanding, or judgment
with consequences (never let it decide whether to run a destructive command, whether a
fix is correct, or anything you'd normally think through yourself). Treat its answer as
one extra data point, not a decision.

## How to call it

Run via the shell tool, **always with `--no-check`** (without it, a missing/offline
laya server triggers an interactive `y/N` install prompt that will hang indefinitely —
there is no terminal attached to answer it):

```bash
python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py fastcheck \
  --text "<a short, self-contained yes/no or multiple-choice question>" \
  --no-check
```

- Exit code 0 with an answer printed to stdout = laya responded. The answer includes the
  chosen option (with a probability) or a 0–1 score.
- Exit code 1 (server not running/unreachable, or the request failed/timed out) = laya is
  unavailable right now. This is expected and NOT an error to report or retry — silently
  fall back to reasoning about it yourself and continue normally.
- Hard-capped internally; never meaningfully stalls a turn.

### Picking a verdict with `--decision`

Pass the option label you consider "go / yes" so laya can answer in plain terms:

```bash
python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py fastcheck \
  --text "<which of A/B/C fits?>" --labelA "option A" \
  --labelB "option B" --labelC "option C" \
  --decision "B" --no-check
```

`--decision B` makes the printed verdict one of: **yes** ("choose B", high probability),
**no** (another option wins, or low confidence on B), or **n/a** (not a yes/no question).

### Short-circuit check (`shortcircuit`)

When `gate.shortCircuit` is enabled and the gate passes both thresholds, run:

```bash
python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py shortcircuit \
  --text "<binary or multiple-choice question>" [--decision <go-label>] [--no-check]
```

It prints `yes` only when **both** hold — `probability ≥ actProbabilityThreshold` (default
0.85) **and** `confidence ≥ confidenceThreshold` (default 0.7). Anything short prints `no`
(and you should proceed to Ornith as normal). Keep it off unless a case is *clearly*
binary and low-stakes — see the spec's §1(b) risk warning.

## Config keys (`.llamacli/config.yaml`)

The `laya:` section controls framing and gating:

| Key | Default | Meaning |
|---|---|---|
| `baseUrl` | `http://127.0.0.1:8000` | laya endpoint (and `/health`). |
| `enabled` | `false` | Master switch. **Off = strict no-op**: no health probe, nothing to laya is attempted. Read once at start-up; runtime toggling isn't supported. |
| `timeoutSeconds` | `3` | Per-call deadline on the HTTP request. A timeout degrades to Ornith (spec §2/§3). |
| `questionType` | `noul` | Default framing: `noul` (yes/no probability), `choice` (multi-option + labels/criteria), or `score` (rank a list). See below. |
| `criteria` | — | Free-text rubric attached to a `choice` question (`--text` can carry it too). |
| `labels` | `{A,B,C}` | Option texts for a `choice` question; override per call with `--labelA/--labelB/--labelC`. |
| `actProbabilityThreshold` | `0.85` | Minimum "go" probability for a short-circuit verdict. |
| `confidenceThreshold` | `0.7` | Minimum confidence to accept a laya answer / allow a short-circuit. |
| `shortCircuit` | `false` | Allow the gate's short-circuit path (spec §1(b)). Off by default because misjudging "is laya sufficient" risks quality. |

### `questionType` framing

- **`noul`** — asks for a yes/no probability; pairs with a `--decision` label that means
  "yes/go". Good for urgency/risk triage.
- **`choice`** — gives N labelled options and returns each one's probability (+ optional
  `criteria`). Use when you have an explicit shortlist. **Do not attach `labels` to a
  `choice` question** (laya rejects that combination) — pass the list via `--text` instead.
- **`score`** — asks laya to rank/grade existing items; returns a normalized order with a
  score each. Use for "order these by X".

### Low-confidence handling (spec §3)

Only accept a laya answer at **high confidence**. When confidence sits in the ambiguous
middle band, treat the result as log-only: note it and let Ornith make the final call
(add a small hint to Ornith that confidence was low). Don't blindly trust or reject.

## Notes

- No installation/startup is attempted by this skill — `--no-check` means it either answers
  or fails silently. To check whether laya is even set up on this machine:
  `python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py status` prints
  `{enabled, installed, running, swapFreeKb, ramFreeKb}` as JSON (read-only, safe).

- **No-install fallback (spec §6).** If laya isn't installed on a different machine, the
  wrapper should NOT auto-install silently (auto venv+pip+multi-GB download without consent
  is risky per spec §6). Detection checks both a configured venv path and `/health`; if
  absent it reports failure cleanly and degrades to Ornith. An opt-in onboarding flow
  (detect → ask for consent → install → start) belongs in a post-MVP upgrade path, not here.

- **CPU/GPU mode (spec §7).** laya runs CPU by default — the spec's baseline risk is that
  GPU VRAM is tight (Ornith holds most of it), and putting laya on GPU risks stealing
  context/VRAM from Ornith. The `gpu`/`auto` options exist but are post-MVP; until then
  keep CPU and let the swap-free gate (`status`) protect against memory pressure.

- **Safety of §4(merge gate).** The merge-style gate degrades entirely to Ornith on any
  failure, so it can't corrupt existing llamacli behaviour — this matches the spec's "the
  core must stay untouched" philosophy. `scripts/llamacli_laya_gate.js` is only the thin
  adapter; `scripts/laya_integration.py` (Python) is everything else and stays outside
  llamacli core.
