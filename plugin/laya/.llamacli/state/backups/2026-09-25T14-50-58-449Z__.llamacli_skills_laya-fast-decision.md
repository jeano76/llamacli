# laya fast decision (System 1 sidekick)

이 머신에는 `laya`가 돌아갑니다 — HTTP(`http://127.0.0.1:8000`)로 공개된 작고
추론 없는 CPU 모델(`convaiinnovations/laya`). 좁고 정형인 질문(`choice` 다지선다 /
`score` 등급·순서 / `noul` 참·거짓 확률)을 **0.5초 이내**에 답합니다. 반면 주 모델
(Ornith)로 완전한 추론 턴 한 번을 돌리면 수십 초~90초가 잡니다. laya를 **참고용 단축경로**로
쓰되, 결론의 유일한 근거로 절대 삼지 마세요.

> 본 스킬은 llama 코어 코드를 건드리지 않습니다. `scripts/laya_integration.py`에 대한
> 단순한 shell 호출이며, laya가 없을 때 무조건 no-op으로 내려갑니다.

## 자원 제약 (이게 왜 중요한지)

- **진짜 제약은 VRAM이 아니라 SwapFree**입니다 (부록 A 확인). GPU VRAM 8GB 중 Ornith가
  7.4GB를 독점합니다. 과거 OOM은 "CPU 모드 laya가 RAM을 늘려 swap을 포화→커널이
  llama-server를 죽임"으로 발생했습니다.
- 따라서 스킬 실행 전 **`swapFreeKb`**를 보고 swap 여유가 부족하면 laya 대신 Ornith로만
  진행합니다 (아래 `cmd_gate`).

## 언제 쓸까

완전한 추론 턴 한 번이 걸릴 법한 빠르고 이산적인 분류/트리지만 때에만:
- 그 오류/출력이 일시적 노이즈인가, 진짜 고칠 것인가
- 앞으로 나가기 전에 알릴 만큼 긴급/험하인가 (긴급우 우선순위 참고)
- 짧은 선택지 중 상황에 가장 맞는 것은 무엇인가

실제 추론·코드 이해·결 quả가 따지는 판단은 절대 아닙니다. 도구 호출 전 위험도 분류(1차),
커밋 메시지가 사소한 변경인지 필터링 등 **Ornith 호출 컨텍스트를 보강**하는 용도로만 쓰세요.

## 어떻게 부를까

두 경로 — **명시 커맨드(`/fastcheck`, c)**와 **gate(`cmd_gate`, a + b short-circuit)**.

### (c) `/fastcheck` — 사용자가 직접 호출 (통제망)

```bash
python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py fastcheck \
  --text "<self-contained yes/no 또는 다지선다 질문>" \
  --no-check
```

- **항상 `--no-check`**: 없으면 죽어 있는 laya 서버가 interactive `y/N` 설치 프롬프트를
  띄 endlessly 걸립니다 (터널이 없어서 답할 사람이 없음).
- Exit 0 + stdout에 답 = laya 응답. 선택지(확률) 또는 0–1 점수 + 어떤 checkpoint가
  왜 답했는지. optional `--decision yes|no`로 "go/yes" 옵션을 지정해
  `yes/no/n/a` 결과를 받을 수 있음.
- Exit 1 (서버 없음/연락 안 됨/타임아웃) = laya 사용 불가. 보고·재시도할 오류가 아니라
  **조용히 Ornith로만 진행**. 내장 데드라인 ~3초(`timeoutSeconds`).

### (a)+(b) `cmd_gate` — 턴 전 자동 게이트 + short-circuit (기본 off)

```bash
python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py cmd_gate \
  --text "<이 턴의 의도: 긴급한가 / 위험한가 / 어떤 타입에 가까운가>"
```

- **SwapFree 게이트**: swap 여유 부족 → laya skip, Ornith로만 진행.
- **merge (a)**: laya가 성공하면 판단 결과를 "Ornith에게 참고 정보"로 얹어 호출을 보강.
  실패해도 전부 Ornith로 우회 → 기존 동작 손상 없음.
- **short-circuit (b, off-by-default)**: `probability ≥ actProbabilityThreshold`
  (기본 0.85) **かつ** `confidence ≥ confidenceThreshold` (기본 0.7)를 **둘 다** 만족할 때
  `"yes"` → Ornith 호출 생략하고 laya 답으로 종결합니다. 둘 중 하나라도 낮으면
  `"no"` → merge(a)로 진행 (`between`/중간은 log-only + Ornith에 "신뢰도 낮음" 힌트만).
- `--question-type noul|choice|score`, `--criteria`, `--labels`, `--json` 옵션 있음.
- Exit 0 = laya 답변(정지 or short-circuit). Exit 1 = laya 불가, Ornith로 진행.

## config (`.llamacli/config.yaml`의 `laya:` 섹션)

```yaml
laya:
  enabled: false          # off일 때 스킬이 아예 개입하지 않음(헬스체크조차 안 함)
  baseUrl: http://127.0.0.1:8000
  timeoutSeconds: 3       # 응답 지연 시 Ornith로 우회
  questionType: noul      # fastcheck/cmd_gate의 기본 질문 타입
  actProbabilityThreshold: 0.85   # short-circuit 확률 임계값(b)
  confidenceThreshold: 0.7        # short-circuit 신뢰도 임계값(b)
  criteria: ...           # score/choice 질문 평가 기준(생략 가능)
  labels: [...]           # choice 질문 라벨 목록(생략 가능)
```

- `enabled` off = **완전한 종료**: laya로 헬스체크조차 시도하지 않습니다(CPU/메모리 오버헤드
  + log noise 방지). 시작 시 1회 읽기만 하고, 런타임 토글은 불필요한 복잡도.
- `questionType` 기본값을 `noul`로 바꾼 이유: laya가 다지선다에 "참/거짓 확률"을 억지로
  붙여 답변 품질이 뚤어졌기 때문(부록 B / git log 참조).

## absence — 이 환경에 laya가 없을 때 (§6)

스킬은 **설치·기동을 시도하지 않습니다** (`--no-check`의 철학). 감지→설치→기동은 별도의
온보딩 플로우(UI 메뉴 A/B/C)에서 handling하며, 스킬은 active일 때만 호출합니다.

- **감지**: venv 경로 + `http://127.0.0.1:8000/health` **둘 다** 확인(단일 신호 신뢰 낮음).
- **설치 트리거**: ✅ **(a) 사용자에게 물어보고 동의 후 설치**. 사용자 모르게 venv+pip+수GB
  다운로드(b)는 배제. 기본값은 안전한 쪽.
- **설치 위치**: 프로젝트별(`<project>/.llamacli/laya-venv/`)로 시작, shared는 이후 검토.
- **실패 시 격리**: layA 기능층만 조용히 inactive + 원인 로그. llamacli 본체 무손상(철학).
- **기동 관리**: **독립 프로세스 권장**(systemd/detached). llamacli 생명주기에 묶이면
  재시작마다 overhead(오늘의 systemd 경험 참조).
- `status` 커맨드: `python3 .../laya_integration.py status` → `{enabled, installed,
  running, swapFreeKb, ramFreeKb}` JSON(read-only, 안전)으로 현재 상태 확인.

## GPU / CPU 구동 모드 (§7)

laya 서버 기동은 `scripts/run-server.sh`가 담당하며 설정(`laya.computeMode`, 기본 **cpu**):

- **cpu**(기본값, 권장): 오늘 사고가 이 모드에서 발생했어도, 실제 원인은 "GPU VRAM이 얇아
  laya를 올리면 Ornith와 다툴 위험"이었습니다. CPU로 두면 Ornith의 VRAM(및 `-c 24576`
  컨텍스트)을 건드리지 않아 안전합니다. MVP 기본값으로 유지.
- **gpu**: ⚠️ 재검토 필요. VRAM 경합으로 Ornith 컨텍스트가 축소될 연쇄 리스크. 초기 검증 후.
- **auto**: 가용 GPU VRAM이 laya 체크포인트(~400MB)+여유보다 크면 gpu, 아니면 cpu 폴백.
  `run-server.sh`의 "동적 계산 + 재시도 폴백" 패턴을 재사용. 기본값은 여전히 cpu.

## 최종 권고 (MVP) — §8

**"laya gate — merge-style(a), c→a sequentially, b off-by-default"**

| 포함(MVP) | 미루기(post-MVP) |
|---|---|
| `config.yaml` `laya.enabled` switch(off default/opt-in) | gpu/auto 초기 검증(7번) |
| CPU 기본값 + gpu/auto 추후 | typed-decisions 추가 로드 |
| **(a) merge-style gate**( 턴 전 판단, 실패→Ornith degrade) | (b) short-circuit allow-list로 추후 |
| swap-free 게이트 + timeout → fail-to-Ornith | 런타임 토글 |
| **(c)** `/fastcheck` 명시 커맨드(사용자 통제망) | shared venv 최적화 |
| low-confidence: log-only + Ornith 힌트만 | GPU 모드 |

short-circuit(b)는 오늘 구현했지만 **기본 off**이며, `probability ≥ 0.85`かつ
`confidence ≥ 0.7`를 동시에 만족할 때만 Ornith 호출을 생략합니다. merge gate(a)는
실패가 전부 Ornith로 우회하므로 기존 llamacli 손상 가능성이 거의 0 — 가장 낮은 난도 +
즉각적 효과(판단 결과가 Ornith 응답 품질을 보강).

## 부록 A: 실측 수치 (부록 B의 근거)

| 지표 | 문서 서술 | **실측 (2026-09-25 22:11, `free -h`)** | 평가 |
|---|---|---|---|
| 시스템 RAM | "타이트 / OOM 재발 위험" | 총계 ~30GB, 사용 14GB, 가용 ~16.9GB | 여유 충분 (과장) |
| Swap | 8G 꽉 참 | 8G 중 7.85G 사용(여유 192M) | 정확이나 지난 사고 잔재 + 지속 스왑 압박 신호 |
| GPU VRAM | 8GB 대부분 Ornith | **7452MB 사용 / 8192MB** | 진짜 제약. laya CPU로 두어도 Ornith VRAM 건드리지 않음 |

**결론:** 게이트는 RAM이 아니라 **SwapFree 기준**으로 잡아야 합니다(과거 OOM이
swap 포화 + CPU 모델 식으로 나타났기 때문).

## 부록 B: 검토 결과 (요약, 원문 `docs/skill-integration-review.md`)

- **(1) 호출 시점**: a/b/c 단일 선택이 아닌 **층별 조합**이 정답. a(merge) 주축 +
  b(short-circuit allow-list, off-by-default) + c(/fastcheck 사용자 커맨드).
- **(2) 자원**: 지연 기동 + SwapFree 게이트 + timeout. MVP는 `english` 단독 유지.
- **(3) 대응**: laya 다운/타임아웃 → Ornith로만 진행(silent skip). low-confidence(between)
  → log-only + Ornith에 "신뢰도 낮음" 힌트만.
- **(4) 적용처**:① 도구 호출 전 위험도 분류 ② 긴급우 우선순위 ③ 커밋/diff 사소 변경 필터
  ④ 응답 형식 예측(choice/score/noul 중 어떤 타입이면 laya로 미리 "결정됐나" 확인).
