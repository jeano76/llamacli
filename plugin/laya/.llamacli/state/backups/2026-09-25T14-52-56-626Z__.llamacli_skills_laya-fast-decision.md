# laya fast decision (System 1 sidekick)

이 머신에는 `laya`라는 작은 **비추론 CPU 모델**(`convaiinnovations/laya`, ModernBERT-large
약 420MB)이 `http://127.0.0.1:8000`에서 HTTP로 떠 있습니다. 좁고 정형화된 질문
(`choice` 다지선다 / `score` 등급순서 / `noul` 참/거짓 확률)에 **0.5초 내외**로 확률·신뢰도
답을 주며, 비해 주요 추론 모델인 Ornith(35B, GPU)는 단일 턴에 답하기까지 수십 초~90초가
걸립니다.

이 스킬은 이를 **자문용 단축 경로(advisory shortcut)**로 씁니다. 결정권은 항상 당신 것이며,
laya 답을 "하나의 추가 데이터 포인트"로만 활용하십시오.

## 배경 — 자원 제약과 VRAM이 진짜 한계 (검토 부록 A 반영)

오늘 실제 사고(GPU 모드에서 laya가 Ornith의 GPU VRAM을 쳐서 OOM)와 실측 수치는 다음과
다릅니다.

| 지표 | 문서 서술 | **실측 (2026-09-25, `free -h`)** | 평가 |
|---|---|---|---|
| 시스템 RAM | 타이트 / OOM 위험 | 총계 ~30GB, 가용 ~16.9GB | 여유 충분 (과장) |
| Swap | 8G 꽉 참 | **7.85G 사용**(여유 ~192M, 지속 스왑) | 진짜 게이트 |
| GPU VRAM | 8GB 대부분 Ornith | **7452MB 사용 / 8192MB** | 진짜 제약 |

**결론:** laya는 항상 **CPU 모드**로 둡니다 (Ornith의 VRAM을 건드리지 않기 위함). 리스킬
게이트도 RAM이 아니라 **SwapFree 기준**으로 잡힙니다.

## 언제 이 스킬을 쓸까

정말로 짧은 분류/트리지 판단이라, 이를 위해 완전한slow-model 턴을 써야 하는 상황에서만:
- 이 오류/출력이 임시 노이즈인가, 진짜 고칠 것인가?
- 진행 전 플래그할 만큼 긴급/험해 보이는가?
- 짧은 옵션 목록 중 상황에 가장 잘 맞는 것은?

**쓰면 안 되는 것:** 진짜 추론·코드 이해·결 quả 있는 판단이 필요하면 절대 아닙니다. 파이프
삭제 같은 파괴적 명령 실행 여부, 수정의 정확성, 당신이normally 생각해볼 문제는 laya가
정하지 못하게 하십시오. 답은 "추가 정보"일 뿐 결정이 아닙니다.

## 호출 방법 — shell 도구로, 항상 `--no-check`

```bash
python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py fastcheck \
  --text "<짧고 자기충족적인 yes/no 또는 다지선다 질문>" \
  --no-check
```

- `--text`: laya에 보낼 질문 (기본 프롬프트를 재가립니다).
- `--no-check`: **필수**. 이를 붙이지 않으면 떨어졌거나 오프라인인 laya 서버가 인터랙티브
  `y/N` 설치 프롬프트를 내밀어 무한 정지합니다(대응할 터미널이 없음).
- `--decision <yes|no>` (옵션): 답을 yes/no로 한정. 특정 옵션이 "네/허용" 의미인지
  자동으로 판단하되, 모호하면 무시됩니다.

### 출력 해석

- **반환 코드 0 + stdout에 답** → laya가 응답함. 선택지 확률 또는 0–1 스코어, 그리고 어떤
  checkpoint가 왜 답했는지 포함.
- **반환 코드 1 (서버 안 떠있음/연락 실패/타임아웃)** → laya가 지금 사용 불가. 이것은
  기대되는 상황이며 보고·재시도할 오류가 아닙니다. **조용히 Ornith로 돌아가 직접 생각해**
  계속하십시오.
- 내부적으로 **~12초 hard cap**. 절대 턴을 크게 멈추지 않습니다.

## 단축 판단 (short-circuit) — 두 게이트 모두 통과 시

`fastcheck`는 기본 off인 short-circuit를 지원합니다 (`config.yaml` `laya.shortCircuit: true`).
**두 조건이 동시에 성립할 때만 laya 답을 확신 결정으로 처리하고 Ornith 호출을 생략**합니다.

1. **활동 확률 ≥ 임계값** — `act_probability`가 `laya.actProbabilityThreshold`(기본 0.85) 이상
2. **신뢰도 ≥ 임계값** — `confidence`가 `laya.confidenceThreshold`(기본 0.7) 이상

출력 예시 (단축 통과):

```
=== FAST CHECK (short-circuit) ===
decision: yes            (예/허용을 의미)
act_probability: 0.92    (임계 0.85 ✓)
confidence: 0.94         (임계 0.7  ✓)
checkpoint: english
> 단축: 두 게이트 모두 통과 — laya답으로 확정하고 Ornith를 건너뛸 수 있음
```

두 조건 중 하나라도 충족 못 하면 `decision`은 여전히 나와 있지만, "short-circuit 가능"으로
표시되지 않으므로 **Ornith로 가십시오**. short-circuit는 allow-list(신뢰도 임계값 충족 시
만) 접근입니다 — 기본값이 off인 이유도 여기 있습니다.

## 관련 정보 (Notes)

### 스위치: config.yaml `laya:` 섹션 (검토 §5)

`fastcheck`의 기본 질문 프롬프트와 게이트/단축 설정을 통제합니다:

```yaml
laya:
  enabled: true            # gate 활성화 여부. false면 스킬 완전 개입 중지 (health probe조차 없음)
  shortCircuit: false      # 위 단축 판단 on/off — off-by-default (allow-list 철학)
  timeoutSeconds: 3        # gate의 laya 호출 데드라인(초). 초과 시 Ornith로 우회
  questionType: noul       # fastcheck 기본 질문 타입 (noul | choice | score)
  criteria: [...]          # score/choice 타입에서 옵션을 평가할 기준
  labels: [...]            # score/choice 타입의 옵션 라벨 (fastcheck --text가 재가림)
  baseUrl: "http://127.0.0.1:8000"
```

- **off일 때는 완전 종료** — `enabled: false`면 laya로 health probe조차 하지 않습니다 (CPU/메모리
  오버헤드 + log noise 제거, 검토 §5 권고 반영). 런타임 토글은 불필요한 복잡도이므로 시작 시 1회만 읽습니다.
- **게이트 타임아웃**: `timeoutSeconds`를 넘겨 laya가 응답을 지연시키면 gate는 조용히 Ornith로 우회합니다 (검토 §3 degrade-to-Ornith).

### 부록 C: 실측 수치 — CPU 게이트 기준 (laya 1.1)

| 지표 | 값 | 평가 |
|---|---|---|
| CPU swapFreeKb (gate 시점) | ~208 MB | SwapFull → gate skip + Ornith 진행 |
| CPU RAM Free/Total | 6.37 GB / 30.49 GB | 여유 충분 (과장) |
| GPU VRAM | 7452MB / 8192MB (Ornith 독점) | laya CPU로 두어도 Ornith VRAM 건드리지 않음 |
| gate timeout | 3s hard cap, 내부 ~12초 | 응답 지연 시 우회 |

## 적용처 후보 — llamacli 내 laya 유용 지점 (검토 §4)

실제 구현은 아니지만, 이 프로젝트(llamacli_plugin + laya 통합) 맥락에서 유력한 적용처 5개:

1. **툴 호출 전 위험도 분류** — 도구 실행 결과를 성공/실패/재시도 중 무엇인지 1차 분류.
   위험 높으면 Ornith에게 extra-caution 프롬프트 강화.
2. **긴급 우선순위** — 입력이 긴급(데이터 손실 관련)인지 일반인지 1차 분류 → 응답 순서/노출 반영.
3. **커밋 메시지/diff "사소 변경 필터"** — 그 변경이 커밋 요약이 필요한 건지 사소한 것인지 필터링.
   사소하면 laya가 판단해 Ornith의 긴 생성을 줄임 (검토 §4 예시, 실용적).
4. **(신선한 아이디어) 응답 형식 예측** — 질문이 `choice`/`score`/`noul` 중 어떤 타입에 가까운지
   미리 확인 → 결정됐는지 laya로 체크, 미결정이면 Ornith에게 길게 추론 유도.
5. **의도 분류 (검증 필요)** — 시스템 프롬프트 인젝션/모호한 지시 감지로 Ornith 보안 주입 강화.

## GPU / CPU 모드 — 기본 CPU + VRAM 게이트 (검토 §7)

- **기본값 CPU**는 오늘 사고(GPU 모드에서 laya가 Ornith의 8GB VRAM을 다퉈 OOM) 때문입니다.
  정확한 원인은 "GPU VRAM이 얇아(8GB) laya를 올리면 Ornith와 경쟁" — CPU로 두면 Ornith 컨텍스트(`-c 24576`)가 안전하게 유지됩니다.
- **`gpu`/`auto`는 post-MVP** (검토 §7). `auto`가 온다면判断 기준: 가용 GPU VRAM이 laya
  체크포인트(~400MB) + 여유 > X GiB이면 GPU, 아니면 CPU 폴백 (`run-server.sh`의 동적 재시도 패턴 재사용).
- **GPU 모드의 리스크**: Ornith 컨텍스트 축소 연쇄 — laya가 GPU VRAM 식이면 Ornith가 VRAM 부족으로
  `-c 24576`을 축소. 오늘 사고와 유사한 2차 실패. 따라서 기본은 CPU로 못빚습니다.

## absence (laya가 이 환경에 없을 때) — 감지 → 동의 → 설치 → 기동 (검토 §6/§6-1)

llamacli가 이 스킬을 쓰려 하는데 대상 환경에 laya가 아예 없으면, **사용자 사전 동의 없는 자동 설치는 배제**하고
온보딩 메뉴로 진행합니다 (검토 §6-1):

**감지 (3단계 점진적):**

| 순서 | 체크 항목 | 판단 기준 |
|---|---|---|
| 1 | **venv 경로** 존재 (`<project>/.llamacli/laya-venv/bin/python` or `~/.llamacli/laya-venv/bin/python`) | 없으면 다음 단계 |
| 2 | `/health` 응답 (venv 있어도 서버 안 떠 있을 수 있음) | 실패하면 C(구동)으로 |
| 3 | **prerequisites** (Python ≥3.10, `uv` 존재, disk 여유, HuggingFace 접근성) | 부족이면 D(설치 실패 격리)로 |

**온보딩 플로우:**

```
[1] 감지: laya 없음 → "laya(System1 고속판단)를 설치하시겠습니까?" (기본 N / off-default와 일관)
      동의 시
[2] 전제 표시: Python 버전, uv 존재, 예상 스페이스(~수GB), 체크포인트 다운로드
      - "GPU VRAM 8GB 중 Ornith가 7.4GB 독점 → laya는 CPU 권장" 안내
      동의 후
[3] 설치: 프로젝트별 venv 생성 → `uv pip install laya[serve]` → HuggingFace 체크포인트(english) 다운로드
      - 백그라운드 실행 (진행률 표시, 프론트엔드 블로킹 금지)
[4] 기동: laya serve CPU 모드로 시작 → /health 확인 → active화
```

**메뉴 선택지 = (A) 설치+자동활성화(추천), (B) 설치만하고 수단 켜기(off 유지), (C) 취소.**
이것이 "6항 (a) 사전 동의"의 사용자 선택 UI 구현입니다. **(b) 사용자 모르게 venv+pip+수GB 다운로드**는 배제.

**설치 실패 시 격리 (모든 실패 layA 기능 계층에서):**

| 실패 유형 | 대응 |
|---|---|
| Python 버전 불일치 (<3.10) | "Python X 필요" 안내 후 설치중지 (사용자 재선택 가능) |
| disk 부족 | "약 XGB 필요" 표시, 사용자 확인 후 진행/중지 |
| 네트워크 불가 (HuggingFace 접속 실패) | 체크포인트 다운로드 실패 → laya inactive 유지 + 원인 로그 |
| uv 미설치 | 자동 설치 시도 또는 수단 안내 |

**핵심:** 모든 실패는 **laya 기능 계층에서 격리** → llamacli 기본 대화/Ornith 동작 항상 정상.

**기동 관리: 독립 프로세스 권장** (systemd/detached). llamacli 생명주기에 묶이면 재시작마다
overhead — 오늘의 systemd 경험 참조.

**설치 위치: 프로젝트별** (`<project>/.llamacli/laya-venv/`)로 시작, 나중에 shared 검토.
버전 충돌 관리가 더 쉬움.

**업그레이드 경로:** laya의 두 "업그레이드"는 분리 — (1) **코드**는 PyPI `laya` 패키지
(`uv pip install --upgrade laya[serve]`), (2) **모델 가중치(체크포인트)**는 HuggingFace Hub
`convaiinnovations/laya` 리포에서 자동으로 (최초 실행 시 `huggingface_hub`로 다운로드,
`~/.cache/huggingface/` 캐시).
