# laya 빠른 판단 (System 1 보좌관) — 한국어

이 머신에는 추가로 `laya`가 돌아갑니다 — HTTP로 노출된 작은 비추론 CPU 모델(`convaiinnovations/laya`,
`http://127.0.0.1:8000`). 좁고 정형인 질문(`choice` / `score` / `noul`)을 1초도 채 안 돼서 답하는데,
주요 모델(Ornith)의 peł한 추론 턴은 수십 초가 걸립니다. **권고용 단축 경로**로 쓰되, 중대·파 destructive한
결정의 유일한 근거로는 절대 사용하지 마십시오.

---

## 1. 호출 시점 · 방식 (a / b / c 조합)

세 가지 방식을 단계별로 섞어씁니다. 이 스킬이 직접 담당하는 건 **(c)** 명시 커맨드와 **(b)** 단축 경로입니다.
**(a)** merge-style 개입은 Node 래퍼(`scripts/run_laya_server.sh`가 부르는 `scripts/llamacli_integration.py`)가 담당합니다.

| 방식 | 역할 | 이 스킬에서의 위치 |
|---|---|---|
| (a) 턴 전 merge | 도입 전 의도/긴급도/위험도 판단 → Ornith 호출 컨텍스트에 얹음. 실패 시 Ornith가 최종 판단 → 기존 동작 손상 없음 | Node 래퍼가 자동 수행 (`--merge`), 이 스킬이 수동 호출하지는 않음 |
| (b) short-circuit | laya만으로 결론낼 수 있는 케이스만 Ornith 호출 생략 | `cmd_gate`가 수행. **기본 off**(allow-list). 신뢰도·확률이 임계값 충족 시만 허용 |
| (c) 명시 커맨드 `/fastcheck` | 사용자가 직접 호출하는 통제망 | 이 스킬이 기본으로 사용하는 경로 |

결론: **(c)**가 기본 사용자 경로, **(b)**는 신뢰도가 명확할 때만 허용되는 단축, **(a)**는 Node 래퍼가 담당하는 자동 개입입니다.

---

## 2. 자원(메모리) 관리 전략 — 지연 기동 + swap 게이트

- **지연 기동 (lazy):** 이 스킬은 항상 떠 있지 않고, 호출될 때만 `fastcheck`/`gate`를 통해 laya에 접근합니다.
  GPU VRAM이 진짜 제약이고 laya(CPU)가 Ornith의 VRAM을 직접 깎진 않지만, **swap 포화 상태에서 laya가 RAM을 식으면 즉시 스왑 압박**입니다(지난 OOM 시나리오와 유사). 필요할 때만 올립니다.
- **SwapFree 게이트 (필수):** 리스킬은 RAM이 아니라 **swap 기준**으로 잡습니다(부록 A 참고).
  `cmd_gate`는 gate를 걸기 전에 swap 여유를 확인하고 부족하면 laya를 스킵하고 Ornith로만 진행합니다.
- **LAYA_MODELS:** MVP는 **`english` 단독** 유지. `typed-decisions`(~2GB) 추가는 swap 압박을 키우므로 검증 후 점진적 검토.

---

## 3. 장애 / 성능 저하 대응 — degrade-to-Ornith + low-confidence log-only

- **laya 다운 / 타임아웃:** ✅ **Ornith로만 진행하고 laya 스킵** (스킬 실패 금지 — 문서 철학).
  `fastcheck`는 exit 1로 조용히 실패하고, hard-cap(내부 ~3초)으로 턴을 막지 않습니다. 이 스킬은 exit 1을 "현재 laya 사용 안 함"으로 처리하고 다시 생각해서 이어갑니다.
- **low-confidence:** ✅ 두 임계값(half/whole) 접근 채택. high confidence → laya采纳;
  `between`(중간/애매)은 **log-only** + Ornith에 "신뢰도 낮음, 확인 필요" 힌트만 제공(merge 방식의 경우).

---

## 4. 구체적 적용처 후보 (llamacli 맥락 특화)

1. **툴 호출 전 위험도 분류** — 도구 실행 빠르게 판단, 높으면 Ornith에게 extra caution 프롬프트
2. **긴급도 우선순위** — 입력이 긴급한지(데이터 손실 관련) 일반인지 1차 분류 → 응답 순서/노출 반영
3. **커밋 메시지/diff "사소 변경 필터"** — 사소한 변경은 laya가 판단해 Ornith의 긴 생성을 줄임
4. **(신선한 아이디어) 응답 형식 예측** — 질문이 `choice`/`score`/`noul` 중 어떤 타입에 가까운지 → laya로 미리 "정답이 이미 결정됐나?" 확인, 미결정이면 Ornith에게 길게 추론 유도
5. (검증 필요) **의도 분류** — 시스템 프롬프트 인젝션/모호한 지시 감지로 Ornith 보안 주입 강화

## 5. 기능 on/off 스위치 — config.yaml, off는 완전 종료

- **위치:** `.llamacli/config.yaml`에 `laya:` 새 섹션이 자연스러움(기존 구조와 호환).
- **off일 때 동작:** ⚠️ **"상태만 조용히 확인"조차 off일 때는 금지**. 완전히 꺼져 laya로 헬스체크까지 하지 않도록 strict — off 상태에서도 health probe는 CPU/메모리 오버헤드 + log noise.
- **토글:** ✅ **시작 시 1회 읽기 충분**. 런타임 토글은 불필요한 복잡도(add-on 철학에 반함).

현재 `config.yaml`의 실체:

```yaml
laya:
  enabled: false            # gate 단축 경로(Ornith 생략) 기본 off
  shortCircuit: false       # (b) — true이면 both-gate 통과 시 Ornith 생략
  timeoutSeconds: 3         # gate/fastcheck 호출 데드라인
  questionType: noul        # fastcheck가 생성하는 기본 질문 타입(choice/score/noul)
  actProbabilityThreshold: 0.85   # (b) 단축의 확률 임계값 — 3번 권고의 allow-list 조건
  confidenceThreshold: 0.7         # (b) 단축의 신뢰도 임계값
  baseUrl: http://127.0.0.1:8000  # laya 서버
```

## 6. 실행 환경에 laya가 없을 때 — 감지·설치·기동

llamacli가 이 스킬을 쓰려 하는데 해당 환경에 laya가 아예 없 대비한 설계입니다(오늘 `laya_plugin`의 실제 설치 경험 반영).

### 6-1. 감지 (3단계 점진적)

| 순서 | 체크 항목 | 판단 기준 |
|---|---|---|
| 1 | **venv 경로** 존재 여부 (`~/.llamacli/laya-venv/bin/python` 등) | 없으면 다음 단계 |
| 2 | `/health` 응답 (venv 있어도 서버 안 떠 있을 수 있음) | 실패하면 C(기동)으로 |
| 3 | **prerequisites** (Python ≥3.10, `uv` 존재, disk 여유, HuggingFace 접근성) | 부족이면 D(설치 실패 격리)로 |

`status` 커맨드는 이 감지를 read-only로 보고합니다:

```bash
python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py status
# → {enabled, installed, running, swapFreeKb, ramFreeKb} (JSON)
```

### 6-2. 설치 트리거 — (a) 사전 동의

(b) "사용자 모르게 venv+pip+수GB 다운로드"는 **부적절** (디스크/네트워크 사용량이 큼).
**(a) 사용자에게 물어보고 동의 시 설치**가 정답입니다. 오늘 `run-server.sh`의 `-y` 없이 실행하면
실제로 이 `y/N` 프롬프트가 나옵니다(터미널 없으면 무한 hang → 반드시 `--no-check`).

온보딩 플로우: `[1] 감지 → laya 없음 → "설치하시겠습니까?"(기본 N) 동의 시 [2] 전제 표시
(Python/uv/예상 스페이스/체크포인트 다운로드, GPU VRAM 8GB 중 Ornith가 7.4GB 독점 → laya CPU 권장)
동의 후 [3] 프로젝트별 venv 생성 → `uv pip install laya[serve]` → HuggingFace 체크포인트(english) 다운로드
[4] laya serve CPU 모드로 시작 → /health 확인 → active화`

메뉴 선택지 = **(A)** 설치+자동활성화(추천), **(B)** 설치만 하고 수단 켜기(off 유지), **(C)** 취소.
이 메뉴가 6항 "(a) 사전 동의"의 사용자 선택 UI 구현입니다.

### 6-3. 설치 위치 — 프로젝트별 시작

⚠️ **프로젝트별(`<project>/.llamacli/laya-venv/`)로 시작**, 나중에 shared 검토. 버전 충돌 관리가 쉬움.
shared는 디스크/다운로드 낭비를 줄이지만 버전 관리가 필요합니다.

### 6-4. 설치 실패 시 격리 — layA 기능만 조용히 inactive

✅ layA 기능만 조용히 inactive + 원인 로그. llamacli 본체 무손상 (철학).

| 실패 유형 | 대응 |
|---|---|
| Python 버전 불일치 (<3.10) | "Python X 필요" 안내 후 설치 중지 (사용자 재선택 가능) |
| disk 부족 | "약 XGB 필요" 표시, 사용자 확인 후 진행/중지 |
| 네트워크 불가 (HuggingFace 접속 실패) | 체크포인트 다운로드 실패 → laya inactive 유지 + 원인 로그 |
| uv 미설치 | 자동 설치 시도 or 수단 안내 |

핵심: 모든 실패는 **laya 기능 계층에서 격리** → llamacli 기본 대화/Ornith 동작 항상 정상.

### 6-5. 기동 관리 — 독립 프로세스 권장

⚠️ **독립 프로식스 권장**(systemd/detached). llamacli 생명주기에 묶이면 재시작마다 overhead.
오늘 systemd 경험 참조. 다만 systemd가 항상 적절한 건 아니므로, 필요시 detach된 백그라운드 프로세스로도 충분.

### 6-6. 업그레이드 경로 (신규 반영)

laya의 두 가지 "업그레이드"는 분리되어 있습니다.

| 대상 | 위치 / 버전 | 업그레이드 방법 |
|---|---|---|
| **코드** | PyPI `laya` 패키지 (`laya.serve`) | `uv pip install --upgrade laya[serve]` (또는 `pip install -U`) |
| **모델 가중치** | 체크포인트 `.safetensors`, 출처: **HuggingFace Hub — `convaiinnovations/laya`** | 패키지 최초 실행 시 `huggingface_hub`로 자동 다운로드 → 로컬 캐시 `~/.cache/huggingface/`. 코드 버전이 다른 체크포인트를 요구하면 HuggingFace 리포에서 자동으로 새로 받아옴 |

## 7. GPU / CPU 구동 모드 — 기본값 CPU + VRAM 게이트 auto

- **세 가지(gpu/cpu/auto):** ✅ 유효. 기본값 **CPU**는 오늘 사고 때문. 정확한 이유는
  "GPU VRAM이 얇아(8GB) laya를 올리면 Ornith와 다툴 위험" — 문서가 CPU모드 실패를 OOM으로만 서술했지만 실제 원인은 VRAM 경합 가능성도 있음 (부록 A에서 RAM 과장 확인).
- **`auto`:** ✅ 가치 있음. 판단 기준: **가용 GPU VRAM이 laya 체크포인트(~400MB) + 여유 > X GiB**이면 GPU, 아니면 CPU 폴백. `run-server.sh`의 동적 재시도 패턴을 재사용할 수 있음.
- **GPU 모드 리스크:** ⚠️ 문서가 지적한 항목 정확. **Ornith 컨텍스트(`-c 24576`) 축소 연쇄** — laya가 GPU VRAM 식이면 Ornith가 VRAM 부족으로 context 축소. 재필 검토 항목.

설치 위치: ✅ 6번과 동일하게 `.llamacli/config.yaml` laya 섹션에 통합. 현재는 `gpu/cpu/auto` 설정이 없으며,
MVP에서는 CPU로 못 박아 두고 추후 `7번` 검토 결과를 반영해 추가하는 방향을 권합니다.

## 부록 A: 실측 수치 (검토 근거)

실제 관측은 문서 서술과 다릅니다. 진짜 제약은 RAM이 아니라 VRAM입니다.

| 지표 | 문서 서술 | **실측** | 평가 |
|---|---|---|---|
| 시스템 RAM | "타이트 / OOM 재발 위험" | 총계 ~30GB, 사용 ~14GB, 가용 ~16.9GB | 여유 충분 (과장) |
| Swap | 8G 꽉 참 | 8G 중 ~7.85G 사용(여유 192M) | 정확이나 지난 사고 잔재 + 지속 스왑 압박 신호 |
| GPU VRAM | 8GB 대부분 Ornith | **7452MB 사용 / 8192MB** | 진짜 제약. laya CPU로 두어도 Ornith의 VRAM은 건드리지 않음 |

**결론:** 리스킬 게이트는 RAM이 아니라 **SwapFree 기준**으로 잡아야 합니다(과거 OOM이 swap 포화 + CPU 모델 식이었기 때문).

## 부록 B: MVP 권고 (검토 결과 8항)

**추진 MVP: "laya gate — merge-style, c→a sequentially, b off-by-default"**

| 포함 (MVP) | 미루기 (post-MVP) |
|---|---|
| ✅ `config.yaml`에 `laya.enabled` switch (off default / opt-in) | ❌ gpu/auto 초기 검증 (7번) |
| ✅ CPU 기본값 + `gpu/auto` 추후 | ❌ typed-decisions 추가 로드 |
| ✅ **(a) merge-style gate** — 턴 전 판단, 실패→Ornith degrade | ❌ (b) short-circuit (allow-list로 추후) |
| ✅ swap-free 게이트 + timeout → fail-to-Ornith | ❌ 런타임 토글 |
| ✅ `/fastcheck` 명시 커맨드 (c) — 사용자 통제망 | ❌ shared venv 최적화 |
| ✅ low-confidence는 `between`=log-only, Ornith에 힌트만 | ❌ GPU 모드 |

**MVP의 안전성:** merge gate는 **실패가 전부 Ornith로 우회**되므로 기존 llamacli 손상 가능성이 0에 가깝습니다 —
문서 철학 완벽 준수. 가장 낮은 난도 + 즉각적 효과(판단 결과가 Ornith 응답 품질을 보강).

## 실행 방법 (이 스킬에서 실제로 쓰는 법)

### 기본 경로: `fastcheck` (c)

Shell 도구로, **항상 `--no-check`** 를 붙여 실행하십시오. 이를 붙이지 않으면 laying 서버가 없/을 때
인터랙티브 `y/N` 설치 프롬프트가 나와 indefinitely 멈춥니다(연결된 터미널이 없어서 답할 사람이 없음):

```bash
python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py fastcheck \
  --text "<짧고 독립적인 yes/no 또는 다지선다 질문>" \
  --no-check
```

- **Exit 0 + 정답 출력** = laya가 답했습니다. 선택 옵션(확률 포함)이거나 0–1 점수, 그리고 어떤 내부 checkpoint가 왜 답했는지 함께 나옵니다.
- **Exit 1 (서버 안 떠 있음/연락 안 됨 / 요청 실패/타임아웃)** = 현재 laya를 쓸 수 없습니다.的预期이며 보고·재시도할 오류가 아닙니다 — 조용히 Ornith로 돌아가 스스로 생각하고 이어서 진행하십시오.
- 내부적으로 hard-cap(약 3초)이 있어 턴을 심각하게 막을 일은 없습니다.

### 단축 경로: `gate` (b, 기본 off)

`fastcheck`에 추가적인 판단을 얹은 것. 입력 문장에 대한 gate 질문을 laya로 보내고 **확률·신뢰도 임계값을 모두
충족할 때만** "Ornith를 생략하고 laya 답변으로 마무리"를 권합니다. `config.yaml`의 `shortCircuit: true`,
`actProbabilityThreshold`, `confidenceThreshold`가 이를 제어합니다(기본 false라 관여 안 함).

```bash
python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py gate \
  --text "<판단할 문장>" \
  --no-check
```

출력: laya 점수, 임계값 충족 여부(`thresholds met`), 그리고 `short-circuit` 제안(both-gate 충족 시에만
"Ornith 호출 생략하고 laya 답변으로 마무리" / 아니면 " Ornith로 정직한 확인 응답 요청").

### merge-style 개입: Node 래퍼 (a)

Turn 진입 전 laya 판단을 붙여 Ornith 응답을 보강합니다. 이 스킬이 수동으로 호출하기보다, Node wrappers
(llamacli core 코드와 통합된 경로)가 자동으로 씁니다. CPU 기본값 + swap 게이트 + timeout(fail-to-Ornith)
방식이며 `config.yaml`의 `laya.enabled`, `timeoutSeconds`, `questionType`이 제어합니다:

```bash
python3 /home/jeano/llamacli_plugin/scripts/run_laya_server.sh        # laya 서버 기동(CPU 기본, -y 없으면 확인 프롬프트)
python3 /home/jeano/llamacli_plugin/scripts/llamacli_integration.py gate --no-check   # merge-style gate 실행
```

### 상태 조회 (read-only, 안전)

```bash
python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py status
# → {enabled, installed, running, swapFreeKb, ramFreeKb} (JSON)
```

---

## 참고 사항

- 이 스킬은 llamacli core 코드를 건드리지 않습니다 — laya는 항상 별도 standalone script(위 shell 호출)를 통해 호출됩니다.
  script는 laya가 없을 때 no-op으로 degrade합니다.
- `config.yaml`의 `laya:` 섹션(`questionType`, `criteria`, `labels`, `baseUrl`, `enabled`, `shortCircuit`, ...)은
  `fastcheck`/`gate`가 기본 질문을 구성하는 방식을 제어합니다 — 보통 필요한 건 `--text` 하나뿐입니다.
- laya는 인증 없는 localhost 전용 서비스입니다 (`LAYA_API_KEY` 미설정).
- gate의 short-circuit 제안도 **권고**일 뿐, 파 destructive하거나 결과 있는 결정의 sole basis로는 절대 사용하지 마십시오.
