# 검증 요청: laya 적용 전/후 A/B 비교 테스트

## ⚠️ 실제 구현 확인 결과 — 테스트 설계 전에 반드시 읽으세요

`loop.ts`/`index.tsx`의 실제 코드를 직접 읽고 확인한 결과, 아래 두 가지가 이 문서
작성 당시 가정했던 것과 다릅니다. 테스트를 그대로 돌리면 결과가 왜곡되니, 아래를
반영해서 진행하세요.

1. **선택적 호출이 아니라 매 턴 무조건 호출입니다.** `runLayaGate`(index.tsx)는
   질문 유형을 가리지 않고, `laya.enabled`가 켜져 있으면 **사용자가 입력하는 모든
   메시지**에 대해 원문 그대로를 `fastcheck --text "<userText>"`로 laya에 보냅니다
   (laya는 이걸 기본 `noul` 참/거짓 질문으로 취급). "짧은 yes/no 판단일 때만" 같은
   선별 로직은 현재 없습니다.
2. **short-circuit(Ornith 생략)이 실제로는 구현돼 있지 않습니다.** `runLayaGate`는
   laya의 답을 상태 메시지로 띄우기만 하고, 그 뒤에 **Ornith 턴이 항상 그대로
   실행됩니다** — confidence가 높아도 Ornith를 건너뛰는 코드가 없습니다. 즉 지금의
   "B안"은 원래 의도한 "빠른 경로로 종료"가 아니라 "Ornith 실행 전에 laya의 참고
   의견 하나를 순차적으로 더 물어보고 가는" 구조이고, `layaGate` 호출이 `await`로
   순서대로(Ornith 턴 시작 전에) 실행되므로 **오히려 매 턴 laya 호출 시간만큼
   지연이 추가됩니다.**

**이게 테스트 설계에 의미하는 것**: 아래 원래 계획(§측정 항목의 short-circuit 발동
여부 등)은 **short-circuit이 실제로 구현된 뒤에나** 유효합니다. 지금 상태로는:
- "B가 A보다 빨라지는지"를 기대하고 테스트하면 안 됩니다 — 현재 구조상 **B가 A보다
  느려지는 게 정상**입니다(매 턴 laya 호출 지연이 순수 추가). 이 자체를 발견으로
  보고하세요.
- 대신 지금 측정 가능한 건 laya의 **답변 품질/관련성**입니다 — 질문 유형을 가리지
  않고 아무 메시지나 억지로 yes/no 확률로 답하게 만들었을 때, 그 답이 실제로
  쓸모 있는지 아니면 의미 없는 노이즈인지.
- short-circuit(진짜 속도 이득)을 측정하려면, 그 스킵 로직부터 구현한 뒤 이 문서의
  §측정 항목·§결과 집계를 그대로 적용하세요. 지금 단계에서는 **"현재 구현(매 턴
  advisory-only) vs 미래 구현(진짜 short-circuit)"을 구분해서 두 단계로 나눠
  보고**해주세요 — Phase 0(현재 상태 측정) → 이 발견을 바탕으로 short-circuit 구현
  → Phase 1(진짜 A/B).

## 목적

지금까지 만든 laya 연동(`gate`/`fastcheck`, short-circuit allow-list)이 **실제로 효과가
있는지**를 추측이 아니라 숫자로 증명합니다. "빠르다"는 이미 개별 호출 실측(0.5초 vs
Ornith 수십~90초)으로 확인됐지만, 그건 laya 단독 응답 속도일 뿐 — 실제 llamacli
사용 흐름에 끼워 넣었을 때 **전체적으로 이득인지, 어디서 손해를 보는지**는 아직
검증되지 않았습니다. 이 문서는 그걸 직접 실행해서 확인하는 절차입니다.

**코드 수정이 필요하면 하되, 이 문서의 목적은 어디까지나 측정입니다** — 측정 도중
발견한 버그는 고치고 넘어가되, 기능을 더 만드는 방향으로 새지 마세요.

## 비교 대상 (A/B)

- **A안 (Before, 베이스라인)**: `.llamacli/config.yaml`의 `laya.enabled: false` —
  모든 판단을 Ornith 혼자 처리.
- **B안 (After, Phase 0 = 현재 구현)**: `laya.enabled: true` — 매 턴 laya에 먼저
  물어보고 그 답을 상태 메시지로 띄운 뒤, **Ornith는 항상 그대로 실행**됩니다(위
  경고 참고 — short-circuit 스킵은 아직 없음). Phase 1(short-circuit 구현 후)에서는
  확신도가 임계값을 넘으면 Ornith를 생략하는 것까지 포함해서 다시 측정하세요.

같은 테스트셋을 A/B 양쪽에 **동일하게** 돌려서 비교합니다.

## 테스트셋 구성 (직접 만드세요)

**15~20개의 대표 질문**을 준비하세요. 아무 질문이나 넣지 말고, 실제로 laya가 유용할
법한 유형(짧은 yes/no·다지선다·긴급도 판단)과, 반대로 laya가 부적합할 법한 유형(복잡한
추론이 필요한 것)을 **의도적으로 섞으세요** — 좋은 케이스만 골라서 결과를 부풀리면
안 됩니다. 예시 구성 (그대로 쓰지 말고 실제 프로젝트 맥락에 맞게 조정):

- 명백한 yes/no 판단 5개 (laya가 잘 맞을 것으로 기대)
- 애매한 경계선 판단 5개 (laya 확신도가 낮게 나올 것으로 기대 — short-circuit이
  제대로 Ornith로 넘기는지 검증하는 용도)
- 복잡한 추론이 필요한 질문 5개 (laya가 부적합해야 정상 — 여기서 laya가 헛똑똑이처럼
  자신 있게 틀린 답을 내면 그게 바로 위험 신호)
- (선택) 한국어 질문 몇 개 포함 — laya의 `english` 체크포인트가 비영어를 어떻게
  처리하는지도 같이 드러남 (라우팅 로직상 `multilingual`로 안 가고 오답 낼 수 있음)

각 질문마다 **정답(ground truth)을 미리 사람이 정해두세요** — 애매하면 "정답 없음"으로
표시하고 정확도 계산에서 제외. 이게 없으면 "laya가 맞았다"를 판단할 기준이 없습니다.

## 측정 항목

각 질문마다 A/B 양쪽에서 아래를 기록하세요 (표로 정리):

| 항목 | A(Ornith만) | B(laya+Ornith) |
|---|---|---|
| 응답까지 걸린 시간(초) | | |
| 최종 답이 정답과 일치했는가 | | |
| (B만) laya의 확신도(confidence/answer_confidence) | | |
| (B만) short-circuit이 발동해서 Ornith를 건너뛰었는가 | | |
| (B만) laya가 실패/타임아웃해서 Ornith로 조용히 넘어갔는가 | | |

## 추가로 측정할 것 (시스템 자원)

테스트 전체를 도는 동안:
- `free -h`, `nvidia-smi --query-gpu=memory.used,memory.free --format=csv`를 **테스트
  시작 직전 / A 종료 직후 / B 종료 직후** 3번씩 찍어서 RAM/VRAM/스왑 변화를 기록.
  (오늘 laya의 CPU 모드가 시스템 OOM을 유발한 사고가 있었으니, 이번엔 안전하게
  재현되는지도 같이 확인하는 셈입니다.)
- B 테스트 도중 `journalctl --user -u llama-server`에 에러/OOM/cancel 로그가 찍히는지
  확인.

## 결과 집계 및 판정 기준

테스트가 끝나면 다음을 계산해서 보고하세요:

1. **평균 응답 시간**: A vs B — B가 A보다 얼마나(%) 빨라졌는지. short-circuit이
   발동한 케이스만 따로 평균을 내서 "짧은 경로일 때의 이득"도 별도로 보여주세요.
2. **정확도**: A vs B — B가 A보다 틀린 답이 늘었다면(특히 "복잡한 추론" 카테고리에서),
   그건 short-circuit 임계값이 너무 낮다는 신호이니 그 자체를 발견으로 보고하세요.
3. **short-circuit 발동률**: 전체 중 몇 %가 Ornith를 안 거치고 끝났는지, 그중 오답률은
   얼마인지 (발동했는데 틀렸다 = 가장 위험한 케이스 — 이게 하나라도 있으면 임계값을
   더 높여야 한다는 뜻입니다).
4. **자원**: RAM/VRAM/스왑이 A 대비 B에서 얼마나 늘었는지, 위험 수준(오늘 사고 때의
   swap 8GB 포화 같은)에 다시 가까워지는지.

## Phase 2 — `typed-decisions` 체크포인트(`agent_trace_observability`) 검증

`docs/agent-trace-observability-directive.md`에서 별도로 구현 지시한 기능입니다 —
사용자 입력이 아니라 **도구 호출 결과**(`run_shell`, 파일 write/edit)를 laya의
`typed-decisions` 체크포인트로 평가하는 기능. 그 구현이 끝나면 여기 이 절차로
검증하세요. Phase 0/1(사용자 입력 게이트)과는 **완전히 별개의 트랙**이니 섞어서
측정하지 마세요 — 비교 대상도, 테스트셋도, 지표도 다릅니다.

### 비교 대상

- **A2안**: laya trace 평가 없이 도구 호출 결과를 그대로 사용 (지금까지의 기본 동작)
- **B2안**: 도구 호출 직후 `typed-decisions` 체크포인트로 `action`/`outcome`/`risk`/
  `needs_review`/`urgency` 5개 판정을 받아 상태 메시지로 표시

### 테스트셋 (직접 만드세요, 최소 10개)

실제 `run_shell`/파일 편집 호출 결과를 최소 10개 준비하되, 반드시 아래 3개 카테고리를
섞으세요 — 이번에도 좋은 케이스만 고르면 안 됩니다:
- **명백한 성공** 3~4개 (예: `ls`, 정상 종료하는 테스트 실행) → `outcome=success`,
  `risk=none/low` 나오는 게 정상
- **명백한 실패** 3~4개 (예: 존재하지 않는 파일 읽기, 문법 에러 있는 스크립트 실행)
  → `outcome=failure` 나오는 게 정상
- **위험/파괴적 동작** 2~3개 (예: `rm`, `git push --force`, DB 스키마 변경 — 실제로
  실행하지 말고 **그 출력 텍스트만** 흉내 내거나, 안전한 sandbox에서 실행) →
  `risk=high`, `needs_review=true`가 나와야 정상. **여기서 안 나오면 그게 가장
  심각한 발견입니다** — laya가 위험한 작업을 위험하다고 못 알아채는 것이므로, 이
  기능을 신뢰도 낮은 참고용으로만 써야 한다는 뜻입니다.

각 케이스마다 사람이 미리 정답(action/outcome/risk/needs_review/urgency 기대값)을
적어두세요.

### 측정 항목

| 항목 | 기록 |
|---|---|
| laya의 5개 필드 응답 (action/outcome/risk/needs_review/urgency) | |
| 사람이 정한 정답과 각 필드가 일치하는가 (5개 중 몇 개 맞았는지) | |
| 응답 시간(초) — `english` 단독일 때와 비교해 더 느려지는지 | |
| `LAYA_MODELS`에 `typed-decisions` 추가 후 RAM 증가량 | |

### 판정 기준

- **위험 카테고리에서 risk/needs_review를 하나라도 놓치면** → 이 기능은 "참고용
  안내"로만 남기고, 실제 위험 명령 차단/확인 로직의 근거로는 절대 쓰지 말 것을
  명시적으로 문서화.
- 전체 필드 일치율이 낮으면(예: 5개 중 평균 2개 이하) → 질문 정의(`criteria` 문구)를
  다듬어서 재시도, 그래도 안 되면 이 워크플로우 자체가 이 프로젝트 맥락엔 안 맞는
  것으로 결론.

## 보고 형식

측정이 다 끝나면 위 표들과 1~4번 집계 결과를, **있는 그대로** 보고해주세요 — 결과가
기대에 못 미치거나(예: 생각보다 short-circuit이 거의 안 발동한다, 정확도가 떨어진다)
그것도 그대로 보고하는 게 목적입니다. "성공적으로 개선됐다"는 결론을 미리 정해두고
거기 맞춰 테스트를 구성/해석하지 마세요. 결과에 따라 다음 중 하나로 이어집니다:
- 뚜렷한 이득 + 안전 → 기본값(enabled)으로 전환 검토
- 애매한 이득/위험 신호 있음 → 임계값 재조정 후 재측정
- 이득 없음/역효과 → laya 단축경로 설계 자체를 재검토
