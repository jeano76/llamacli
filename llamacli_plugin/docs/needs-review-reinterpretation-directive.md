# 정정: `needs_review`가 "거꾸로"라는 이전 판단을 철회합니다 — 더 정밀한 테스트 필요

## 철회하는 것

Phase 2 결과 표에서 파괴적 삭제(`rm -rf node_modules` 등, risk 2.5~2.7)가
`needs_review ≈ 0.35`(낮음)이고, 단순 문법 에러(risk 1.6)가 `needs_review = 0.533`
(더 높음)인 걸 보고 "risk와 needs_review가 반대로 움직이는 버그/이상 신호"라고
판단했었는데 — **이 판단을 철회합니다.**

## 대안 가설 (더 타당함)

`risk`와 `needs_review`는 애초에 **같은 축을 재는 지표가 아닐 수 있습니다**:

- `risk` = 그 행동 자체가 얼마나 위험/되돌리기 어려운가 (행동의 위험도)
- `needs_review` = 그 **결과**가 얼마나 모호해서 사람의 해석·진단이 필요한가
  (결과 해석의 불확실성)

이 관점으로 보면 기존 데이터가 오히려 일관됩니다:
- **문법 에러**: "왜 실패했지?"가 불명확 → 진단 필요 → `needs_review` 높음 (타당)
- **`rm -rf` 성공**: 의도한 대로 정확히 실행됨, 결과 자체는 명확함(모호함 없음) →
  위험하긴 해도 "결과를 보고 헷갈릴 일"은 없음 → `needs_review` 낮음 (타당). 이
  해석에서는 진짜 검토가 필요한 시점이 "명령 실행 후 결과 해석"이 아니라 **"명령을
  실행하기 전, 그 명령을 써도 되는지"**이므로, risk와 needs_review가 다른 시점/다른
  질문에 답하는 게 자연스럽습니다.

## 요청 사항 — 가설 검증용 정밀 테스트

이건 어디까지나 **가설**입니다. 5개 샘플, 카테고리당 1~2개, 반복 없이 1회씩만 돈
지금 데이터로는 "이게 laya가 실제로 학습한 의미 있는 패턴"인지 "그냥 비보정된
잡음"인지 구분이 안 됩니다(로드 시점 경고: 일부 값이 [0.5,5] 범위 밖이라
비보정 처리한다는 RuntimeWarning이 실제로 있었음). 다음을 추가로 측정하세요:

1. **카테고리당 샘플 3~5개로 확장** — 특히 "위험하지만 결과가 명확한 성공"
   (파괴적 삭제 성공, 강제 push 성공 등) vs "위험하지 않지만 결과가 모호한 실패"
   (문법 에러, 알 수 없는 예외, 애매한 경고 메시지) 두 그룹을 표현만 바꿔가며
   각각 여러 개 만드세요.
2. **동일 입력을 3회 반복 실행**해서 `needs_review` 값이 매번 비슷하게 나오는지
   (결정론적/일관적인지), 아니면 호출마다 크게 흔들리는지 확인하세요 — 흔들리면
   신뢰할 수 없는 신호라는 뜻입니다.
3. 두 그룹(위험하지만 명확 vs 안전하지만 모호) 사이에서 `needs_review`가
   **가설대로(모호한 쪽이 높게) 일관되게** 나오는지, 아니면 뒤섞이는지 확인하세요.
