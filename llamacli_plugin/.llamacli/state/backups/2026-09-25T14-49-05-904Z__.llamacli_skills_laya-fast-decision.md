# laya fast decision (System 1 sidekick) — Korean

이 머신에서는 `laya`라는 소형 비추론 CPU 모델을 `http://127.0.0.1:8000`에서 돌려,
전용 질문(`choice` / `score` / `noul`)에 1초 이내로 답받습니다. 메인 모델(Ornith)의
완전한 추론 턴이 수십 초 걸리는 것과 대비돼요. **권고형 단축 경로**로 쓰되, 결코 sole
기재로 쓰지 않습니다.

## 이 스킬을 쓸 때 — 핵심 판단 (§4 적용처)

llamacli 내부에서 laya가 유용한 구체적 지점:

1. **툴 호출 전 위험도 분류** — 도구 실행이 안전할지 1차 분류, 높으면 Ornith에게 extra caution 힌트
2. **긴급우 우선순위** — 입력이 긴급/일반인지 분류 → 응답 순서 반영
3. **사소 변경 필터** — 커밋 메시지/diff가 의미 있는 변경인지 사소한 변경인지 필터링 (Ornith 긴 생성 줄임)
4. **응답 형식 예측** — 질문이 `choice`/`score`/`noul` 중 어떤 타입에 가까운지 → laya로 "정답이 이미 결정 됐나?" 확인, 미결정이면 Ornith에게 길게 추론 유도
5. **의도 분류** — 프롬프트 인젝션/모호한 지시 감지로 Ornith 보안 주입 강화

## 사용할 조건

실제로 빠른 분류/triage에만 사용하세요. 진짜 추론·코드 이해·결과가 따르는 판단은
Ornith가 담당합니다. laya 답을 "하나의 데이터 포인트"로만 취급하되, 최종 결정은 하지 마세요.

## 호출법 (§3/§5)

```bash
python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py fastcheck \
  --text "<짧고 자기 자신의 yes/no 또는 다지선다 질문>" \
  --no-check
```

- `--decision yes` / `--decision no` — "이 작업 진행해도 되나요?"/"이미 실패했거나 무해한가요?" 등
- Exit 0 + 답 출력 = laya 응답 success. 선택지(확률 포함) 또는 0–1 스코어, 어느 checkpoint가 답변했는지/이유 printed.
- Exit 1 (server not running / unreachable / timed out) = laya unavailable. 보고·retry 금지 — **silently Ornith로 fallback**하고 계속 진행. 스킬 실패 금지(문서 철학).

`--decision no`일 때: `score >= SCORE_THRESHOLD(0.5)`이면 affirming으로 간주해 yes 응답.

### short-circuit (b, 기본 off) — §8 권고 allow-list

`cfg["shortCircuit"]` 활성화 시에만 사용. **두 조건 동시 충족** 필요:
- `act_probability >= ACT_PROB_THRESHOLD(0.85)` AND `confidence >= CONFIDENCE_THRESHOLD(0.7)`

```bash
... fastcheck --text "..." --decision yes --json
```

- Exit 2 = short-circuit verdict: **both gates pass** → laya 단독으로 결론, Ornith 생략 가능.
- Exit 3 = both failed (proceed recommended) — affirming·affirming-doubt 둘 다 아니라 진행 추천.
- Exit 0/1 = 일반 응답 / 사용 안 함.

`--json`은 `act_probability`, `confidence` 등 내부 지표를 함께 출력(디버그/데이터 수집용). short-circuit 확인 시 "short_circuit: both gates pass — proceed on laya alone, skip Ornith"를 print.

## Notes (config & installation §5/§6/§7)

- 이 스킬은 llamacli core 코드를 건드리지 않음. standalone script에 대한 shell call일 뿐.
- `--no-check`: 답하거나 silently fail. 설치/기동 시도 안 함.

**swtich (§5):** `.llamacli/config.yaml`의 `laya:` 섹션:
- `enabled: true|false` — off이면 **아무 개입 없음**(laya health probe도 하지 않음)
- `questionType`: `noul`(기본, 참/거짓 확률) / `choice`(다지선다) / `score`(등급)
- `criteria`, `labels` — default question 프레이밍 제어 (`--text`가 보통 유일한 인자)
- `baseUrl` — 기본 `http://127.0.0.1:8000`
- `timeoutSeconds: 3` — laya 호출 데드라인, 초과 시 Ornith로 우회(§3)
- `shortCircuit: false` — 단축 경로 off-by-default
- `actProbabilityThreshold: 0.85`, `confidenceThreshold: 0.7`

**감지 (§6):** `status` 서브コマンド이 `{enabled, installed, running, swapFreeKb, ramFreeKb}` JSON을 read-only로 출력(안전). 이 값으로 laya 설치 여부/실행 여부를 판단.

**설치 (§6):** 감지→동의→설치→기동 플로우를 MVP에 포함하되, **사전 동의 없는 자동 설치는 배제** (디스크/네트워크 사용량이 큼). venv는 프로젝트별 (`<project>/.llamacli/laya-venv/`) 시작, 공유 venv는 이후 검토. 실패 시 laya 기능만 quietly inactive + 원인 로그 — llamacli 본체는 무손상(철학).

**GPU/CPU 모드 (§7):** 기본값 **CPU** (오늘 OOM 사고 때문). GPU VRAM 8GB 중 Ornith가 7.4GB를 독점 → laya CPU 권장. `gpu`/`auto`는 이후 검증 항목. auto이면 가용 GPU VRAM이 ~400MB checkpoint 올리기에 충분한지만 판단, 부족하면 CPU 폴백(`run-server.sh`의 동적 재시도 패턴 재사용).

**자원 게이트 (§2):** 리스킬 게이트는 RAM이 아니라 **SwapFree 기준**. SwapFree 부족 시 laya skip + Ornith 진행 (과거 OOM은 swap 포화 + CPU 모델 식).

## 부록: laya 세 가지 응답 스키마

laya 서버 체크포인트(english/typed-decisions)에 따라 세 스키마로 답변이 달라집니다.
`_decision_from_answer`가 이 세 가지를 모두 `(label, score, decision)`로 정규화합니다.
- `noul`: `{state: {prob_true}, usage}` — prob_true >= 0.9 → affirming / < 0.1 → negative / else neutral
- `choice`: `{answer_choices: [{text, probability}], usage}` — max-prob option. labels 순서가 "go/yes" 방향이면 affirming-doubt, 그 외 low-confidence는 Ornith만 신뢰
- `score`: `{answer_scale: [{label, score}], answer_choice}` — max-score label

## 부록 A: 실측 수치 (검토 근거)

| 지표 | 문서 서술 | **실测** | 평가 |
|---|---|---|---|
| 시스템 RAM | 타이트 / OOM 위험 | 총 ~30GB, 사용 14GB, 가용 ~16.9GB | 여유 충분 (과장) |
| Swap | 8G 꽉 참 | 8G 중 7.85G 사용(여유 192M) | 정확 — 지난 사고 잔재 + 지속 스왑 압박 신호 |
| GPU VRAM | 8GB 대부분 Ornith | **7452MB 사용 / 8192MB** | 진짜 제약. laya CPU로 두어도 Ornith VRAM 건드리지 않음 |

**결론:** 게이트는 RAM이 아니라 **SwapFree 기준**으로 잡아야 함(과거 OOM이 swap 포화 + CPU 모델 식).
laya 응답시간 실측 ~0.55초; Ornith eval time ~90초(max_tokens 4096).
