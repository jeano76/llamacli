# laya 빠른 판단 (System 1 사이드킥)

이 머신에서는 `laya`라는 작고 추론 없는 CPU 모델을 `http://127.0.0.1:8000`에서 돌려지고 있습니다.
 narrow하고 정형인 질문(`choice` / `score` / `noul`)을 1초도 채 안 되어 답하지만, 메인 모델(Ornith)의
전체 추론 턴은 수십 초가 걸립니다. **권고형 단축경로**로 쓰세요. 절대 결론의 유일한 근거로 쓰면 안 됩니다 —
위험하거나 파괴적인 결정엔 항상 Ornith로 진짜 추론을 거치세요.

> 핵심 설계: laya는 System 1(빠른 직관)이고 Ornith는 System 2(느린 심층 추론)입니다.  
> 이 스킬은 **System 1의 판단만 빠르게 받아온 뒤, 실제 결정은 System 2가 내리는** 구조를 목표로 합니다.

## 언제 쓰면 되는지

순전히 "빠른 분류/트리아주"에만 쓰세요 — 그렇지 않으면 걸리는 느린 모델 턴을 아낄 수 있을 때:
- 이 오류 메시지/출력이 임시 노이즈인지, 진짜 고칠 것인지
- 진정으로 긴급하거나 위험해 보여 전진 전에 알べき인지
- 짧은 옵션 목록 중 상황에 가장 맞는 게 뭔지

**쓰면 안 되는 것:** 진짜 추론·코드 이해·결과가 따르는 판단이 필요하면 절대 아닙니다.  
파괴적 명령 실행 여부, 수정이 맞는지, 보통 당신이 직접 생각해볼 문제는 laya로 결정하게 만들지 마세요.  
laya 답은 "추가 데이터 포인트"일 뿐입니다.

## 호출 방법

셸 도구로 Always `--no-check`와 함께 실행하세요 (안 하면 꺼져있는 laya 서버가interactive한 `y/N` 설치 프롬프트를 띄워 멈춥니다 — 답변할 터미널이 없기 때문입니다):

```bash
python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py fastcheck \
  --text "<짧고 독립적인 yes/no 또는 다지선다 질문>" \
  --no-check
```

- **종료 코드 0 + stdout에 답이 출력됨** = laya가 답했습니다. 선택 항목(확률 포함)이나 0–1 점수가 나오고, 어떤 내부 checkpoint가 왜 답했는지 나옵니다.
- **종료 코드 1 (서버 안 떠있거나 연결 실패/타임아웃)** = laya를 지금 쓸 수 없습니다. 이건 정상이고 재시도/보고할 오류가 아닙니다 — 조용히 Ornith로 스스로 추론하고 그대로 계속하세요.
- 내부적으로 최대 ~12초로 묶여 있어, 턴을 사실상 멈추게 하지 않습니다.

### fastcheck 출력 (실제 값)

현재 `--text`만 주면 위 문장으로 질문이 만들어지고, 예시 응답은 이렇습니다:

```json
{"label":"아니오","score":0.03,"decision":"no"}
```

- **label**: laya가 고른 항목 (예: "예"/"아니오", 등급, 옵션 텍스트)
- **score**: 그 확률/점수 (0–1)
- **decision**: normalize된 결론 — `yes` / `no` / `n/a`(판단 불가)

`--text` 대신 config로 기본 질문을 미리 짜놓을 수도 있습니다 (아래 "설정 참고" 및 §4参照).

## 단축 경로 short-circuit (Ornith를 생략하고 laya 답으로 끝내기) — off-by-default

명확할 때만 Ornith 호출을 아낄 수 있습니다. **의존도가 매우 높아져서** laya 답 하나로도 충분히 결론 낼 수 있는
경우엔 fastcheck가 `--short-circuit` 옵션과 함께 "이 답으로 마무리해도 됩니다"라는 확인 메시지를 뱉습니다.

그 조건은 **두 개가 동시에** 충족될 때뿐입니다:

- **P(act)** ≥ `actProbabilityThreshold`(기본 0.85): 이 항목을 고를 확률이 매우 높음
- **confidence**(=max probability) ≥ `confidenceThreshold`(기본 0.70): 답변 신뢰도가很高

이 두 게이트를 모두 통과해야 `--short-circuit`가 "이 답으로 마무리해도 됩니다"를 반환합니다.  
어느 하나라도 넘지 못하면 short-circuit는 `n/a`를 반환하고, **반드시 Ornith로 진짜 추론을 거치세요**.

> off-by-default 이유: 언제 laya만으로 충분한지를 잘못 판단하면 품질이 급락하기 때문입니다 (§검토 1항의 핵심 위험).  
> 따라서 기본적으로는 항상 Ornith(System 2)가 최종 판단을 하게 하고, short-circuit는 신뢰도가 극히 높아
> "이건 진짜로 안전한 답"인 경우에만 쓰는 allow-list 접근입니다.

## 설정 참고 (`.llamacli/config.yaml`의 `laya:` 섹션)

fastcheck의 기본 질문을 어떻게 만들지는 아래 값들이 결정합니다 (`--text`는 보통 안 줘도 됩니다):

| 키 | 의미 |
|---|---|
| `timeoutSeconds` | laya 호출 데드라인(초). 넘으면 Ornith로 우회 (§3, 7) |
| `questionType` | 기본 질문 타입: `noul`(기본)/`choice`/`score` (§4 참고) |
| `criteria` / `labels` | `choice`·`score` 타입에 쓸 항목 목록/등급 (noul은 안 씀) |
| `actProbabilityThreshold` | short-circuit의 P(act) 게이트 기본 0.85 |
| `confidenceThreshold` | short-circuit의 confidence 게이트 기본 0.70 |
| `enabled` | laya 연동 전체 on/off 스위치 (§5) |
| `shortCircuit` | short-circuit 경로 사용 여부 — **기본 false** (§2) |

`status` 커맨드는 읽기 전용으로 `{enabled, installed, running, swapFreeKb, ramFreeKb}` JSON을 뱉습니다.

## 4. 적용처 (llamacli 맥락에서 laya가 유용한 곳)

검토(§검토 4항)에서 제안한 후보들입니다 — 실제 스킬 코드로 자동 삽입되는 게 아니라 **이 스킬을 통해 사람이 호출**하는 방식:

| # | 후보 | 설명 |
|---|---|---|
| 1 | **툴 호출 전 위험도 분류** | 도구 실행 전에 빠르게 위험도 1차 분류 → 높으면 Ornith에게 extra caution 힌트 |
| 2 | **긴급우 우선순위** | 입력이 긴급한지(데이터 손실 등) 일반인지 1차 분류 → 응답 순서/노출 반영 |
| 3 | **커밋 메시지/diff "사소 변경 필터"** | 사소한 변경은 laya가 판단해 Ornith의 긴 생성을 줄임 (문서: "검증 필요") |
| 4 | **응답 형식 예측** | 질문이 `choice`/`score`/`noul` 중 어떤 타입에 가까운지 → laya로 미리 "정답이 결정됐나?" 확인, 미결정이면 Ornith에게 길게 추론 유도 |
| 5 | **의도 분류 (검증 필요)** | 시스템 프롬프트 인젝션/모호한 지시 감지로 Ornith 보안 주입 강화 |

> 참고: 이 스킬은 위 후보를 자동으로 실행하지 않습니다. 사람(혹은 추후 Node 래퍼)이 fastcheck로 호출하는 방식이라,  
> 아직 **(a) merge-style 자동 개입**까지는 아닙니다. §5 스위치가 켜진 뒤 Node 래퍼가 도입되면 턴 전에 자동으로 붙일 예정입니다.

## 5. 기능 on/off 스위치

- **위치**: `.llamacli/config.yaml`의 새 `laya:` 섹션 (`enabled: true|false`). 기존 config 구조와 자연스럽게 호환 (검토 §5).
- **off일 때 동작**: **완전한 종료**로 간주합니다. off면 laya로의 헬스체크조차 하지 않습니다 — CPU/메모리 오버헤드와 log noise를 막기 위해서 (§검토 5항, "상태만 조용히 확인"마저 금지).  
  따라서 `enabled: false`일 때 이 스킬은 그냥 Ornith로만 동작합니다.
- **토글**: 시작 시 1회 읽는 것으로 충분합니다 (_RUNTIME_ 토글은 add-on 철학에 반하는 복잡도).

## 6. 실행 환경에 laya가 없을 때 — 자동 설치/구동

llamacli가 이 스킬을 쓰려는데 해당 환경에 laya가 아예 없으면 대비해야 합니다.  
**이 스킬 자체는 설치/기동을 시도하지 않습니다** (`--no-check` = 답하거나 조용히 실패할 뿐).  
전체 흐름은 검토(§검토 6항, 6-1항)를 따르되 기본 방향은 (a)**사전 동의 + 프로젝트별 venv + 격리 + 독립 기동**입니다.

### 감지 (3단계 점진적)

| 순서 | 체크 | 판단 |
|---|---|---|
| 1 | **venv 경로** 존재 (`<project>/.llamacli/laya-venv/bin/python` or `~/.llamacli/laya-venv/bin/python`) | 없으면 다음 단계 |
| 2 | `/health` 응답 (venv 있어도 서버 안 떠 있을 수 있음) | 실패하면 C(구동)으로 |
| 3 | **prerequisites** (Python ≥3.10, `uv` 존재, disk 여유, HuggingFace 접근성) | 부족이면 D(설치 실패 격리)로 |

### 온보딩 플로우

```
[1] 감지: laya 없음 → "laya(System 1 고속판단)를 설치하시겠습니까?" (기본 N / off default와 일관)
      동의 시
[2] 전제 표시: Python 버전, uv 존재, 예상 스페이스(~수GB), 체크포인트 다운로드
      - "GPU VRAM 8GB 중 Ornith가 7.4GB 독점 → laya는 CPU 권장" 안내
      동의 후
[3] 설치: 프로젝트별 venv 생성 → `uv pip install laya[serve]` → HuggingFace 체크포인트(english) 다운로드
      - 백그라운드 실행 (진행률 표시, 프론트엔드 블로킹 금지)
[4] 기동: laya serve CPU 모드로 시작 → /health 확인 → active화
```

메뉴 선택지 = 6항의 (a)(b)(c)를 UI로: **(A)** 설치+자동활성화(추천), **(B)** 설치만하고 수단 켜기(off 유지), **(C)** 취소.  
이 메뉴가 6항 "(a) 사전 동의"의 사용자 선택 UI 구현입니다.

### 설치 실패 시 격리

| 실패 유형 | 대응 |
|---|---|
| Python 버전 불일치 (<3.10) | "Python X 필요" 안내 후 설치중지 (사용자 재선택 가능) |
| disk 부족 | "약 XGB 필요" 표시, 사용자 확인 후 진행/중지 |
| 네트워크 불가 (HuggingFace 접속 실패) | 체크포인트 다운로드 실패 → laya inactive 유지 + 원인 로그 |
| uv 미설치 | 자동 설치 시도 또는 수단 안내 |

**핵심**: 모든 실패는 **laya 기능 계층에서 격리** → llamacli 기본 대화/Ornith 동작 항상 정상 (철학:核心 손상 없음).

### 업그레이드 경로

laya의 두 "업그레이드"는 분리되어 있습니다.

| 대상 | 위치 / 버전 | 업그레이드 방법 |
|---|---|---|
| **코드** | PyPI `laya` 패키지 (`laya.serve`) | `uv pip install --upgrade laya[serve]` (또는 `pip install -U`) |
| **모델 가중치** | 체크포인트 `.safetensors`, 출처: **HuggingFace Hub — `convaiinnovations/laya`** | 패키지 최초 실행 시 `huggingface_hub`로 자동 다운로드 → 로컬 캐시 `~/.cache/huggingface/` |

### 기동 관리

독립 프로세스(systemd/detached)를 권장합니다. llamacli 생명주기에 묶이면 재시작마다 오버헤드가 발생합니다 (오늘의 systemd 경험 참조).

## 7. GPU / CPU 구동 모드 설정

- **세 가지(gpu/cpu/auto)**: 유효. 기본값 **CPU**는 오늘 사고 때문입니다. 정확한 이유는 "GPU VRAM이 얇아(8GB) laya를 올리면 Ornith와 다툴 위험"입니다. 문서가 CPU모드 실패를 OOM으로만 서술했지만 실제 원인은 VRAM 경합 가능성도 있습니다 (부록 A에서 RAM 과장 확인).
- **`auto`**: 가치 있음. 판단 기준: **가용 GPU VRAM이 laya 체크포인트(~400MB) + 여유 > X GiB**이면 GPU, 아니면 CPU 폴백. `run-server.sh`의 동적 재시도 패턴을 재사용할 수 있습니다.
- **GPU 모드 리스크**: ⚠️ 문서가 지적한 항목 그대로입니다. **Ornith 컨텍스트(`-c 24576`) 축소 연쇄** — laya가 GPU VRAM을 식이면 Ornith가 VRAM 부족으로 context가 축소됩니다.

설치 위치/위치: 6번과 동일하게 `.llamacli/config.yaml` laya 섹션에 통합합니다.

## 부록 A: 실측 수치 (검토 근거)

실제 관측은 문서 서술과 다릅니다. 진짜 제약은 RAM이 아니라 VRAM입니다.

| 지표 |文书 서술 | **실测 (2026-09-25 22:11, `free -h`)** | 평가 |
|---|---|---|---|
| 시스템 RAM | "타이트 / OOM 재발 위험" | 총계 ~30GB, 사용 14GB, 가용 ~16.9GB | 여유 충분 (과장) |
| Swap | 8G 꽉 참 | 8G 중 7.85G 사용(여유 192M, `si` 273M/s) | 정확이나 지난 사고 잔재 + 지속 스왑 압박 신호 |
| GPU VRAM | 8GB 대부분 Ornith | 7452MB 사용 / 8192MB | 진짜 제약. laya CPU로 두어도 Ornith의 VRAM은 건드리지 않음 |

**결론**: 리스킬 게이트는 RAM이 아니라 **SwapFree 기준**으로 잡아야 합니다(과거 OOM이 swap 포화 + CPU 모델 식으로 나타났기 때문).
