# laya fast decision (System 1 sidekick)

This machine also runs `laya` — a small, non-reasoning CPU model (`convaiinnovations/laya`)
exposed over HTTP at `http://127.0.0.1:8000`. It answers narrow, typed questions
(`choice` / `score` / `noul`) in well under a second, versus tens of seconds for a full
reasoning turn on the main model (Ornith). Use it as an **advisory shortcut**, never as
the sole basis for anything consequential or destructive.

This skill touches no llamacli core code; it is only a thin Python wrapper (`scripts/laya_integration.py`)
around `laya`'s HTTP API and the Node gate that calls it. When laya is unavailable the
wrapper degrades to a silent no-op, so an always-on shell call never stalls or errors.

## Core rules (read first)

1. **Advisory only — never final authority.** Treat `laya`'s answer as one extra data point, not
   a decision. It has no reasoning and no access to your tools/files; it can only score the text you
   feed it. Never let it decide whether to run a destructive command, confirm a fix, or anything
   that needs real judgment — those still go through Ornith (System 2).
2. **No interactive install.** `laya` is not guaranteed to be installed/running on every machine.
   Only ever call with `--no-check`; never without it (see "How to call it").
3. **Failure = no-op, not an error.** Exit code 1 means laya was unavailable right now — fall back to
   reasoning about it yourself and continue. Do not report or retry on a single failure.

## When to use this

Only for a genuinely quick classification/triage judgment that would otherwise cost a full slow-model
turn to reach — e.g.:
- Is this error message/output transient noise or something that actually needs fixing? (applies to §4 target 1/2)
- Does this look urgent/risky enough to flag before proceeding? (§4 target 2, security-relevant input)
- Given a short list of options, which one best matches the situation? (§4 target 3 — diff/scope triage)

Do NOT use it for anything that needs real reasoning, code understanding, or judgment with consequences.

## How to call it

Run via the shell tool, **always with `--no-check`** (without it, a missing/offline laya server
triggers an interactive `y/N` install prompt that will hang indefinitely — there is no terminal
attached to answer it):

```bash
python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py fastcheck \
  --text "<a short, self-contained yes/no or multiple-choice question>" \
  --no-check
```

- **Exit 0** → laya answered. stdout carries the chosen option (with a probability) or a 0–1 score,
  plus which internal checkpoint answered and why.
- **Exit 1** → laya was unavailable right now (server down, request failed/timed out). Expected; not an
  error to report or retry — silently fall back to reasoning yourself and continue.
- Internally hard-capped at ~3 seconds (`timeoutSeconds`), so it can never meaningfully stall a turn.

### Reading the answer (confidence matters)

`fastcheck` reports a `probability`/`score` in 0–1. Treat it as **trustworthy only when high**
(≥ your configured threshold, default `0.9`):
- **High confidence** → a reasonable extra signal to act on.
- **Low / ambiguous (< 0.9)** → treat as noise; prefer Ornith for anything consequential and only use it
  as one of several inputs.

## Gate: merge laya's read into Ornith (systematic, §5)

`fastcheck` answers a single question. To fold that answer *into the next reasoning turn* — i.e. hand
Ornith `laya`'s quick judgment alongside your request so it can weigh it — call the gate:

```bash
python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py gate \
  --text "<the same short question you would ask laya>"
```

- **Exit 0** → stdout is JSON with a `systemone_summary` field (human-readable, in Korean). Paste that
  text into your next message to Ornith as extra context. If laya was unavailable it prints a
  ready-to-use fallback line instead (still exit 0).
- **Exit 1** → should not happen for `gate` (it never errors on unavailability); treat the same as above.

This is the "merge-style" integration: laya judges first, its verdict is appended to Ornith's context,
and Ornith always makes the final call. Failure degrades cleanly — nothing is lost.

## Short-circuit verdict (optional, off by default)

For simple yes/no questions you can ask both systems at once and skip Ornith entirely if laya agrees:

```bash
python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py gate \
  --text "<yes/no question>" \
  --fastcheck-decision yes            # or "no" — the verdict you're checking against
```

This runs **both** `fastcheck` and `gate`, then prints a short confirmation: if laya's probability is
high (≥ `actProbabilityThreshold`, default `0.85`) **and** Ornith agrees with your intended decision,
it confirms and says how much time you saved — skip Ornith. Otherwise it tells you to still run the full
turn. This shortcut requires agreement from both systems; when in doubt, fall through to Ornith.

> Requires `shortCircuit: true` under `laya:` in config (disabled by default). Only use for low-stakes,
> clearly-typed yes/no calls where a wrong skip is cheap and reversible.

## Status & configuration

- To check whether laya is set up at all on this machine, run the read-only status command:
  ```bash
  python3 /home/jeano/llamacli_plugin/scripts/laya_integration.py status
  ```
  It prints `{enabled, installed, running, swapFreeKb, ramFreeKb}` as JSON — never errors, never installs.

- All behaviour lives under the `laya:` section of `.llamacli/config.yaml`:

| key | purpose | default |
|---|---|---|
| `baseUrl` | laya HTTP endpoint | `http://127.0.0.1:8000/v1/systemone` |
| `timeoutSeconds` | per-request cap for `fastcheck`/`gate`; a timeout degrades to Ornith/no-op | `3` |
| `questionType` | default laya question type framed by `fastcheck`: `noul` / `choice` / `score` | `noul` |
| `criteria` | free-text grading/ranking instruction for the `score` type | (none) |
| `labels` | ranked options for the `score` type; space-separated choices for `choice` | (none) |
| `enabled` | **master switch**. When off, no health probe or call to laya is attempted at all — fully inert | `false` |
| `actProbabilityThreshold` | min probability for a short-circuit confirmation to count as "yes" (`gate --fastcheck-decision`) | `0.85` |
| `confidenceThreshold` | min probability before a `fastcheck` answer is trustworthy | `0.9` |

When `enabled: false`, this skill never touches laya — not even a health check (per the "off must mean
fully off" requirement). When `true`, it answers, degrades silently when unavailable, and never errors.

## Absence / auto-install (§6)

On a machine that doesn't have laya yet, the wrapper **does nothing on its own** — no silent install, no
background venv creation, no multi-GB download (`--no-check` guarantees this). Detection is manual via
`status` (it reports `installed`/`running`). If not present, install it interactively and explicitly
(with the user's consent): create a project-local venv
(`<project>/.llamacli/laya-venv`, reuse `~/.llamacli/laya-venv` if already shared), then:

```bash
uv pip install laya[serve]      # or: pip install -U laya[serve]
python3 -m laya.serve --cpu     # pulls the english checkpoint from HuggingFace on first run
```

If `status` reports laya is present (`installed: true, running: true`) but a call still returns exit 1,
the server is likely unhealthy or overloaded — retry once after a short pause, then fall back to Ornith.

## CPU vs GPU mode (§7)

Always run laya with **`--cpu`** on this machine (`python3 -m laya.serve --cpu`). Reason: the GPU (8 GB)
is almost fully occupied by Ornith (~7.4 GB), so pulling laya onto the GPU would fight Ornith for VRAM
and can force Ornith to shrink its context — a cascade the OOM incident already showed risks stability.
The safe default is CPU; a GPU mode could be added later behind an explicit `gpu` config option with a
VRAM headroom check, but it must never become the default.
