# 로컬 모델 3종 코딩 능력 비교 — 2026-10-03

대상: **Qwen3.6 35B-A3B** (UD-Q4_K_M, `--n-cpu-moe 31`) · **Ornith-1.5 35B-A3B** (Q4_K_M, `--n-cpu-moe 32`) · **Ternary-Bonsai-2 27B** (PTQ1_0).
하드웨어와 서버 설정은 `docs/model-bench-2026-10-03.md` 와 같다 (RTX 2070 SUPER 8 GB, 컨텍스트 20,480 / 32,768).

> 이것은 **함수 수준 코딩 문제의 pass@1** 이다. 대규모 코드베이스 수정, 도구 호출을 쓰는 에이전트 작업,
> 코드 리뷰, 다른 언어는 측정하지 않았다. 문제 수가 적어(52개) 작은 점수 차이는 통계적으로 의미가 없다.

## 1. 방법

모델이 쓴 코드를 **실제로 실행해서 채점**한다 (서브프로세스, 타임아웃, 메모리 제한, 임시 디렉토리).

| 세트 | 문제 | 모드 | 채점 |
|---|---|---|---|
| HumanEval 부분집합 | 164 문제 중 4번째마다 **41개** | 생각 **끔**, `max_tokens 1024` | 데이터셋 자체의 테스트 |
| 직접 만든 문제 | **11개** (LRU 캐시, 수식 계산기, 구간 병합, 위상 정렬, 버그 수정, 로마 숫자, 줄바꿈, 다익스트라, 중첩 리스트 파서, CSV 한 줄 파서, 최소 윈도우) | 생각 **켬**(llamacli 기본값), `max_tokens 12000` | 정답 구현과의 **차분 테스트**(생성한 수백~수천 입력에서 출력 비교) |

공통: `temperature 0`, `repeat_penalty 1.1`(llamacli 값), 문제당 **1회 시도**.

**채점기 검증**: 직접 만든 11개 문제 모두에서 제가 쓴 정답 구현은 통과하고, 일부러 틀리게 쓴 구현(예: LRU 가 `get` 에서 순서를 갱신하지 않음)은 전부 실패하는 것을 확인했다.

재현: `scripts/coding_eval/` (`eval_model.py`, `custom_tasks.py`). 문제별 원자료: `scripts/coding_eval/results/2026-10-03/*.jsonl`.

### 2.3 실패를 구분하면 — 이 표가 점수보다 중요하다

실패는 두 종류다. **틀린 답**과 **답을 못 낸 경우**(생각이 길어져 토큰 상한에서 잘려, 코드가 아예 나오지 않음)는 의미가 전혀 다르다.

| | 틀린 답 | 답을 못 냄 (토큰 상한) | 답을 낸 것 중 정답률 |
|---|---|---|---|
| Qwen3.6 | 2 (HumanEval/32, `calc`) | 2 (HumanEval/132 @1024, `dijkstra` @12000) | 48 / 50 = **96 %** |
| Ornith | 4 (HumanEval/32 시간 초과, /76, /132, /160) | **0** | 48 / 52 = 92 % |
| Bonsai 27B | 2 (HumanEval/108, /132) | **4** (`calc`, `roman`, `parse_nested`, `parse_csv_line` 전부 12,000 토큰 소진) | 46 / 48 = 96 % |

- **Bonsai 의 직접 만든 문제 실패 4건은 모두 오답이 아니라 "12,000 토큰을 생각에만 쓰고 답을 못 낸" 경우다.** 정답을 낸 문제에서는 오답이 없었다. 코드 능력이 낮은 것이 아니라 **생각이 길고 끝을 못 맺는 경향**이다.
- 마찬가지로 Qwen 의 `dijkstra` 도 토큰 상한이다. Qwen 의 `calc` 만 진짜 오답이다 (`"1 2"` 같은 숫자 연속 입력에 `ValueError` 를 내지 않음).
- **HumanEval/132 는 세 모델이 모두 실패했다.** 이 문제의 설명이 모호해 보이지만 그것이 원인이라고 확인하지는 못했다. Qwen 의 경우 답이 1024 토큰에서 잘렸다.

## 3. 해석

- **정답률(답을 낸 문제 기준)은 세 모델이 거의 같다**(92~96 %). 52문제에서 48 대 46 의 차이는 오차 안이다. 순수한 코드 작성 능력에서 우열을 가릴 수 있는 데이터가 아니다.
- **차이는 효율에서 크게 난다.** 어려운 문제 11개를 푸는 데 Ornith 가 18,297 토큰·467 초, Qwen 이 64,127 토큰·1,604 초, Bonsai 가 59,173 토큰·2,614 초를 썼다. **Ornith 는 Qwen 의 약 1/3.5 토큰, 1/3.4 시간**으로 같은 문제를 모두 풀었다.
  - Bonsai 는 tg 가 느려(23 t/s 대 40 t/s) 같은 토큰 수가 시간으로 1.8배 더 든다. 거기에 생각이 길다.
  - 에이전트에서 응답을 기다리는 시간은 곧 이 값이라, **실사용 체감은 Ornith > Qwen > Bonsai** 로 갈릴 가능성이 높다 (이 문제 세트 기준).
- **HumanEval** 은 세 모델 모두 90 % 안팎으로 변별력이 낮다(39/39/37 중 2문제 차이는 노이즈).

## 4. 한계 (결과를 쓸 때 반드시)

- **문제 수가 적다** (HumanEval 41 + 직접 만든 11). 단일 시도, `temperature 0`. 다른 시드나 샘플링에서 순위가 바뀔 수 있다.
- **직접 만든 문제는 제가 만들었다.** 특정 모델에 유리하도록 고르지 않았지만, 같은 사람이 만든 11개일 뿐이며 공개 벤치마크가 아니다.
- **토큰 상한 12,000 이 결과를 좌우한다.** 상한 때문에 못 푼 5건(Bonsai 4, Qwen 1)이 상한을 늘리면 풀릴 수 있다. "정답 능력"이 아니라 "**12,000 토큰 안에 푸는 능력**"을 잰 것이다. 상한을 늘린 재측정은 하지 않았다.
- HumanEval 은 공개 데이터라 모델이 학습했을 가능성이 있다.
- 생각 **끔**(HumanEval)과 **켬**(직접 만든 문제)이 섞여 있다. 같은 모드끼리만 직접 비교해야 한다.
- 컨텍스트 창이 다르다(Qwen·Ornith 20,480 / Bonsai 32,768). 12,000 토큰 상한은 세 모델 모두 창 안에 들어간다.
- **측정하지 않은 것**: 에이전트로서의 도구 호출 정확도, 여러 파일 수정, 긴 컨텍스트 유지, 다른 언어, 한국어 주석/설명 품질.
