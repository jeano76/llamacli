## 0. 이 문서의 목적

llamacli의 **응답 속도**를 높이고 **토큰 비용**을 줄이기 위해, *생성형 모델이 아니라
작은 결정 모델(decision model)* 로 대체할 수 있는 지점을 찾고 그 효과를 실측한다.

원문 기사의 핵심을 이 연구의 설계 원칙으로 그대로 가져온다.

> Laya는 문장을 생성하지 않는다. 상태를 받아 **사전 정의된 선택지** 중 하나로
> 점수화해 돌려준다. 토큰을 하나씩 생성하지 않는다.

따라서 이 연구가 답할 질문은 "더 작은 모델로 더 좋은 답을 만들 수 있는가"가
**아니다**. 답을 만드는 게 아니라 **답이 필요한지, 얼마나 필요하고, 무엇을 먼저
보낼지**를 정하는 계층을 찾는 것이다.

### 0.1 두 지표의 정의 (혼동 금지)

| 지표 | 정의 | 측정 단위 |
|---|---|---|
| **속도** | 사용자가 Enter 를 누른 뒤 다음 입력을 할 수 있기까지의 시간. 메인 턴의 TTFT·wall clock, 컴팩션 대기, 결정 모듈 자체의 지연 | wall clock ms, p50/p95 |
| **토큰 절약** | 1턴·1세션 동안 **실제로 청구/전송된** prompt·completion 토큰의 감소량. 추정치가 아니라 `/tokenize`·`usage` 실측 | tokens/turn, tokens/session |

**속도가 빨라졌어도 토큰이 줄지 않으면 반쪽 성공이고, 토큰이 줄었어도 턴이 느려지면
실패다.** 두 지표를 항상 함께 제출하라.

### 0.2 Laya 결정 모델이란 (원문 기사에서 가져온 사실)

- Convai Innovations, **Apache 2.0**, 약 **421M 파라미터**, ModernBERT-large 인코더
  + 2층 결정 헤드. 공개 가중치, 자기 호스팅 가능.
- 결정 타입 3종:

  | qtype | 반환값 | 예 |
  |---|---|---|
  | `choice` | 사전 정의된 옵션에 대한 확률 | 결제 / 지원 / 영업 |
  | `score` | 순서 척도상의 예상값 | 0–4 긴급도 |
  | `noul` | P(true) | 이것은 피싱인가요? |

- **선택지는 20개 미만**을 권장. 큰 라벨 공간에서는 계층적 2단계로 나눌 것.
- 컨텍스트 예산: 영어 체크포인트 **512토큰**, 다른 변형은 1,024토큰.
- 학습은 RLCD(보정된 결정을 위한 강화 학습). 그래도 **배포 도메인에 맞춘 보정이 필요하다**고
  프로젝트 문서 자체가 인정한다. 프로젝트는 보정 후 성능이 크게 좋아졌다고 보고한다.
- 정확도(원문 Typed-Decision 평가):

  | 조건 | 정확도 |
  |---|---|
  | 무작위 기준선 | ~0.318 |
  | 기본 Laya 제로샷 | ~0.36 |
  | 파인튜닝된 typed-decisions | ~0.766 |

  → **이 표가 이 연구 전체의 위험告示다.** 제로샷 0.36은 무작위와 0.04 차이다.
  §3.3에서 이 수치를 어떻게 다뤄야 하는지가 이 연구의 성패를 가른다.
- 지연(원문): Tesla T4에서 수십 ms, 독립 MLX 포트가 M3 Max에서 영어 13.4ms ·
  다국어 7.4ms. **CPU에서의 수치는 원문에 없다 — 반드시 직접 측정하라(§5 T0-2).**
- 런타임: 공식 PyTorch/Transformers, 커뮤니티 ONNX(Node/TS) · MLX(Apple Silicon).
  즉 **CPU 전용 경로가 실제로 존재한다.**

### 0.3 ★ 제약 — 보조 결정 모델은 반드시 **CPU RAM** 위에서만 돌린다

이 제약은 선택이 아니라 요구사항이다. 위반한 결과는 이 문서에서 받아들이지 않는다.

1. **GPU VRAM을 쓰지 않는다.** `laya.load(..., device="cpu")`, 또는
   `CUDA_VISIBLE_DEVICES=""` 로 강제. `-ngl 0`. GPU를 쓰는 측정은 별 트랙으로
   분리하고, 본 트랙의 숫자에 섞지 마라.
2. **메인 추론 슬롯을 점유하지 않는다.** llama.cpp `-np 1` 서버의 슬롯은 공유되면
   안 된다. 결정 모델은 **별도 프로세스**(파이썬 venv 프로세스 또는 ONNX Runtime
   프로세스)로 격리하고, HTTP/프로세스 호출은 메인 턴의 `chat()` 요청과 **겹치지
   않게** 스케줄한다.
3. **RSS 예산을 명시하고 지킨다.** 가중치 `model.safetensors` 는 **842,609,220 B
   (약 803 MiB)** 다 (§8). fp32 가중치 + 활성화 + 런타임 오버헤드를 모두 포함해
   상한을 정하고(시작값 **1.5 GiB**), 초과는 거부하고 결정론적 fallback으로 내려간다.
4. **스왑 금지.** 이 머신은 스왑 7 GiB 중 6 GiB가 이미 사용 중이다(§1.6). 결정 모델이
   스왑을 건드리면 메인 턴의 지연이 무너진다. `vmstat` 의 `si`/`so` 가 실험 전후
   **0** 이어야 하며, 하나라도 늘면 그 측정은 폐기다.
   참고: 이전 시도에서 `resource_gate_ok()` 가 "스왑만 부족해도 무조건 차단"이라
   laya가 영영 호출되지 않았던 버그가 있었다. **RAM은 충분할 때 스왑 부족만으로
   차단하지 마라** — 대신 스왑을 *사용*하지 않는 것이 더 중요하다.
5. **CPU 경합을 측정하라.** 이 머신의 메인 서버는 `--n-cpu-moe 33` 으로 **CPU에서도
   33개 MoE 레이어를 계산한다**(§1.6). 즉 "메인은 GPU니까 CPU는 여유롭다"는 가정이
   **이 박스에서는 틀렸다.** 결정 모델은 `-t 2` 이하, `nice` 상향, `OMP_NUM_THREADS`
   제한으로 cpu-side를 자기 것이 아닌 메인 모델에 양보해야 하며, 그럼에도 측정치가
   나빠지면 기각한다.
6. **디스크.** `.llamacli/laya-venv` 는 이미 **5.4 GB**(torch 2.14 + CUDA 13
   bindings 포함)다. torch를 import 하는 것만으로 수백 MB RSS를 쓴다.
   본 트랙의 기본 경로는 **ONNX Runtime 경로**를 우선 검토하고(무CuDA, 수백 MB
   수준), 파이썬 venv를 쓸 경우 CUDA 패키지를 제거한 별도 venv를 쓸 것.

### 0.4 이 연구가 답해야 하는 세 질문

1. llamacli가 지금 **결정을 위해 생성 모델을 쓰고 있거나, 아무 판단 없이 하고 있는**
   지점은 어디인가 (§4 인벤토리)?
2. 그 지점의 결정이 틀렸을 때 **비용이 무엇인가** — 느려지는가, 토큰이 늘거나,
   아니면 **사용자의 작업이 조용히 사라지는가**(§3.4)?
3. 그 지점들 중 **안전한 실패가 가능한 것**만 골라, CPU RAM 위에서 실제 몇 %·몇 ms를
   얻는지 수치로 답하라.

### 1.1 ★ 1차 시도(laya "System 1" 게이트)는 왜 실패했는가 — 가장 중요한 섹션

이 저장소는 **이미 한 번** 정확히 이 연구를 시도했고 **삭제했다**.
`3eecbad refactor!: remove model acquisition, /fastcheck, and /reset`(2026-09-29).
삭제된 코드: `src/agent/gate.ts`, loop.ts 의 `system1` 턴 모드, `laya` config 블록,
`plugin/laya/`, `scripts/laya_integration.py` 등.

`src/agent/gate.ts`doc comment에 남은 실측(라벨 10개 프롬프트 세트):

short-circuit rate ............................. 80.0%  (8/10)

같은 라벨 세트로 **메타질문 4개를 바꿔 가며** 분리도를 측정했다
(skip-class 평균 − full-class 평균, 0.25 이상이면 사용 가능):

```

"does it need to read files?" ................... 0.183   분리 안 됨
"is it routine and safe?" ........................ 0.093   분리 안 됨
"is it answerable from general knowledge?" ....... 0.223   분리 안 됨
```

신뢰도도 보정되지 않았다 — 오답에 0.993, "git 히스토리 영구 삭제"에 0.72.

**구조적 원인(프롬프트 튜닝 실패가 아니다):** 판정자(=judge)가 게이트가 피하려던
**그 35B 모델 그 자체**였다. `~/.laya/settings.json` 의 모든 역할
(router/stager/chat/trace/omni)이 **이 앱 자신의 llama-server**를 가리키고 있었다.
자기 자신에 대한 메타질문을, ground truth도 없는 상태로 물었다.

**제거 사유 요약 (`README.md:660`):**

> 턴당 ~0.11 s, "이건 진짜 모델이 필요하다"인 프롬프트에 대한 일치율이 67%,
> 어떤 프롬프트 표현으로도 두 클래스를 구분할 수 없었고,
> 판정자는 피하려던 그 모델과 동일했다.

**이 연구가 반드시 지키는 결론 두 가지:**

1. **"모델을 건너뛰기"는 이 구조에서 구현 불가다.** Laya는 텍스트를 반환하지 않고
   확률만 반환하므로, 스킵은 곧 "**아무것도 답하지 않기**"가 된다. 그게 1차 시도의
   실제 동작이었다(응답 0자).
2. **틀린 판정의 비용은 "품질"이어야 하고 "정답"이면 안 된다.**
   → 따라서 §4의 Tier A(안전)만 기본 후보로 삼는다. Tier B(스킵·승인·실행)는
   §5 트랙에 넣지 않는다.

> 참고: 재도입 시 `scripts/project_persona_check.ts:497` 의 불변식
> ("`/fastcheck` 는 없었고 **계속 없어야 한다**")을 의도적으로 갱신해야 한다.
> 조용한 드리프트가 아니라 보이는 변경으로 남겨라.

### 1.2 지연시간의 구성 (2026-10-02 실측, 재측정 금지)

`docs/compaction-latency-research-prompt.md` §1.1–1.2 에 이미 확정돼 있다.

| 구간 | 실측 |
|---|---|
| 로컬 계산 전체(`selectKeptTail`+`sanitizeForSummary`+예산 산정+체크포인트 쓰기) | **5.6 ms** |
| `POST /apply-template` + `POST /tokenize` | **4.5 ms** |
| **`backend.chat()` 요약 생성** | **~27,000 ms** |

```
prefill 334 tok/s   decode 38 tok/s
메인 턴   7,244 프롬프트 토큰  75.9 s
컴팩션      22 프롬프트 토큰  40.8 s   ← prefill 은 prompt cache 로 ~0.3 s
```

- **async/계산 최적화로 얻을 수 있는 상한은 0.02%.** 그 방향에 시간을 쓰지 마라.
- **지연은 100% decode다.** prefill 캐시·템플릿 경량화는 토큰을 줄이지 않는 한
  지연을 줄이지 못한다.
- 컴팩션 지연 실측 범위: 턴당 **4.3–13.6 s**, 요약 예산 1,024토큰이면 38 tok/s 머신에서
  ~27 s.

프롬프트 예산의 일부는 "이번 턴 내용"과 무관하게 매 요청마다 나간다.

| 브라우저 도구 4개 스키마 | **1,238 토큰 = 16,384 창의 7.6%** | `config.ts:163-169` | 켜져 있을 때 항상 |
| 기본 시스템 프롬프트 | ~1,234자(≈340 토큰) | `index.tsx:73` | 항상 |
| 프로젝트 룰 인젝션 | `MAX_RULE_PROMPT_CHARS = 32_000` (**≈8–10k 토큰 상한**) | `loader.ts:208, 219` | 항상, 전량 |
| 스킬 인덱스 목록 | 8개 내장 스킬 + 프로젝트 스킬 | `loader.ts:294-297` | ≈150–250 토큰 |

> 즉 **"이 턴에 필요한 컨텍스트"가 아닌 것이 한창을 차지한다.** 이것이 토큰 절약
> 트랙(§5 T1–T2, T5)의 근거다. 결정 모델이 필요 없는 것부터 건드려라.

| 자기치유 회로차단기 | 실패 클래스 **2개뿐**(하드 타임아웃, 반복). `argsSignature` 가 **원시 JSON**이라 한 글자만 바뀌어도 회피 | `hermes/selfHeal.ts:19-55`, `loop.ts:1229` |
| 스킬 선택 | **매칭이 아예 없다.** 모델이 스스로 `load_skill` 를 호출해야 함 | `loader.ts:294-297` |
| 컴팩션 언어 판정 | user 턴 존재 여부 | `compactor.ts:552` |
| 모델 선택/라우팅 | **런타임 라우팅이 존재하지 않는다.** 전부 setup/슬래시 명령 시점 | `setup/modelSelect.ts:183`, `modelSwitch.ts:121` |

대충 처리되고 있거나, 아무것도 없이 지연되고 있는** 지점들이다. §1.1의 게이트가

## 2. 절대 하지 말 것

1. **사용자의 살아있는 세션을 건드리지 마라.** 현재 :8080 서버와 `~/.llamacli/config.yaml`은
   사용자의 것이다. 실험은 **전용 포트(8090+)·전용 모델 경로**에서만 한다.
2. **스왑을 쓰지 마라.** `vmstat` 의 `si`/`so` 가 0 이 아니면 그 측정은 무효다(§0.3-4).
3. **GPU 를 쓰지 마라.** `device="cpu"` / `CUDA_VISIBLE_DEVICES=""` 를 명시하지 않은
   측정은 제출하지 마라.
4. **1.1 의 1차 게이트를 재구현하지 마라.** 스킵·저가 턴 강등·"모델 불필요" 판정은
   이 연구의 범위 밖이다(§0.4-2).
5. **"모델이 사실은 필요 없었다"는 주장을 측정 없이 쓰지 마라.** 그것이 이 연구의
   결론일 수 있지만, 근거 없이 먼저 결론을 쓰지 마라.
6. **`npm test` 를 통과시킨 척 하지 마라.** 실패한 테스트가 옳다면 테스트를 고치고
   근거를 보고서에 적어라.
7. **정규식 목록을 "안전장치"로 포장하지 마라.** 이전 리스크 레일의 정직한 이름을
   유지하라: 보안 통제가 아니다(§1.1의 `HIGH_RISK_PATTERNS` doc comment 참조).

### 3.2 단일 측정 금지

- 최소 **5회 반복 후 중앙값**. p95 는 20회 이상.
- 측정 직전 **메인 슬롯 유휴**를 확인하고 기록할 것(`GET /slots` 의 `is_processing`).
  `-np 1` 에서는 다른 세션과 슬롯을 공유해 중앙값도 오염된다.
- A/B 는 **같은 프롬프트·같은 히스토리·같은 시드**로. 온도 기본값이 1.0 인
  서버에서는 같은 입력도 매번 다른 출력이므로, 품질 채점은 시드 고정 또는 반복 수를
  올릴 것(선례: `docs/compaction-latency-research-prompt.md` §3.2).
- **측정이 성립하는지 먼저 확인하라.** 100% 또는 0% 가 나오면 그게 아니라 측정
  부재다(같은 문서 §3.3.1 의 세 가지 함정 참조).

### 3.3 ★ 의사결정 품질 측정 — "정확도"가 아니라 "뒤집힘·정밀도·마진"

원문 표를 그대로 적용하면 이 연구는 끝난다: 제로샷 0.36 vs 무작위 0.318.
**따라서 채점 기준을 바꿔라.**

**금지:** 전체 정확도 36% < 50% 를 이유로 즉시 폐기.

**필요:** 아래 4개를 모두 보고하라.

| 지표 | 정의 | 왜 |
|---|---|---|
| **양성 클래스 정밀도** | Laya가 "챙기자"(또는 "작게 하자")라고 판단한 것 중 실제로 그랬던 비율 | 절대 정확도가 낮아도 **이 값만 높으면 쓸 수 있다** |
| **재현(recall)** | 실제로 그럴데 Laya가 놓친 비율 | 이것이 후속 처리(에스컬레이션)로 이어져야 한다 |
| **뒤집힘 비율(flip rate)** | 판정이 기본값을 뒤집은 전체 시도 중的比例 | 여기가 낮아야 토큰/지연이 실제로 줄어든다 |
| **기본선 대비 마진** | (양성 예측 평균) − (음성 예측 평균) | 원문 게이트의 4개 메타질문이 전부 실패한 바로 그 지표(0.25 이상이면 사용 가능) |

**핵심 reframing:**

> 저정확도 분류기도 **기본값이 "현재 동작"이고, 양성 클래스가 narrow하며,
> 뒤집힘이 드물고, miss는 안전하게 fallback되는** 경우에 쓸 수 있다.
> 이게 이 연구가 봐야 할 유일한 유효한 형태다.

예: "이 요청은 지금과 다르게 **더 적은** 컨텍스트만 있으면 된다"는 판단이 36%로
정확해도, 그 narrower 집합 안에서만 토큰을 줄이면 **사용자가 모르는 사이에도
안전**하다. 반대로 "이 요청은 안전하다"(80% 위험 판정이 아니라 안전 판정을 해야 하는
게이트)와 같은 방향은 쓰면 안 된다. §1.1의 교훈과 동일한 논리다.

### 3.4 실패 비용을 먼저 분류하라 (트랙 착수 전)

| 등급 | 실패 시 | 예 | 채택 가능성 |
|---|---|---|---|
| **A** | 현재 동작으로 자동 복귀, 비용만 소모 | thinking 예산을 잘못 잡음 | 채택 가능 |
| **B** | 되돌릴 수 있으나 사용자 동선 방해 | 자동 주입한 스킬이 무관한 내용을 넣음 | 조건부(하한·회수 설계) |
| **C** | 되돌릴 수 없음 | 사용자 메시지를 누락됨, 승인 없이 파괴 명령 실행, 사용자 입력을 없앰 | **채택 불가** |

**Tier B/C 를 A/B 로 만들 수 있는 설계가 있다면 그 설계 자체를 트랙으로 제시하라.**
없으면 그 지점은 하지 마라.

### 3.5 고정 픽스처 코퍼서스를 먼저 만든다

- 실제 세션 로그에서 **의사결정이 실제로 갈리는 지점**의 입력을 30개 이상 고르고
  라벨을 붙여 `src/` 하위 픽스처로 고정한다(기존 `src/compaction/fixtures/` 관례 준수).
- 라벨은 "그래서 뭘 해야 하나"로 적는다(정답 문장이 아니라 **정책**).
- **한국어를 반드시 포함하라.** 이 사용자는 한국어로 입력하고, 컴팩션 요약 언어
  문제도 실측된 전례가 있다(`compactor.ts:654-668`: 영어 지시만 주어 요약이 영어로
  나왔던 사례). 영어 체크포인트와 다국어 체크포인트를 **따로** 채점하라.
- 라벨 집은 **환자 출력**(자기 구현 기록)이 아니라 **판정 근거**로 남겨라.

| T0-2 | **CPU 결정 지연 실측.** threads 1/2/4 스윕, 원문 수치(T4 수십 ms, M3 Max 13.4 ms)와 **같은 조건이 아님을 명시**. 프로세스 기동 비용과 분리(상주 후 핫콜) | 예산이 §0.3-1과 맞지 않으면 무효 |
| T0-3 | **RSS 실측.** 가중치 로드 후 상주 RSS. 1.5 GiB 상한(§0.3-3) 초과 시 산술과 함께 배제 | 무효 |
| T0-4 | **CPU 경합 실측.** 결정 모듈을 메인 턴과 **동시에** 돌리며 메인 서버 tok/s 저하율 측정. `--n-cpu-moe 33` (§1.6) 때문에 이 box 는 해당 없음 | 저하 > 5%면 기본 OFF 외 대안 없음 |
| T0-5 | **한국어 분리도.** 제로샷 영어/다국어 체크포인트가 한국어 결정에서 무작위와 몇 %p 차이 나는가 | §3.3 마진이 0.25 미만이면 파인튜닝(T7) 없이는 무효 |
| T0-6 | **제거 이력 재확인.** `git show 3eecbad^:src/agent/gate.ts` 를 **통째로** 읽고, T0-1~6 결과가 1차 실패의 구조적 원인과 다른 이유 때문인지 서술하라 | 동일 원인이면 **종료**하고 근거를 남긴다 |

### T1 — 모델 없이 가능한 토큰 절감 (분자부터 줄여라) ★최우선★

**가설.** §1.3 의 고정 비용 중 상당수는 **판단이 필요 없다.** 결정 모델을
도입하기 전에, 결정 없이 줄일 수 있는 것을 먼저 줄여야 비교 기준선이 생긴다.

**할 것.** 순서대로 측정만 하고 근거 있는 것만 채택:
1. **A8 룰 인젝션 범위화** — 32,000자 상한이 실제 몇 룰이든 항상 붙는다. 단위 테스트
   명령(`npm run check:harnesses` 의 프로젝트 persona)을 근거로 **정적으로 결정할 수
   있는가**(예: 프롬프트 내 무관한 예시 코드 블록 제거)를 먼저 검토. 안 되면 §4 A8.
2. **A10 브라우저 스키마 게이팅** — 이미 기본 OFF. 현 상태가 최선이면 "개선 없음"으로
   **명시적으로 기록**(negative result도 결과다).
3. **A9 도구 결과 shaping** — `run_shell` 이 `maxBuffer 10 MB` 를 읽고 나서 자르는
   구조 자체를 머리/꼬리/에러부 3구간으로 바꾸는 식. Laya 불필요.
4. **스킬 인덱스 목록 압축** — 8개 스킬의 trigger 문장을 매 요청에 싣는 비용.

**성공 기준.** 고정 프롬프트 비용 p50 감소 **10% 이상**, 턴 p95 회귀 0.

**실패 시.** 감소 5% 미만이면 T2로 넘어가되 **기준선을 이 값으로 고정**하라.

### T2 — 스킬 사전 주입으로 턴 하나 아끼기 ★근본 후보★

**가설.** 스킬은 "모델이 스스로 `load_skill` 를 부르는" 유일한 경로다(`loader.ts:294`).
즉 **스킬이 필요할 때마다 메인 턴이 통째로 하나 더 돈다.** 7,244 프롬프트 토큰 ·
75.9 s인 턴이 하나 더 도는 것이 가장 큰 단일 비용이다(§1.2).

**해야 할 것.**
1. 실제로 스킬이 쓰인 세션에서 `load_skill` 이 몇 회 호출됐는지 **계측**하라.
   (임의 추측 금지 — `note()` 로 스스로 기록하게 하거나 로그를 세라.)
2. 사용자 텍스트(또는 최근 미완결 도구콜 상태)에서 **어떤 스킬이 관련 있는지**를
   Laya `choice`(≤20 라벨, 필요 시 2단계)로 결정하고, **본문을 시스템 메시지에
   바로 주입**한다.
3. 여전히 `load_skill` 경로는 유지한다(주입이 틀리면 회복 경로로 남긴다).

**반드시 함께 검증.**
- **주입은 되돌릴 수 없다**(B). 근거를 읽게 하려면(되돌릴 수 있는 실패) 주입보다
  **인덱스 요약만 강화**하는 변형이 나을 수 있다. 두 변형을 **따로** 측정하라.
- 라벨이 흩어지면 실패한다 → 라벨 수 ≤20 준수(원문 권장), 안 되면 2단계.
- **한국어 코퍼서스가 없다면 이 트랙의 수치는 신뢰할 수 없다**(T0-5).

**성공 기준.** 세션당 LLM 턴 수 감소 **15% 이상**, 그리고 턴 p50/p95 **무회귀**(이게
핵심이다. 토큰은 줄되 지연이 늘면 실패).

**실패 시.** 뒤집힘이 잦아서 회복 경로를 자주 타면(§3.3) T7(파인튜닝)로 넘어간다.

### T3 — thinking / 회신 예산 결정 (1.1 의 실패를 안 되풀이하는 조건부 트랙)

**가설.** `enableThinking` 기본값은 **한 번 오독된 측정 때문에 false 로 두었다가
다시 true 로 되돌린** 이력이 있다(`config.ts:176-198`의 doc comment 참조). 실측:
예산 420 토큰일 때 thinking on → 추론 1,874자·내용 0자·`finish=length`.
이제 예산 유지를 고쳤으니, **"이 턴에 사고가 필요한가"를 되돌아볼 자격이 생겼다.**

**반드시 지킬 것.**
- 스킵이 아니다. **예산만 바꾼다** (같은 모델, 켜고 끄는 선택). 오답이 되어도
  **품질 저하이지, 정답 소실이 아니다**(§1.1 결론 2).
- 판정 안 하면 **현재 동작(thinking on)** 이 된다. 기본값을 뒤집는 게 아니다.
- 측정은 **품질 점수와 함께** 제출하라. thinking을 껐을 때 "근거 없이 그럴듯한
  답변"으로 보이는 비율을 세라(§3.3 의 "안전한 실패" 기준과 같은 축).

**성공 기준.** 턴 p50 **10% 이상** 감소 + 품질 점수 하락 0 + 오답 시 사용자가
인지하는 시간 1 s 미만.

**실패 시(가능성 높음).** T0-6이 이 트랙의 근거를 이미 약화시켰다. 실패 시 **수치로
증명**하고 폐기하라.

---

### T4 — 컴팩션 경로 분기 (속도 최대 단일 후보)

**가설.** 컴팩션 지연의 **100%는 요약 생성(decode)** 다(§1.2). 체크포인트는 이미
**구조화 상태**(목표·완료 단계·진행 중·남은 단계·수정 파일·다음 도구콜·사유)를
기계적으로 기록한다(`PROMPT.md` §2.2, `compaction/checkpoint.ts`). 즉 **일부 구간은
LLM 요약 없이도 기계 추출만으로 대체 가능하다.**

**해야 할 것.**
- `mustPreserve` 는 지금 항상 빈 배열이다(`compactor.ts:526-533`). 비어 있는
  리스트를 채우는 일은 LLM 필요 없다 — **로컬 분류가 정확히 맞는 일**이다.
- 결정: (a) 요약 생략 + 체크포인트만 / (b) 짧은 요약 / (c) 현재 LLM 요약.
  이것은 3택 `choice` 다.
- 단, (a)는 "요약 = 대화 이해의 압축"이라는 §1.2 의 설계를 건드리는 것이므로
  **결정론적 입력**(tool 결과 위치, 파일 목록, 미완결 작업)으로 먼저 판단하고,
  판단 불가할 때만 모델에 물어라.

**성공 기준.** 컴팩션 p50 **50% 이상** 감소 + **mustPreserve retention 하락 0**
(기존 코퍼서스 `src/compaction/fixtures/` 재사용) + 컴팩션 발동 빈도 증가 없음.

**주의(실측된 함정).** 부분 절단 요약은 문장이 끊긴다(`trimPartialSummary`).
품질 측정이 이 시나리오에서 가장 크게 떨어진다. Laya는 텍스트를 못 만들므로
"요약을 조금만"이 아니라 "**요약하지 않기**"만 가능하다 — 그 차이를 명확히 구분하라.

---

### T5 — 히스토리 선별 (토큰 절약)

**가설.** 컴팩션은 고정 비율(0.35)로 예산을 정하고 tail을 통째로 보존한다. 그 전에
**관련도 낮은 턴**(이미 완료·폐기된 탐색·오류만 남은 구간)을 걸러내면 토큰을 줄일 수 있다.

**반드시 검증.** 순서가 반대다. **보존 후 → 버림**으로 구현하면 관련 정보를 잃는다.
거꾸로 하면 실수가 사용자 눈에 보인다. 이 위험을 인지하고 설계하거나, 버리되
`note()` 로 남기는 우회로를 두거나, 하지 마라.

**성공 기준.** 동일 세션 컴팩션 발동 간격 **20% 이상** 증가 + retention 하락 0.

---

### T6 — 상시 부하 검증 (켜 둘 수 있는가)

**가설.** 결정 모델은 **상주**해야 쓸 만하다(프로세스 기동 비용이 결정보다 크면 무의미).

**할 것.** 30분 연속 실제 세션(或 그 재생)에서 결정 모듈을 켜고:
- 메인 턴 p50/p95 회귀, 컴팩션 p50 회귀, 슬롯 경합, `vmstat` `si`/`so`, RSS 상한,
  결정 지연 p99 를 모두 기록.
- **한 번이라도 스왑이 늘면 그 트랙은 즉시 실패다**(§0.3-4).

**성공 기준.** 메인 턴 p95 회귀 **3% 이하**, 스왑 증가 0.

---

### T7 — 파인튜닝 (T2~T5 중 정확도가 부족한 것만)

**가설.** 원문 표는 제로샷 0.36 → 파인튜닝 0.766 이다. **이 트랙이 T2~T6의 실적이
나쁘고, 원인이 정확도일 때만** 쓴다. 라벨 코퍼서스(§3.5)가 있어야 한다.

**할 것.** §3.5 코퍼서스를 학습/검증으로 분리하고, **검증 셋에서 §3.3 의 네 지표를**
재측정하라. 파인튜닝이 **양성 클래스 정밀도**를 못 올리면 폐기다.

**실패 시.** 명확히 적어라. 그러면 이 연구의 결론은 "CPU 위의 제로샷 결정 모델로는
llamacli의 어떤 지점도 안전하게 개선되지 않는다" 이고, **그것도 유효한 결론이다.**

## 6. 산출물 형식

### 6.1 최종 보고서 — `docs/decision-layer-report.md`

```
## 1. 한 줄 결론
   (예: "A8 룰 범위화로 고정 프롬프트 -18%, A2 는 0.36 정밀도로 폐기. T6 상시 부하 통과.")

## 2. T0 사전 확인 결과
   표: T0-1 ~ T0-6 결과와, 실패한 항목이 어떤 트랙을 무효화했는지

## 3. §4 인벤토리 판정 표
   각 후보별: 채택 / 조건부 / 폐기 + 근거 지표 3개 이상

## 4. 트랙별 결과
   가설 / 실험 조건 / 측정 표 / §3.3 네 지표 / 판정

## 5. 속도 vs 토큰 트레이드오프
   가로축 = 씬당 토큰 절감, 세로축 = [턴 p50/p95 회귀, RSS, CPU steal]

## 6. 채택안 — 등급별
   - 즉시 적용 가능 (설정만)
   - 코드 변경 필요 (파일:라인 명시)
   - 채택하지 않음 — 근거

## 7. 배제한 가설과 그 근거
   (§1 의 측정값을 반복하지 말고, 각 트랙이 왜 실패했는지)

## 8. 재현 방법
   사용한 명령·스크립트·모델·플래그를 그대로. 추측 금지.
```

### 6.2 채택 안의 조건

모든 수정은 다음을 만족해야 한다.

1. `npm run check` 통과 (typecheck + test + harness 4종).
2. **기존 테스트를 삭제해서 통과시키지 마라.**
3. 변경 위치는 `파일:라인` 으로 명시.
4. §3.1 의 지표를 **변경 전/후 양쪽**으로 기록.
5. **기본값은 OFF(opt-in).** 근거: §1.1 과 삭제 이력. 켜려면 명시적 설정이 있어야 한다.
6. 결정 모듈이 죽거나 시간이 초과되어도 **현재 동작으로 복귀**해야 한다. (§3.4-A 의 정의)
7. 주석과 커밋 메시지는 **왜 그 값인지**를 담을 것. 이미 이 저장소의 관례다
   (`compactor.ts` 의 실측 표기 참조).

### 6.3 금지

- 근거 없는 "최적화"를 넣지 마라. §1.2 의 측정으로 0.02% 이하다.
- **안전장치를.regex로 대체하지 마라.** 사람의 확인을 대체하는 판정을 넣지 마라.
- §1.1 의 결론을 번복하는 설계(스킵·강등)를 "개선"으로 포장하지 마라.

## 7. 종료 조건

각 트랙은 다음 중 하나로 종료한다.

1. 성공 기준 충족 → §6.2 에 따라 반영하고 수치로 남긴다.
2. 실패를 **수치로 증명**했다 → 폐기하고 근거를 남긴다.
3. 이 머신의 한계로 불가능하다 (RAM·CPU·가중치 부재) → **산술과 함께** 폐기 근거를
   남긴다.

**"해봤는데 모르겠다"는 종료 조건이 아니다.** T6 이 막혔으면
T1 + T2 + T4 조합으로 승인을 확정하고 무엇을 못 했는지 명확히 적어라.

**전체 연구의 종료 조건:** T0-6 결과가 1.1 의 구조적 실패와 **같은 이유**로 모든
트랙을 무효화한다면, 그 즉시 종료하고 "llamacli에서는 결정 모델 계층이 이득이 없다"를
**근거와 함께** 보고하라. 이것도 성공한 연구다.
