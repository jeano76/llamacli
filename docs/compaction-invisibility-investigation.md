# 컴팩션을 "없는 것처럼" 만들기 — 추가 조사 보고서

> 요구: 적용된 컴팩션 개선 위에서, 더 줄이거나 컴팩션이 없는 것처럼 만드는 방법
> 실행일: 2026-10-04 · 대상: live `:8080` (`Ornith-1.5-35B-A3B-Q4_K_M`, `-c 98304 -np 1`)
> 방법: 읽기 전용 측정 + 소스 확인. 라이브 세션·설정·서버에 손대지 않음

---

## 1. 한 줄 결론

> **지금까지 최적화한 요약 생성(27초)은 컴팩션 전체 비용의 20%다. 나머지 80%는
> 컴팩션 직후 다음 턴의 전체 re-prefill(약 100초)이며, 누구도 모델링하지 않았다.
> "없는 것처럼"의 유일한 길은 re-prefill을 idle 시간으로 옮기는 것인데, 그 설계(O1)가
> 아래 있다. 트리거 조정·요약 예산 손보기는 수학적으로 총비용을 거의 안 바꾼다(§3).**

---

## 2. 비용 모델 — 컴팩션 1회의 진짜 청구서

### 2.1 세 항으로 나뉜다

| 항 | 내용 | 크기 (현재 설정) | 근거 |
|---|---|---|---|
| S | 요약 생성 (decode) | **~27초** (1,024 tok ÷ 38 tok/s) | `compactor.ts:559` 실측, 동일 박스·GPU·모델급 |
| P | 요약 요청 prefill | **~0.3초** (prompt cache 적중) | `compactor.ts:563-568` |
| **R** | **다음 턴의 전체 re-prefill** | **~100초** (34,400 tok ÷ 334 tok/s) | 아래 §2.2 — **추정치임을 명시** |

R의 계산:

- 윈도우 W = 98,304 (`ps`에서 `-c 98304` 확인).
- 트리거 t = 0.7 (기본값; 라이브 `~/.llamacli/config.yaml`에 compaction 섹션 없음 — 전부 기본값).
- 컴팩션 후 착지점 = 0.5 × t × W = **34,406 토큰** (`loop.ts:1714`, 시스템+도구+요약+tail 전부 포함).
- prefill 속도 334 tok/s (`compactor.ts:559`, RTX 2070급 + 35B-A3B + CPU MoE 30 — 현 서버 `--n-cpu-moe 33`과 동급).
- 34,406 ÷ 334 ≈ **103초**.

### 2.2 R이 실제로 발생하는 이유 (소스 확인됨)

llama.cpp 서버의 KV 재사용은 **엄격한 prefix 매칭**이다:

```cpp
// tools/server/server-context.cpp:3219
n_past = slot.prompt.tokens.get_common_prefix(input_tokens);
```

컴팩션은 시스템 메시지를 바꾼다(base +旧 요약 → base +新 요약). 새 프롬프트와
슬롯에 남은 이전 프롬프트의 공통 prefix는 base 프롬프트 토큰(약 1–2k)뿐이다.
따라서 **34k 중 ~32k 토큰이 다음 턴에서 전부 재계산**된다. middle-drop 설계에서는
어디를 잘라도 이게 발생한다 — 잘린 지점 이후의 모든 KV가 무효이기 때문이다.
이건 버그가 아니라 구조다.

### 2.3 분할 상환 수식 — 트리거 조정이 무의미한 이유

한 사이클(컴팩션 1회)당:

- 얻는 여유 I = t×W − 0.5×t×W = 0.5×t×W ≈ 34,400 토큰 (t=0.7)
- 턴당 증가 g ≈ 3,000 토큰 (실측 7,244 토큰 턴 + `loop.ts` 코멘트의 "tool-heavy step당 2–5K")
- 사이클 길이 ≈ 34,400 ÷ 3,000 ≈ **11턴**
- 턴당 분할 비용 = (S + R) ÷ 11 ≈ (27 + 103) ÷ 11 ≈ **12초/턴 ≈ 76초 턴의 15%**

그리고 트리거 t를 올리면 분자와 분모가 **같이** 커진다:

```
턴당 비용 = (S + p·0.5·t·W) ÷ (0.5·t·W/g) = S·g/(0.5·t·W) + p·g
```

t → ∞ 일 때 → **p·g** (re-prefill 단가 × 턴당 증가량). t=0.7에서 이미 항등식의
두 번째 항(p·g ≈ 9초)이 첫 항(≈2.4초)을 압도한다. **트리거를 0.85로 올려도 턴당
11.4초 → 10.9초.** 트리거 조정은 총비용을 안 바꾸고 "잦고 짧게 vs 드물고 길게"만
바꾼다(p50/p99 재분배). 빈도를 줄였다고 총량이 줄지 않는다.

## 3. 이미 돼 있는 것 — 다시 하지 마라

| 항목 | 상태 |
|---|---|
| 요약 요청의 prompt-cache prefix (`originalSystemText` verbatim) | ✅ 적용됨 (P 항목을 0.3초로 만듦) |
| 적응형 요약 예산 (`0.35 × 입력`, 하한 128) | ✅ 적용됨 |
| `summaryMaxTokens` / `summaryDeadlineMs` 노브 + 배선 | ✅ 적용됨 (`index.tsx:708-709`) |
| warm 컴팩션 idle-gap 실행 + 실패 시 fallback | ✅ 적용됨 (`index.tsx:975-993`, `loop.ts:596-604`) |
| 입력 큐잉 (컴팩션 중 타이핑 가능) | ✅ 적용됨 (`onQueueMessage`) |
| 상태줄 진행 표시 | ✅ 적용됨 |

warm은 S(27초)만 critical path에서 치운다. **R(100초)은 다음 `send()`에서 그대로
맞는다.** warm의 실효는 전체의 20%에 국한된다 — 코드 주석도 "moves the cost, it
does not remove it"라고 적고 있다.

## 4. 닫힌 선택지 (산수와 함께)

| 선택지 | 판정 |
|---|---|
| 병렬 슬롯(`-np 2`)으로 요약과 턴 분리 | ❌ VRAM free **803 MiB** (`nvidia-smi` 실측, GPU 90% 가동 중). 두 번째 슬롯의 98k KV는 GB 단위. 불가 |
| 윈도우 확대 (`-c` 상향) | ❌ 같은 이유. 803 MiB로는 수천 토큰도 못 늘림 |
| 작은 모델로 요약 | ❌ 같은 CPU에서 decode — 1B 모델도 20–40 tok/s급이라 27초가 그대로. 품질만 내려감. VRAM/CPU RAM도 추가로 먹음 |
| middle-drop 대신 앞부분 유지형 재설계 | ❌ prefix 매칭(§2.2)상 어디를 잘라도 잘린 뒤는 전부 재계산. 시스템 메시지만 byte-동일하게 두면 1–2k 토큰을 아끼는데 전체 34k의 3–6% — 무의미 |
| 추측 디코딩 | ❌ 선행 연구(`docs/compaction-latency-research-prompt.md` §5.10)에서 vLLM 주장의 비전환 확인. llama.cpp lookup도 S(20%)에만作用 |
| 요약 예산 추가 삭감 | ❌ S에만作用 + 품질 곡선 미확정(T3 "판정 불가"). 20%짜리 항을 깎는 일 |

## 5. 열린 선택지 — 순위순

### O1 ★ warm prefill — R을 idle로 옮기는 유일한 설계 (신규 제안)

**아이디어.** warm 컴팩션이 idle-gap에 끝난 직후, 같은 idle-gap에 **compact된
컨텍스트를 prefill만 하는 요청**을 보낸다. 다음 턴은 사용자 메시지가 끝에 추가될
뿐이므로 prefix가 그대로 맞아 **증분 prefill만** 낸다. R(100초)이 critical path에서
사라진다.

**오늘 당장 가능한 이유 (서버 변경 없음):**

- 슬롯 KV는 요청 간에 유지된다 (`cache_prompt` 기본 true — 요약 요청이 precedente turn의
  cache를 타는 것이 (§1.2) 이미 그 증거다).
- prefill-only 엔드포인트가 없어도 된다: `max_tokens=1` (또는 0이 허용되면 0)로
  보내면 prefill + 토큰 1개로 끝난다. 비용은 idle 슬롯 시간뿐이다.
- 취소 수단이 이미 있다: `backend.cancel()` (`types.ts:137-144`, Esc 취소용으로 존재).
  사용자 입력이 오면 warm-prefill을 취소하고 평상 동작으로 복귀 — **실패 모드가
  곧 현재 동작**이라 안전하게 opt-in할 수 있다.

**정직한 단서:**

- idle-gap이 100초 미만이면(사용자가 빨리 타이핑) prefill이 취소되고 효과 0.
  그래도 손해는 없다 (취소 → 현재 동작).
- 슬롯을 100초간 점유하므로, 그 사이 들어오는 send()는 대기 후 취소 처리된다.
  직렬화(`enqueue`)는 그대로라 경합은 없으나, 취소 경로의 테스트가 필수다.
- 효과의 실측은 라이브 세션에서만 가능하므로, 구현해도 기본값 OFF + Mane수치 보고가 조건이다.

**기대 효과 (모델 기준):** critical path의 컴팩션 비용 S+R ≈ 130초 → **≈0초**
(둘 다 idle + 취소 가능). 컴팩션이 사용자에게 "없는 것"이 된다.

### 구현됨 (2026-10-04, 기본값 OFF)

`compaction.warmPrefill` 노브로 구현했다. warm 컴팩션 직후 idle-gap에서 compact된
대화를 `max_tokens: 1`·`stream: false`로 1회 전송하고, `send()`·`compact()` 진입 시
취소한다. 실패·취소는 무음 swallow (fallback = 현재 동작). 취소 불가 백엔드에서는
시작조차 안 한다.

- `src/agent/loop.ts` — `warmPrefill` 필드, `startWarmPrefill()`/`stopWarmPrefill()`,
  `maybeWarmCompact` 양 분기 후 호출, `send()`·`compact()` 진입 시 중단.
  메인 턴과 요청 형태를 일치시킴 (messages 스냅샷 + `activeToolDefs()` + thinking 플래그).
- `src/config.ts` / `src/compaction/compactor.ts` (`CompactionThresholds`) /
  `src/index.tsx` / `src/setup/bootstrap.ts` — 노브 선언·배선·유지.
- 회귀 테스트 5개 (`src/agent/loop.test.ts`): 발화 조건·미설정 시 무동작·전송 중
  취소 후 턴 정상 진행·실패 swallow·취소 불가 백엔드에서 미시작.
- `npm test` 1291/1291, `tsc` 클린.

**효과 입증은 라이브에서만 가능**하므로 기본값 OFF를 유지한다. 시험하려면 라이브
설정에 `warmTriggerRatio` (예: 0.5)와 `warmPrefill: true`를 함께 넣고,
`[compaction] prompt cache warmed in Xs` 상태줄과 다음 턴 체감을 보고할 것.
공유 서버에서는 끄고 쓸 것 (단일 슬롯 점유 — 노브 주석에 명시).

### O2 warmTriggerRatio 시험 운용 (코드 변경 없음)

`warmTriggerRatio: 0.5`를 라이브 설정에 넣어 보고 체감만 본다. 단, §2.3의 수식대로
**총작업량은 오히려 는다** (0.5W에서 발화 → 15k만 확보하고 같은 비용 지불 → 더 잦게).
S만 숨기고 R은 그대로다. 효과 미미가 예상되나 비용 0으로 시험 가능. 기본값 변경은
수치 없이는 금지(저장소 규칙 §6.2).

### O3 컴팩션 후 착지점 하향 (0.5 → 0.3 × trigger)

R을 선형으로 깎는다 (34k → 20k, 103초 → 60초). 대가: tail 축소 = 품질. retention
코퍼서스(`src/compaction/fixtures/`)로 하락 0을 증명해야 채택 가능. 코드 변경 +
품질 입증 필요.

### O4 prefill 자체를 빠르게 (서버 플래그)

p가 전 계수다 (`-b`/`-ub` 상향 등). 단, 서버 재시작이 필요하고(라이브 세션 중단),
벤치용 2번 인스턴스는 VRAM에 안 들어간다(§4). **측정 없이는 손대지 마라.**
권고만 남긴다.

### O5 트리거 상향 (0.7 → 0.85)

§2.3에서 증명됐듯 총비용은 11.4초 → 10.9초/턴. p99는 나빠진다(드물고 길게).
**하지 마라.** "빈도를 줄였다"는 착시만 준다.

## 6. 권고

1. **O1을 구현 검토 대상으로 올린다.** R을 치는 유일한 설계이고, 실패 모드가 현재
   동작이라 안전하게 opt-in할 수 있다. 단, 효과 입증이 라이브에서만 되므로 구현해도
   기본값 OFF가 조건이다.
2. O2는 오늘 바로 시험 가능하다 (설정 한 줄, 되돌리기 쉬움). 기대치는 낮게.
3. O3·O4는 증거 비용이 크고 효과는 O1의 부분집합이라 후순위.
4. O5·요약 예산 추가 삭감은 하지 마라 (수학·선행연구가 이미 기각).

**구현 여부는 사용자 판단에 맡긴다.** O1 구현 시 필요 항목: `compact()` 후 idle 경로에서
`max_tokens=1` warm-prefill + `send()` 진입 시 취소 + 회귀 테스트(가짜 백엔드로 요청
발송·취소 검증) + 라이브 A/B 수치 보고.
