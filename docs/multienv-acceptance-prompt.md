# llamacli 다중 환경 순차 검증 프롬프트

> 이 문서는 **에이전트에게 주는 실행 지시문**입니다. 그대로 넘기면 됩니다.
> 대상 저장소: `/home/jeano/llamacli` (또는同级 clone)

---

## 0. 이 문서의 목적과 전제

당신은 **100명의 물리적 개발자**가 각자의 **서로 다른 OS와 하드웨어**에서
llamacli를 쓰는 상황을 담당한다. 아래 순서대로 TC를 실행하고, **하나 발견할 때마다
고치고 그 TC를 다시 돌린다.** 마지막 TC까지 통과하면 push + merge 한다.

### 반드시 지켜야 할 3가지 원칙

**1) 환경 격리 — 이게 가장 중요하다.**
각 TC는 **다른 TC의 흔적이 하나도 없는 상태**에서 시작해야 한다. TC-N이 TC-(N-1)의
설정·프로세스·캐시 때문에 통과/실패했다면 그 결과는 무효다. 매 TC 시작 시 반드시
아래 §2의 `TC-RESET` 스크립트를 **그 TC가 건드린 경로에 한정해서** 실행하고,
끝난 뒤에는 그 TC가 만든 것만 되돌린다. 전체 사용자 환경을 초기화하지 마라 —
그래야 병렬로 굴릴 수 있다.

**2) 실패는 관찰이 아니라 증거로 보고한다.**
"동작하지 않았다"가 아니라 **무엇을 입력했고 / 화면에 무엇이 떴고 / 기대와 무엇이
달랐는지**를 그대로 붙여라. 재현 안 되는 버그를 고치는 건 시간 낭비다.

**3) 한 번에 하나씩.**
여러 문제가 보여도 **하나만** 고치고 TC를 재실행한다. 동시에 고치면
"왜 통과했는지"를 알 수 없어 다음 TC에서 같은 문제가 되살아난다.

## 1. 대상 환경 매트릭스

아래 6개 프로파일로 전체 TC를 돌린다. 한 프로파일에서 통과해도 다른 프로파일에서
실패할 수 있다. 실패 원인이 **환경 차이인지 코드 버그인지**를 반드시 구분해서
기록하라. (예: "Windows에서만 경로 구분자 문제" → Windows 프로파일을 추가)

| # | 프로파일 | OS | GPU / VRAM | RAM | 코어 | 비고 |
|---|---|---|---|---|---|---|
| A | `nvidia-small` | Linux (X11) | RTX 2070 SUPER / 8 GB | 30 GB | 12 | MoE 스트리밍, VRAM 부족 경로 |
| B | `nvidia-large` | Linux (Wayland) | RTX 4090 / 24 GB | 64 GB | 32 | 전량 오프로드 경로 |
| C | `nvidia-none` | Linux | **GPU 없음** | 16 GB | 8 | CPU 전용 폴백 |
| D | `mac-arm` | macOS (Apple Silicon) | Apple M-series / 통합 메모리 | 16 GB | 10 | 통합 메모리, `/media` 없음 |
| E | `win` | Windows 11 + PowerShell | RTX 3060 / 12 GB | 32 GB | 12 | conhost, `\r\n`, `C:\` 경로 |
| F | `linux-musl` | Alpine (musl) | 없음 | 8 GB | 4 | 최소 환경, `uv`/`pip` 없음 가능 |

각 프로파일에서 **반드시 사전 준비**를 명시하라:
- `llama.cpp` 설치 여부 (있음 / 없음 → 빌드 경로)
- GGUF 모델 존재 여부 (있음 / 없음 → 다운로드 경로)
- `llama-server` 이미 실행 중인지 (포트가 이미 점유된 상태)

> **포트 점유 상태는 반드시 변수로 만들어라.** 8080이 비어 있는 경우와
> 이미 健康한 서버가 있는 경우는 **완전히 다른 코드 경로**다. 과거에
> "이미 서버가 있는데 포트를 옮겨 두 번째 서버를 띄워 OOM"이 실제로 발생했다.

## 2. TC 격리 스크립트 (매 TC 전후로 실행)

```bash
#!/usr/bin/env bash
# TC-RESET — 직전 TC가 만든 흔적만 되돌린다.
# 주의: 사용자 전체 환경을 지우지 않는다. 병렬 실행이 전제다.
set -uo pipefail

PROJ="${PROJ:?PROJ=<테스트 프로젝트 경로> 필요}"
MODELS="${MODELS:-$HOME/models}"

# 1) 이 TC가 띄웠을 수 있는 프로세스만 종료
#    (사용자가 개인적으로 돌리는 서버는 건드리지 않는다 — PID 파일이 있을 때만)
if [ -f "$PROJ/.llamacli/test-server.pid" ]; then
  kill "$(cat "$PROJ/.llamacli/test-server.pid")" 2>/dev/null || true
  rm -f "$PROJ/.llamacli/test-server.pid"
fi

# 2) TC가 만든 임시 laya 서버 정리 (systemd transient unit)
systemctl --user stop laya-serve.service 2>/dev/null || true

# 3) 프로젝트 상태 초기화 — 이것이 "최초 구동"을 재현하는 방법이다
rm -rf "$PROJ/.llamacli" "$PROJ/.git" 2>/dev/null || true
mkdir -p "$PROJ"

# 4) 모델 디렉터리 정리 여부는 TC가 명시한다.
#    기본값은 **삭제하지 않는다** (20 GB를 매번 받으면 검증이 불가능하다).
#    TC-06처럼 "모델이 없는 상태"가 검증 대상인 경우에만:
#     rm -f "$MODELS"/*.gguf

# 5) 포트 확인 — 비어 있어야 한다. 안 비어 있으면 TC를 시작하지 말고 보고
for p in 8080 8099; do
  if ss -ltn 2>/dev/null | grep -q ":$p "; then
    echo "BLOCKED: $p 포트가 이미 사용 중. TC를 시작할 수 없습니다."; exit 1
  fi
done
echo "TC-RESET OK"
```

**격리 검증 방법:** TC-N을 두 번 돌려 결과가 같으면 격자가 성공한 것이다.
두 번 중 다른 결과가 나오면 그 TC는 격리 실패다 — 먼저 격리를 고칠 것.

## 3. 순차 TC 목록

각 TC는 **① 준비 → ② 실행 → ③ 판정 → ④ 실패 시 1개만 수정 후 재실행**을 거친다.
아래 표의 "기대"가 그대로 판정 기준이다.

### Phase 1 — 최초 구동 (First Launch)

| ID | 시나리오 | 조작 | 기대 |
|---|---|---|---|
| **TC-01** | 완전히 빈 디렉터리 | 빈 폴더에서 `llamacli` 실행 | 부트스트랩이 하드웨어 감지 → llama-server 탐색/빌드 → 모델 결정 → 다운로드 → config 기록 → **프롬프트가 입력 가능 상태로 뜬다**. 콘솔에 진행 표시가 살아있고 멈추지 않는다 |
| **TC-02** | llama.cpp 없음 | PATH·`~/llama.cpp` 비우고 실행 | 빌드 의존 패키지 설치 후 소스 클론 + 빌드. 진행 메시지(`cmake 설정 중`/`빌드 중`)가 보인다. 빌드 후 프롬프트 준비 |

| **TC-08** | 평가코레 | 8코어 이상에서 실행 | threads가 코어 수보다 크지 않다. **GPU가 있으면 CPU보다 우선**된다 |

| **TC-44** | 붙여넣기 판정 | 정상 속도(≥100ms/키)로 `/fastcheck on` 입력 | **붙여넣기 칩으로 오인되지 않는다** (과거 실제 실패) |

### Phase 7 — 컴팩션

| ID | 시나리오 | 조작 | 기대 |
|---|---|---|---|
| **TC-45** | 소요 시간 | 컨텍스트를 임계치까지 채움 | `[compaction] N.Ns (요약 …)` 가 출력된다 |
| **TC-46** | 예산 상한 | `compaction.summaryMaxTokens` 설정 | 설정값을 존중한다. 단 **창 크기가 항상 이긴다** |

## 4. 실행 루프 (이대로 반복)

```
for 각 프로파일 A~F:
  for 각 TC-01 ~ TC-47:            # 반드시 이 순서
      TC-RESET                     # 격리
      실행 TC
      판정
      if 실패:
          원인 분석 → **버그 하나만** 수정
          npm run typecheck && npm test   # 회귀 확인
          **같은 TC 재실행** (격리 후)
          재현 안 되면: 되돌리고 다음 TC
          통과하면: 뒤의 TC를 계속
      if 통과: 기록
```

### TC-N 통과 판정

- 검증이 **코드로 남아 있어야** 한다. `src/**/*.test.ts`에 추가하거나,
  pty 기반이라면 `scripts/`에 재현 스크립트로 남겨라.
- "일단 넘어간다"를 금지한다. 실패한 TC는 **이슈로 기록하고** 통과할 때까지 못 가거나,
  사용자에게 "이건 막았습니다"와 함께 명시적으로 보고한다.

## 5. 보고 형식

TC 하나가 끝날 때마다:

```
### TC-NN (프로파일 A) — PASS | FAIL
- 입력: (실제 조작)
- 기대: (기대 동작)
- 관찰: (터미널에 실제로 나온 것. 스크린샷/로그 발췌)
- 판정: PASS / FAIL (FAIL이면 어느 문장이 어긋났는지)
- 조치: (수정한 파일:라인 / 또는 "수정 없음 — 사유")
```

최종 요약에 반드시 포함:

1. 프로파일 × TC 통과율 매트릭스
2. **OS/하드웨어 의존 실패 목록** (어떤 환경에서만 나는지)
3. 수정한 버그 목록 (원인 → 조치 → 재발 방지 테스트)
4. 남은 미해결 항목과 그 영향
5. `npm test` 통과 수 / 총 수
