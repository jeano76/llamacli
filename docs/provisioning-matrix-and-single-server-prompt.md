# llamacli 구동 시 환경 매트릭스 최적화 + 단일 서버 정책 — 구현 및 검증 프롬프트

> 이 문서는 에이전트(또는 개발자)에게 그대로 넘기는 작업 지시서다.
> 선행 문서: `docs/first-run-provisioning-prompt.md`(최초 구축), `docs/multienv-acceptance-prompt.md`(다환경 수용).
> 이 문서는 그 위에 **(a) 환경 매트릭스 전수 검증**과 **(b) 단일 서버·사용자 확인 정책**을 못 박는다.
> 이미 구현된 것은 다시 만들지 말고, 아래 매트릭스로 **빈칸/오동작을 찾아 고친다.**

---

## 0. 목표 (한 문장)

`llamacli` 를 어떤 머신에서 처음 구동해도, 아래 축의 조합마다 **(1) 엔진(llama.cpp) → (2) 최적 설정 → (3) 구동 가능한 모델의 설정 또는 다운로드 → (4) 단일 포트 서버 기동**까지 사용자 개입을 최소로 끝낸다.
단, **이미 떠 있는 서버를 건드리는 순간에는 반드시 사용자 확인을 거친다.**

## 1. 환경 축 (매트릭스)

| 축 | 값 |
|---|---|
| A. llama.cpp | 설치됨(PATH / 설정 binPath / 모델 인접 / `~/.llamacli` 설치본) · 미설치 · 설치됐으나 모델 양자화를 못 읽는 낡은 빌드 · 깨진 바이너리 |
| B. GPU | NVIDIA+CUDA 사용 가능 · NVIDIA 지만 CUDA 툴킷/드라이버 부족 · AMD/Intel(Vulkan) · Apple Metal · GPU 없음 |
| C. VRAM | 0 · 4 · 6 · 8 · 12 · 16 · 24 · 48 GiB (여유 VRAM 기준, 다른 프로세스 점유분 제외) |
| D. RAM | 4 · 8 · 16 · 32 · 64 GiB |
| E. OS/쉘 | Linux(bash, zsh, fish, sh/dash, 루트 아님/sudo 없음) · Windows(PowerShell, cmd, Git-Bash, WSL) · macOS(zsh) |
| F. 서버 상태 | 아무것도 없음 · 우리 설치 소유 서버가 8080/다른 포트에서 실행 중 · 외부(타 프로그램) 서버가 포트 점유 · 서버 2개 이상 · 좀비/로딩 중 |

전수 조합(수천 개)은 필요 없다. **축별 경계값 + 위험 조합**(§5)을 합성 프로파일 표로 만든다.

## 2. 요구사항

### R1. 엔진 확보 (축 A·B·E)
1. 이미 쓸 수 있는 llama-server 가 있으면 **재다운로드/재빌드하지 않는다.** 탐색 순서: 설정 `llama.binPath` → PATH → 모델 인접 런타임 → `~/.llamacli` 설치본 → 알려진 빌드 디렉토리.
2. "있다"의 기준은 파일 존재가 아니라 **실행해서 확인**(`--version`)이고, 모델 파일이 있으면 **그 모델을 실제로 읽을 수 있는지 probe** 한다. 못 읽으면 후보에서 제외하고 다음 후보로, 전부 실패하면 새 엔진을 받는다.
3. 없으면 사다리: **stock 사전빌드(GitHub release, sha256 검증) → Vulkan → CPU → 소스 빌드**. 각 단계는 *실행 검증*을 통과해야 성공으로 친다(바이너리만 받고 끝내지 않는다).
4. 백엔드 선택은 하드웨어 기준:
   - NVIDIA: 드라이버가 지원하는 CUDA 버전에 맞는 릴리스 자산 선택(`cudaTagFor`/`pickPublishedCudaTag`). 없으면 Vulkan, 그다음 CPU.
   - AMD/Intel: Vulkan. Apple: Metal. 그 외: CPU.
   - CUDA 가 *있어 보이지만* 실제로 못 돌리면(드라이버 불일치 등) 조용히 CPU 로 떨어지지 말고 **이유를 한 줄로 알리고** 다음 백엔드로 간다.
5. 소스 빌드가 필요하면 빌드 도구(git/cmake/컴파일러) 점검 → 부족한 것만 OS 패키지 매니저(apt/dnf/pacman/zypper/apk/brew/winget)로 설치 계획 제시. **sudo 가 없거나 root 가 아니면 임의로 실행하지 말고** 사용자가 실행할 명령을 출력한다.
6. Windows: zip 자산(`llama-<tag>-bin-win-*`) + CUDA 런타임(`cudart-*`) 동봉 처리, PowerShell/cmd 모두에서 경로·실행 확장자(`.exe`)·따옴표 규칙 올바르게. 소스 빌드는 안내만 해도 된다(비목표로 명시).

### R2. 최적 설정 (축 B·C·D)
`tuneForHardware` 가 아래를 **측정 가능한 규칙**으로 결정한다 (매직넘버 금지, 근거를 `rationale[]` 에 남긴다).
- `-ngl`(GPU 레이어), `--n-cpu-moe`(**MoE 모델에만**; 밀집 모델에는 절대 붙이지 않는다 — GGUF `expert_count` 로 판별), `-fa`, KV 캐시 타입(`q8_0`), `-c` 컨텍스트, `-t/-tb` 스레드, `-np 1 -no-kvu`.
- KV 비용은 **GGUF 헤더에서 읽는다**(`readGgufKvShape`) — 파일 크기로 추정하지 않는다. 하이브리드 모델(`full_attention_interval`)은 KV 가 있는 레이어만 센다.
- 컨텍스트 상한은 VRAM 잔여 + RAM 으로 계산하고, 컴팩션(창의 70% 도달 시 → 35% 로 축소) 이 의미 있도록 **최소 컨텍스트 하한**(예: 8k 미만이면 경고)을 둔다.
- VRAM 0 / RAM 부족 머신: 실행 가능한 가장 작은 모델 + 낮은 컨텍스트, 그리고 "느릴 수 있음" 경고. 실행 불가능(모델이 RAM+VRAM 에 안 들어감)이면 **받지 않고** 이유를 말한다.

### R3. 모델 결정/확보 (축 C·D)
1. 구동 가능한 최선을 고른다 (현재 카탈로그: Ornith-1.5-35B-A3B(MoE), Ornith-1.5-9B(밀집)). 판정 근거(VRAM 상주 / RAM 스트리밍 / 불가)를 사용자에게 보여준다.
2. 이미 설정된/디스크에 있는 동일 모델은 **재사용**(다른 디스크 포함, 이름·크기 검증). 중복 다운로드 금지.
3. 다운로드: 임시(staging) 디렉토리 → **sha256 검증 통과 후** 최종 디렉토리로 원자적 이동, 멀티 연결 + 이어받기, 한 줄 진행률(스크롤 금지), 디스크 여유 공간 사전 점검(여유 부족 시 다른 마운트 제안).
4. 사용자가 `/models` 로 직접 고른 모델은 **그 모델이 받아진다**(다른 모델로 바꿔치기 금지; 같은 패밀리의 다른 양자화만 허용하고 알린다).
5. 완료되면 `config.yaml` 의 `model` 과 `llama.modelPath` 를 **항상 함께** 기록하고 서버 설정/연동까지 자동으로 끝낸다.

### R4. 단일 서버·단일 포트 정책 (축 F) ← 핵심
1. **llamacli 가 관리하는 llama.cpp 서버는 항상 하나, 하나의 포트**에서만 동작한다. 두 번째 서버를 절대 띄우지 않는다(8 GB 급 GPU 에서 이중 기동은 곧 OOM).
2. 기동 전 **포트 소유자 판별**(`ours` / `foreign` / `none`):
   - `none` → 그대로 기동.
   - `ours`(이 설치가 띄운 llama-server) 이고 **원하는 모델·엔진·설정과 동일** → 재기동 없이 **연결만** 한다.
   - `ours` 인데 모델/엔진/튜닝이 **다르다** → 아래 확인 절차.
   - `foreign`(다른 프로그램) → **절대 종료하지 않는다.** 다른 포트를 쓸지/중단할지 사용자에게 알리고 선택받는다.
3. **확인 절차 (기존 서버를 멈추고 갱신해야 할 때)**
   - 무엇이 어떻게 바뀌는지 diff 로 보여준다: `현재 모델 → 새 모델`, `현재 빌드 → 새 빌드`, 컨텍스트/`--n-cpu-moe` 변화, pid·포트.
   - 명시적 Y/N 을 받는다. **기본값은 N(유지).** 비대화형 환경에서는 N 으로 간주하고 "재시작하려면 `/server restart`" 를 안내한다.
   - Y → 그 포트 소유 pid 로 정확히 종료(`pgrep` 이름 매칭 금지; `ss -ltnp`/OS 동등 수단으로 포트 소유 pid 확인) → **종료 확인 + VRAM 해제 확인** → 새 서버 기동 → 헬스 체크(`/health`, 모델 로딩 완료) 통과까지 대기.
   - 새 서버가 실패하면 **자동 롤백하지 않고**(이전 서버는 이미 내려갔음) 실패 이유(로그 tail)와 직전 설정으로 복구하는 명령을 보여준다. 단, 종료 *전에* 새 설정이 로드 가능한지(모델 파일 존재, 엔진 probe) 사전 점검하여 실패 가능성을 줄인다.
4. 서버가 2개 이상 발견되면 자동 정리하지 말고 목록(pid/포트/모델/소유)을 보여주고 어느 것을 유지할지 묻는다.
5. 시작 시 이전 작업 재개 프롬프트(Y/N)나 체크포인트를 건드리는 모든 동작은 사용자 데이터 보호 대상이다 — 검증 하네스가 대신 답하면 안 된다(§6).
6. 포트는 설정 → 실행 중 서버에서 확인 → 8080 기본 순으로 결정한다. 설정에 포트가 없는데 8084 처럼 이미 서버가 있으면 8080 으로 **두 번째 서버를 띄우지 말고** 그 서버를 쓴다.

### R5. 사용자 경험
- 단계마다 한 줄: `[1/4] llama.cpp 확인 … ✔ (cuda, b6xxx, 재사용)`. 실패는 **원인 + 사용자가 할 일** 한 문장.
- 모든 외부 확인(서버 종료, sudo 설치, 큰 다운로드(>1 GiB))은 요약 후 확인. `--yes` 같은 플래그가 있어도 *서버 종료*는 별도 확인을 유지(또는 `--yes-restart` 처럼 명시 플래그).
- 오프라인이면 네트워크 단계를 건너뛰고 가진 것만으로 가능한 최대치를 한다.

## 2.5 슬래시 명령 연계: `/reset` · `/server` · `/models` (R6)

초기 구동(bootstrap)과 세 명령은 **같은 코어 함수**를 호출해야 한다. 명령마다 자체 로직(포트 판별, 서버 종료, 엔진 탐색, 다운로드)을 복제하면 정책이 어긋난다.
공통 코어: `ensureLocalStack`/`provision`(엔진·모델), `findLlamaServer`(엔진), `tuneForHardware`(설정), `switchModelAndServer`+`PortOwner`(포트·교체), `reportServer`(상태), `download` 파이프라인.

### 명령별 계약

| 명령 | 하는 일 | 서버를 건드리는가 | 확인 |
|---|---|---|---|
| `/server` | 읽기 전용 상태: 포트·pid·소유(ours/foreign)·모델·빌드·"이 빌드가 모델을 읽는가"·설정과의 불일치 | 아니오 | 불필요 |
| `/server restart` | 설정대로 재기동 | 예 | **diff + Y/N** (R4.3) |
| `/models` | 이 머신 기준 후보 표(VRAM 상주 / RAM 스트리밍 / 불가) + 현재 선택 표시 | 아니오 | 불필요 |
| `/models <번호\|이름>` | 선택 → config 에 `model`·`llama.modelPath` 동시 기록, 디스크의 동일 모델 재사용, 없으면 다운로드 안내, 빌드 호환성 보고 | 기록만(서버는 그대로) | 다운로드는 `confirm` |
| `/models <선택> confirm` | 다운로드 → 해시 검증 → 이동 → 설정 | 아니오 | — |
| `/reset` | 현재 GPU·VRAM·RAM 으로 모델/설정/컨텍스트 **재계산**한 결과를 diff 로 미리보기 | 아니오 | — |
| `/reset confirm` | 재계산 결과 적용(+필요 시 엔진/모델 확보) 후 서버 반영 | 예 | **diff + Y/N** (R4.3) |

### 연계 요구사항
1. **세 명령 + 시작 시 bootstrap 이 동일한 단일 서버 정책**을 쓴다: 포트 소유자 판별, `foreign` 불가침, 동일 설정이면 재기동 없음, 두 번째 서버 금지, 교체는 diff+확인.
2. **상태 일관성**: `/models` 로 모델을 바꾸면 `/server` 가 즉시 "실행 중 서버 모델 ≠ config 모델, 재시작 시 X→Y" 를 보여주고, `/server restart` 한 번으로 그 결과가 반영된다. `/reset` 도 같은 불일치를 diff 로 보여준다.
3. **서버가 떠 있어도 `/models` 선택은 실패하지 않는다**(예전 버그: 서버를 중지해야만 모델 변경 가능). 선택은 설정 기록이고, 반영은 재시작 시점이다.
4. **`/models` 선택 → `/reset` 상호작용**: `/reset` 은 사용자가 `/models` 로 *명시 선택한 모델*을 하드웨어 기본값으로 덮어쓰지 않는다(덮어쓰려면 diff 에 그 사실을 명시하고 확인). 반대로 직접 키운 `llama.*` 값은 `/reset` 이 다시 계산한다는 점을 diff 에 보인다.
5. **엔진 연계**: 세 명령 모두 엔진 판단에 `findLlamaServer`(실행 probe)를 쓴다. 선택한 모델을 못 읽는 빌드면 `/models` 가 그 자리에서 알리고, `/reset confirm`·`/server restart` 는 기동 *전에* 막거나 새 엔진 확보를 제안한다. 기록되는 `llama.binPath` 는 그 모델을 읽을 수 있는 빌드다.
6. **포트 일관성**: 세 명령이 같은 규칙(설정 → 실행 중 서버 → 8080)으로 포트를 정한다. 어느 명령도 설정에 없다는 이유로 8080 에 두 번째 서버를 만들지 않는다.
7. **진행 표시**: 다운로드·빌드·재기동 진행은 TUI 가 화면을 소유하므로 한 줄 transient 진행률 seam 을 쓴다(스크롤 금지). 명령 응답이 오래 걸리면 입력이 막히지 않는다.
8. **중단/오류 안전**: 명령 도중 실패·취소해도 config 는 *전부 적용 또는 전부 미적용*(부분 기록 금지, `model` 과 `llama.modelPath` 불일치 금지). 서버 종료 후 기동 실패는 R4.3 의 보고 절차를 따른다.
9. **비대화형/헤드리스**: 확인이 필요한 단계는 N 으로 간주하고, 다음에 입력할 정확한 명령을 안내한다.

### 연계 검증 (E2E 시나리오 — 각각 테스트로 존재해야 한다)
가짜 `PortOwner`/`makeServer`/`findServer`/`listLocalModels`/`fetchImpl` 주입으로 서버·네트워크 없이 돌리는 **명령 시퀀스 테스트**:

| # | 시퀀스 | 기대 |
|---|---|---|
| C1 | 서버 없음 → `/server` | "서버 없음" + 시작 방법, 부작용 0 |
| C2 | 서버(ours, 모델 A) 실행 중 → `/models 9B` | config 만 B 로 기록, 서버 무변경, 다운로드 필요 시 `confirm` 안내 |
| C3 | C2 직후 `/server` | 불일치(A→B) 표시, 재시작 계획 표시 |
| C4 | C3 직후 `/server restart` → N | 변경 0, `stop` 호출 0 |
| C5 | C3 직후 `/server restart` → Y | stop→start 순서, 새 모델로 헬스 통과, `/server` 가 일치로 표시 |
| C6 | 하드웨어 변화 후 `/reset` | 미리보기 diff 만, 적용 0 |
| C7 | `/reset confirm` → Y | 재계산값 적용, 단일 서버 유지, 두 번째 서버 0 |
| C8 | `/models` 로 명시 선택한 뒤 `/reset confirm` | 선택 모델 유지(또는 덮어쓰기를 diff 에 명시) |
| C9 | 동일 모델·동일 설정에서 `/reset confirm` | "변경 없음", 재기동 0 |
| C10 | foreign 프로세스가 포트 점유 중 `/server restart`·`/reset confirm` | 종료 0, 다른 포트/중단 선택 안내 |
| C11 | 선택 모델을 못 읽는 빌드만 있을 때 `/models`→`/reset confirm` | 기동 전 차단 또는 새 엔진 제안, 서버 종료 0 |
| C12 | 다른 디스크에 동일 모델 존재 `/models <선택>` | 다운로드 0, 그 경로 기록, `/reset` 이 그 경로를 유지 |
| C13 | `/models <선택> confirm` 중 해시 불일치 | 최종 디렉토리 무변경, config 무변경, 실패 보고 |
| C14 | 서버 2개 실행 중 `/server` | 목록·소유 표시, 자동 종료 0 |
| C15 | 명령 도중 오류 주입(쓰기 실패 등) | config 부분 기록 0 |

실환경 검증(별도 포트의 테스트 서버, 빈 임시 프로젝트, §6 규칙 준수): C1·C2·C3·C4·C5·C9 를 pty+pyte 로 실제 바이너리에서 1회 확인하고 화면 캡처 텍스트를 보고서에 남긴다. 사용자의 실제 서버(8084 등)·체크포인트는 건드리지 않는다.

## 4. 수행 순서 (한 번에 하나, 단계마다 테스트 + 커밋)

1. **감사(read-only)**: §2 의 각 요구사항(R1~R6)에 대해 "구현됨 / 부분 / 없음" 표를 `docs/provisioning-matrix-report.md` 로 작성. 코드 근거(파일:라인)를 단다. 추측 금지.
2. **매트릭스 테스트 표 확장**: `profiles.test.ts` 에 §5 의 행을 추가(처음엔 실패해도 된다 — 공백의 증거).
3. **공백 수정**: 실패한 행을 하나씩 고친다. 우선순위: R4(단일 서버·확인) → R6(명령 연계) → R1 의 실행 검증/백엔드 선택 → R2 튜닝 경계 → R3 → R5.
4. **R4 전용 테스트**: 포트 소유자 3종 × 설정 동일/상이 × 대화형/비대화형 × 사용자 Y/N 전부. 종료는 가짜 `PortOwner`/`makeServer` 로 주입해 *실제 프로세스를 죽이지 않고* 호출 순서(`stop` 이 `start` 보다 먼저, N 이면 `stop` 호출 0회)를 검증.
5. **실환경 검증**(§6).
6. 문서(README 해당 절) 갱신, 빌드(`npm run build`) 후 `bin` 커밋. **푸시는 사용자 확인 후.**

## 6. 검증 규칙 (사고 방지 — 반드시 지킬 것)

- **"내 머신에서 된다"는 증거가 아니다.** 합성 프로파일(단위)로 전 행을 먼저 통과시킨 뒤, 실환경은 *이 머신에서 가능한 행*(예: #1~#3, #23, #24)만 실제로 돌리고 나머지는 합성 근거임을 보고서에 명시한다.
- **실제 사용자 서버를 건드리지 않는다.** 이 머신의 8084 등 실행 중 서버는 사용자 것이다. 종료/재시작 검증은 **별도 포트의 테스트 전용 서버**(`setsid nohup`, 임시 모델/작은 모델)로만 한다. 사용자 서버를 내려야 하면 먼저 묻는다.
- **pty 하네스는 빈 임시 프로젝트 디렉토리(`mktemp -d`)에서만 실행**한다. "이전 작업이 있습니다 … 이어서 진행할까요?" 프롬프트에 **절대 대신 답하지 않는다**(과거 체크포인트를 영구 삭제한 사고가 있었다). 사용자 프로젝트 디렉토리에서는 실행하지 않는다.
- 프로세스 종료는 **포트 소유 pid** 로만. `pgrep llama` 같은 이름 매칭 금지(엉뚱한 pid 를 죽여 GPU 가 점유된 채 벤치를 돌린 사고가 있었다). 종료 후 포트 해제와 VRAM 반환을 확인한다.
- 다운로드 실검증은 작은 GGUF(수십 MB)로. 20 GiB 급 모델을 검증 목적으로 받지 않는다.
- 테스트는 `freePort()` 로 빈 포트를 쓴다(8080 에 실제 서버가 있어도 흔들리지 않게).
- 모델 파일, 설정, 체크포인트를 삭제/덮어쓰는 동작은 대상을 먼저 확인한 뒤에 한다.

## 8. 하지 말 것

- 이미 있는 엔진/모델을 확인 없이 다시 받거나 다시 빌드하지 않는다.
- 사용자 확인 없이 실행 중 서버를 종료·교체하지 않는다. foreign 프로세스는 어떤 경우에도 종료하지 않는다.
- 두 번째 llama-server 를 띄워 "일단 돌려보지" 않는다.
- 실패를 성공으로 보고하지 않는다(바이너리가 실행 검증을 통과하기 전엔 "설치됨"이 아니다).
- 하드웨어별 분기를 매직넘버로 박지 않는다 — 측정/헤더에서 읽은 값과 근거를 남긴다.
- 폐기한 기능(Bonsai/PrismML fork 경로)을 되살리지 않는다.
