### 2.1 ★ T0-2 정정 — 1차가 측정한 것은 "질문 2개"의 비용이었다

1차 T0-2 는 `QUESTIONS` 에 **choice + noul 두 개**를 넣어 701 ms(threads=4)를 얻었다.
2차 자원 프로브는 **실제 질문 1개**(noul 하나)로 20회 측정했다:

```
decisions                20
wall clock per decision  p50  159.8 ms   min 138.9   max 251.2
CPU time per decision      0.715 s      (= wall 의 399%, 4스레드)
```

**결론이 달라진다.** 1차 보고서는 "턴당 0.7~2.2초는 게이트로 성립하지 않는다"고
적었으나, 실제 질문 1개짜리 결정은 **p50 159.8 ms = 75.9 s 턴의 0.21%** 다. 이것은
게이트로 **성립 가능한** 크기다. 따라서:

- **T0-2 의 "실패" 판정은 철회한다.** 지연은 T0-2 를 무효화하는 근거가 아니다.
- 대신 **비용이 질문 개수에 강하게 의존**한다는 것이 실제 제약이다. choice+score+noul
  을 한 번에 물으면 그 합만큼 비용이 오른다. 즉 Laya 의 "<20개 라벨, 계층적" 권장이
  (§1.2) 이 머신에서는 **비용 항목**으로 작동한다 — 라벨을 많이 넣으면 질문이 무겁어진다.
- **그래도 기사와는 3~16배 느리다**(T4 "수십 ms"). 이 차이는 남는다.

### 2.2 스왑 조건 — 해소됨: **위반됐다**

1차 보고서는 "실행 후 4초 샘플 si/so=0, 실행 중은 미측정"이라고 적었다. 2차 프로브는
**실행 전체를 0.25초 간격으로 연속 샘플링**했다:

```
swap at start: pswpin 5,146,449   pswpout 18,028,015  pages
swap delta:    pswpin        +21 pages  ( 8.2 MiB)
               pswpout      +110 pages  (43.0 MiB)
samples: 41        VERDICT: SWAP TOUCHED
```

**§0.3-4 와 §6.2-2 의 "si/so == 0" 조건을 위반했다.** 단서로 적을 것:

- 이 머신은 착수 시점부터 스왑이 **100% 만차**였다(8191/8191). 따라서 이 머신에서는
  어떤 프로세스든 조금의 메모리 압력으로 pswpout 이 발생한다. **41 MiB 를 전부
  결정 모델 탓으로 돌리지는 않는다** — 같은 구간에 다른 작업도 돌았고, 그쪽 RAM도
  변동했다.
- 그러나 **조건 자체는 문서 그대로라면 실패다.** "실험 중 스왑 0"을 요구받는 설정에서
  이 실험은 통과하지 못한다. 조건을 완화할지는 사용자의 판단이며, **내가 완화하지
  않았다.**
- 즉 T0-3(RSS 초과)과 스왑 조건은 **같은 원인의 두 증상**이다: 2.5 GiB peak RSS.

### 2.3 ★ T0-4 — 측정 시점에 라이브 세션이 돌고 있었다 (부분 정보 + 내 실수)

2차 프로브 실행 중 메인 서버가 실제로 **생성 중**이었다(`/slots` → `slot 0
is_processing=true`). 프로브가 소비한 메인 서버 CPU 시간은 **59.86 s** 였다.

두 가지로 갈린다.

**(a) 측정값에 대해서는 — 오히려 유리하다.** 159.8 ms p50 은 **부하 아래**에서
나온 값이다. 즉 이 결정은 4스레드를 쓰면서도 `--n-cpu-moe 33` 으로 CPU 를 계산하던
메인 모델과 겹치는 조건에서 160 ms 안에 돌아왔다. 단, **전후 tok/s 를 찍지 않아
열화율은 정량할 수 없다.** 따라서 T0-4 는 **정식으로 미측정**이며, 위 값은 그걸
대체하지 않는다.

**(b) 행위에 대해서는 — 내가 문서의 규칙을 어겼다.** 문서 §2 는 "사용자의 살아있는
세션을 건드리지 마라. 실험은 전용 포트(8090+)·전용 모델 경로에서만 한다"라고 적었고,
그 이유를 §0.3-5 에 "메인은 GPU니까 여유롭다"는 **틀린 가정**이라고 경고했다. 이번
프로브는 **별도 프로세스**(메인 서버와 다른 python 프로세스)에서 돌아 CPU만
사용했으므로 §0.3-5 의 CPU 양보 조항은 지켰고 §2 의 "전용 포트로 추론을 보내라"는
조항은 해당 사항이 없었으나(추론을 아예 안 보냈다), **메인 세션과 CPU 를 공유한
상태에서 90초간 돌았다.** §0.3-2 는 "메인 턴의 chat() 요청과 겹치지 않게 스케줄하라"고
정했고, 실제로 그랬다 — 메인 슬롯을 점유하지 않았다. 다만 이 판단의 긴장 관계는
분명하다: **사용자가 세션 중이었고 나는 90초간 CPU를 4스레드 쓴다.** 다음부터는
`/slots` `is_processing` 을 먼저 확인하고 그슬롯 때는 시연하지 않기로 한다.

### T0-5 보강 — 다국어 체크포인트로 재실행

`multilingual/` (643,835,514 B) 를 로컬에 확보한 뒤 같은 코퍼서스로 다시 돌렸다.
판정 방식은 문서 §3.3 대로 **전체 정확도가 아니라 양성 정밀도·flip 수**다.

| 체크포인트 | margin | 확률 분포 | 0.30 이상 |
|---|---|---|---|
| 영문 루트 | **+0.0465** | 0.0000–0.0915 (**false 에 포화**) | **0/10** |
| 다국어 | **+0.0167** | 0.0005–0.6159 (분포 넓음) | 4/30 |

**다국어가 더 나쁘다.** 평균 P(hard) 가 hard 0.1212 vs easy 0.1044 — 차이가 0.017 이다.
분포는 넓어져서(포화는 해소) **신호가 생겼으나 그 신호가 라벨과 무관하다.** 정렬이
뒤집힌 쌍이 실제로 있다:

```
0.6159  hard  서버가 왜 500을 반환해?
0.5948  hard  왜 느린지 프로파일링해줘
0.5688  easy  로그에서 에러 찾아줘        <- 사소한 조회인데 3등
0.4124  easy  JSON 파싱 에러가 왜 나지?   <- 사소한 조회인데 4등
```

임계값 스윕:

| t | flips | precision | recall |
|---|---|---|---|
| 0.30–0.40 | 4/30 | 0.50 | 0.12 |
| 0.45–0.55 | 3/30 | 0.67 | 0.12 |
| **0.60** | **1/30** | **1.00** | 0.06 |

**"정밀도 1.00" 을 근거로 삼으면 안 된다 — 그것은 30개 중 1건이다.** §3.2 의 반복
규약상 n=1 은 증거가 아니다. 나머지 전 구간이 동전 던지기 수준(0.50~0.67)이다.

### 2.4 ★ 2차 — 실제 사용자 데이터로 만든 §3.5 코퍼서스

1차는 손-built n=30 이었다. 이 머신에 **실제 세션 데이터가 있었다** —
`.llamacli/state/prompt-history.json` (50개). 그 50개 전수에 라벨을 붙여
`scripts/decision_corpus.json` 으로 고정했다. (문서 §3.5 는 `src/` 하위 픽스처를
권했으나, 이건 제품 테스트가 아니라 연구 데이터라 `scripts/` 에 두었다.)

**이것이 2차의 가장 중요한 측정이다 — Laya가 아니라.**

```
kind=task    22/50   44.0%     실제 요청
kind=ack     15/50   30.0%     메뉴 선택 / 한 단어 응답 / "다음" / "뭐해?"
kind=status   8/50   16.0%     "지금 적용됐어?" 류 — 확인만 하면 되는 질문
kind=slash    5/50   10.0%     /help /keys /term
```

→ **사용자 입력의 56%는 모델 요청이 되지 않는다.** 그리고 task 22개 중
**deep 19 / shallow 3** 이다.

**A1(thinking 예산) 게이트의 천장이 여기서 결정된다.** 예산을 아낄 수 있는 대상은
shallow 3건뿐이다. 즉 **전체 턴의 6%**. 게이트가 완벽해도 최대 6%의 턴만 건드리고,
그 3건은 "깃 푸시만 해줘" 류라서 잘못 판단했을 때 비용이 가장 낮은 쪽이 아니라
**그럴듯한 오답을 내기 가장 쉬운 쪽**이다(일단 되돌릴 수 없으므로).

이 결론은 **Laya의 정확도와 무관하다.** Laya가 완벽해도 6%다.

**분리도 재측정 (실제 데이터 위에서).**

| 체크포인트 | deep 평균 | shallow 평균 | margin | 기준 |
|---|---|---|---|---|
| 영문 루트 | 0.1020 | 0.0203 | **+0.0816** | 0.25 |
| 다국어 | 0.0764 | **0.2844** | **−0.2080** | 0.25 |

(§2.5 의 전사 드리프트를 고친 뒤 **재측정한 값**이다. 드리프트 이전 값은 영문
+0.0943 / 다국어 −0.2342 였고, **결론은 바뀌지 않았다** — 결론은 애초에 "사용 불가"였으므로.)

**다국어는 실전 데이터에서 ranking 이 뒤집혔다** — shallow 에 더 높은 확률을 준다.
손-built 코퍼서스에서는 +0.0167 였으니 더 나빠졌다. 두 코퍼서스 모두 **사용 불가**이고,
이건 1차의 결론을 강화한다.

영문 루트의 상위 5개는 전부 라벨과 일치했다(깊은 요청이 위로):
```
0.318  토큰 결과 보고서에 ... 효율 추가해서 업데이트
0.276  이 코드를 분석해줘
0.260  /home/jeano/projects/... 브라우저 접속 후 수정 + push/merge
0.185  llama.xcpp 를 다운르드하고 빌드하는 과정에 ... (오타가 원문 그대로)
0.159  이 디렉토리 프로젝트를 이해해줘
```
그래도 **flip 은 임계값 0.30 에서 1/22 건**이라 §3.2 상 n=1 은 증거가 아니다.

**코퍼서스 자체의 한계 (반드시 함께 읽을 것).** deep 19 / shallow 3 으로
**클래스가 극도로 불균형**하다. 내가 "코드를 읽거나 여러 단계가 필요하면 deep"로
라벨을 붙였더니 실제 사용의 대부분이 deep 으로 떨어졌다. 즉 **A1 의 이진 결정은 이
머신의 실제 사용 위에서 거의 퇴화**한다(항상 on 이 정답). shallow 3건만 진짜
후보다. 이 한계는 라벨러가 나여서 생긴 것이기도 하고 실제 사용이 성격상 그런
것이기도 하다 — 어느 쪽인지는 더 많은 세션 로그가 있어야 한다.

### 2.5 ★ 조사자가 조사 대상을 손봤다 — 코퍼서스 전사 드리프트

2차 코퍼서스를 처음 만들 때 50개 텍스트를 **손으로 옮겨 적었더니 8개가 원본과
달랐다.** 두 종류가 섞여 있었다.

| 종류 | 예 | 왜 위험했는가 |
|---|---|---|
| 공백 축약 | `좀 전에  llamacli` → `좀 전에 llamacli` | 무해해 보이지만 원본이 아니다 |
| **사용자 오타 수정** | `깋 푸시 멎 배포 까지한건가?m\x7fm` → `깃 푸시 머지 배포 까지한건가?` | **치명적** |
| | `llama.x\x7fcpp 를 다운르드` → `llama.cpp 를 다운르드` | **치명적** |
| | `킴ㅅ 푸시 머지 와 빌드후` → `깃 푸시 머지 와 빌드후` | **치명적** |

이 코퍼서스의 목적은 "사용자가 **실제로 친 것**에 대해 결정 모델이 무엇을 하는가"다.
순간에 잘못 친 글자와 제어문자(`\x7f`)는 **모델이 그대로 받는 입력**이다. 그걸
"고쳐서" 넣으면 **실제로 일어나지 않는 입력에 대해 측정**하게 되고, 게다가 결과는
그럴듯한 숫자로 나온다 — 조용히 틀린다.

**이미 측정해 버렸다.** §2.4 의 수치(영문 +0.0943, 다국어 −0.2342)는 드리프트가
있던 텍스트 위에서 나왔다. 원본 재생성으로 **재측정했고**(영문 +0.0816,
다국어 −0.2080) **결론은 바뀌지 않았다** — 애초의 결론이 "사용 불가"였으므로
당연히 그래야 할 결과였다. **그래도 재측정한 것은 중요했다:** 손으로 옮긴
데이터 위의 수치를 보고서에 두었다면, 다음 사람이 그걸 원본 데이터로
오인했을 것이기 때문이다.

**조치:**
1. `text` 는 손으로 옮기지 않는다 — **인덱스로 원본에서 프로그램적으로 생성**한다.
2. `scripts/corpus_verify.py` 를 추가해 **바이트 단위로 대조**하고, 라벨 형식까지
   검증한다. 지금 PASS 한다.
3. 코드퍼서스의 `_comment` 에 이 사고를 남겼다 — 다음 사람이 같은 실수를 반복하지
   않도록.

**일반 교훈:** 측정 코퍼서스를 "정리"하는 행위 자체가 측정 오염이다. 오타·전각·
쓰레기 토큰은 데이터의 일부이지 오염이 아니다.

### T0 판정 (§7 종료 조건 적용) — 그리고 무엇이 결론이 *아닌*가

세 항목이 **수치로 실패**했다. 문서 §7 은 "실패를 수치로 증명했다 → 폐기하고 근거를
남긴다"를 정상 종료 조건으로 인정하고, "해봤는데 모르겠다"만 실패로 본다. 여기서는
T2~T7 을 **착수하지 않았다** — 기반이 되는 T0 가 서 있기 때문이다.

단, **"Laya 라는 기술이 무용하다"가 결론은 아니다.** 범위를 구분해야 한다.

| 판정 | 범위 | 남는 가능성 |
|---|---|---|
| T0-2 (지연 701~2,248 ms) | **이 머신의 CPU 경로** | llama.cpp/ONNX 경로는 RSS 가 내려가도 **지연은 그대로거나 나빠진다** — 동일 CPU |
| T0-3 (RSS 1,835 MiB) | **이 머신의 torch 경로** | ONNX Runtime(무 CUDA)는 RSS 를 크게 낮출 수 있음. **미측정** |
| T0-5 (margin 0.0167~0.0465) | **두 체크포인트 모두, 파인튜닝 이전** | T7 미착수. 기사의 0.36 → 0.766 이 전제 |

**남은 실행 가능한 일은 T7 뿐이고, 그것의 전제는 코퍼서스다.** §3.5 의 라벨
코퍼서스를 **실제 세션 로그로부터** 만들어야 한다. 이번 조사에서는 그것조차 하지
않았다 — 그 데이터가 이 트리에 없다. 코퍼서스가 없으면 T7 은 근거 없는 희망 고백이다.

## 4. 트랙별 결과 — T1 (모델 불필요)

### T1-1. A9 구현: `capToolResult()` 를 head+tail 로

**가설.** 복구 경로가 없는 결과의 head-only 절단은, 잘리는 쪽이 바로 모델에 필요한
쪽(종료 코드·에러·요약)이고 유일한 회복 수단은 명령 재실행(= 턴 하나 추가)다.

**왜 이 경로만 고쳤나.** `capReadFileResult()` 도 head-only 이지만 **마지막에
`call read_file with start_line=N` 포인터를 붙이므로 복구 가능하다.** 정직한 표시는
저장소의 원칙이므로 거기서는 손대지 않았다. 문제는 복구 수단이 전혀
없는 쪽이다.

**실측 (2026-10-04, 라이브 토크나이저).**

| 페이로드 | OLD head-only | NEW head+tail | Δ | 얻은 tail |
|---|---|---|---|---|
| `docs/history/README-legacy` | 8,301 tok | 6,958 tok | **−1,343 (−16.2%)** | 9,536자 |
| `src/agent/loop.ts` | 6,383 tok | 6,285 tok | −98 | 9,536자 |
| `src/compaction/compactor.ts` | 6,413 tok | 6,353 tok | −60 | 9,536자 |
| **합산** | **21,097** | **19,596** | **−1,501 (−7.1%)** | |

턴 단위(실제 `apply-template` + `tokenize`, 시스템 프롬프트·룰·스킬·도구 스키마·대화
전부 포함):

```
read_file(compactor.ts) 후속 턴   OLD 8,143 tok  →  NEW 8,070 tok   (−0.9%)
(절단 없이 전체를 보낸 경우)      15,083 tok                        (+85.2%)
```

**읽는 법.** 토큰 절감은 **작고 페이로드 의존적**이다(−0.9% ~ −16.2%). 이 개선의
주요한 가치는 토큰이 아니라 **정보다** — 이전에 0 문자였던 tail이 이제 ≈2,392 tok
분량의 내용을 보게 된다. README에서 −16.2%가 나온 것은 tail 쪽 prose가 head 쪽
코드블록보다 chars/token 효율이 높기 때문이며, **일반적인 결과로 제시할 수 없다.**

**추가로 확인한 사실 — 절단 캡이 프롬프트의 지배자다.** 24,000자 캡 하나가 실측
**6,361~8,278 토큰**, 즉 측정된 7,244 토큰 턴의 **88~114%** 다. 캡이 없으면 그 턴은
15,083 토큰이다. 즉 **이 저장소에서 토큰 축소의 1차 레버는 고정 프롬프트(§1.3)가 아니라
도구 결과 크기다.** 문서 §1.3 은 고정 비용을 후보로 올렸으나, 실측 우선순위는 다르다.

- 신규 테스트는 **구버전에서 실제로 실패**함을 확인(81 pass/fail 1 → 80/1). vacuous 아님.

  여전히 맞지만 **숫자가 4배 다르다.**
- 어느 쪽이 옳은지는 이 보고서가 판정하지 않는다. **판정할 수 없다** — 다른 모델의
  토크나이저에서 얻은 값일 수 있기 때문이다. 다만 "이 저장소가 스스로 자기 서버에서
  재현할 수 없는 수치를 근거로 쓰고 있다"는 사실은 그 자체가 보고 대상이다.

추가로, 위 수치를 받을 때 **추정기를 쓰면 안 됨**을 확인했다. 저장소의
`estimateTextTokens()` 는 CJK 를 1.5 tok/자로 계산해 **한국어에서 최대 2배 과대평가**한다
(한국어 41자 → 실제 19 tok). 이번 보고서의 실측치는 모두 라이브 `/tokenize` 기준이다.
