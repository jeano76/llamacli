## 0. 먼저 읽어야 할 사실 — 이 문서가 요청한 것을 다 하지는 못했습니다

원문은 **6대의 물리 머신(A~F) × 47개 TC = 282회**를 요구합니다. 실행 환경은
**1대**였습니다. 따라서 아래는 그 6×47 매트릭스가 아니며, 그렇게 표기하지
않습니다. 이 문서가 원문대로 요구하는 "100명이 서로 다른 OS·하드웨어에서 쓴다"
는 시나리오를 이.box 하나로 대표할 수는 없습니다.

대신 실제로 한 것 / 못한 것을 분리해서 적습니다.

## 1. 문서 자체의 결함 (실행 전 발견, 수정 없이 보고)

원문 §2의 격리 스크립트를 **그대로 쓰면 저장소가 파괴됩니다.**

```bash
rm -rf "$PROJ/.llamacli" "$PROJ/.git"   # 문서 §2 3번
```

스크립트는 `PROJ`가 버려지는 테스트 디렉터리라고 가정하지만, 이 저장소의 유일한
사본이 곧 `PROJ`가 됩니다. 그대로 실행하면 `.git`이 지워져 **590건 테스트
기준선과 모든 수정 이력이 사라집니다.**

같은 스크립트의 5번(포트 확인)은 문서 자체의 요구와도 충돌합니다.
"8080에 기존 서버 있음"(TC-05)을 검증하려면 8080이 **비어 있으면 안 되고**,
다른 모든 TC는 8080이 **비어 있어야** 합니다. 이 box의 8080은 실제 서비스 중입니다.

→ 본 작업에서는 저장소를 보호하기 위해 **`.git`을 건드리지 않는** 자체 격리
스크립트(`/tmp/opencode/llamacli-accept/TC-RESET.sh`)를 사용했고, 8080은
끄지 않았습니다. 저장소 안에 만든 임시 하네스는 전부 삭제했습니다.

## 2. 발견·수정한 버그 3건

모두 **재현 → 원인 규명 → 수정 → 재현 방지 테스트**로 닫았습니다.

### BUG-1 — 재귀/강제 삭제가 위험 판정에서 빠져나감 (TC-28)

- **재현 입력**: `/`로 판정
  ```
  CAUGHT  "rm -rf /home/jeano"
  CAUGHT  "rm -rf /*"          ← 별표 때문에 우연히 걸림
  MISSED  "rm -rf /"           ← 게이트가 "간단한 요청"으로 강등
  MISSED  "rm -fr node_modules"
  MISSED  "rm -rf ~"
  ```
- **원인**: `bulk delete` 패턴이 `all: [동사, 수식어]` **두 조건을 요구**하는데,
  `rm -rf`의 `-r`/`-f` 플래그 자체가 수식어 역할을 하는데 목록에 없었습니다.
  결과적으로 `rm -rf /*`는 별표 `*`로, `rm -rf /home/…`는 경로 패턴으로
  **우연히** 잡혔고, 대상이 드러넣 `rm -rf /` 만 통과했습니다. 어느 형태가
  걸리는지가 오직 뒤따르는 단어에 달려 있던 것입니다.
- **조치**: `src/agent/gate.ts` — `-r`/`-f` 플래그를 수식어로 인정하고,
  루트/홈 대상 삭제용 패턴(`delete of a filesystem root or home`)을 신설.
- **재발 방지**: `src/agent/gate.test.ts` 3개 테스트 추가.
- **부수 확인**: 정상 요청 18개(영문) + 6개(한글) 오탐 0건 유지.

### BUG-2 — 1~3코어 머신에서 스레드 수가 코어 수를 초과 (TC-08)

- **재현 입력**: 합성 1코어 + GPU
  ```
  cpu= 1 gpu=yes  threads= 2 threadsBatch= 2   ← 1코어에 스레드 2개
  ```
- **원인**: `tuneForHardware`의 GPU 분기가 `Math.max(2, …)` 하한을 써서,
  코어가 1~3개인 머신에서 코어 수보다 많은 스레드가 나왔습니다.
  **개발 박스는 12코어라 `max(2, 6)`이 우연히 정상값에 떨어졌고**, 기존
  590건 테스트는 이 버그를 전혀 발견하지 못했습니다. 환경 행렬 스윕이 처음
  잡아냈습니다.
- **영향**: 6,720 조합 중 1,440건 위반(전체 위반의 99.9%).
- **조치**: `src/setup/tuning.ts` — `Math.min(cpuCount, …)`로 코어 수를 넘지
  않도록 클램프.
- **재발 방지**: 신규 `src/setup/tuning.test.ts` (11개) — 1~64코어 전 구간 +
  12코어 정상값이 변하지 않았음을 고정하는 테스트 포함.
- **정상 동작 보존 확인**: 12코어 → `threads=6`, `threadsBatch=11` **변경 없음**
  (이 저장소 README에 기록된 손으로 튜닝한 작업 설정과 동일).

### BUG-3 — 한국어 동사 활용형이 판정에서 탈락 (TC-28)

- **재현 입력**: 한국어 요청 스윕
  ```
  CAUGHT  "전부 삭제해줘"
  MISSED  "모든 파일을 지워줘"    ← 같은 뜻, 다른 활용형
  MISSED  "모든 것을 제거해줘"
  MISSED  "재귀적으로 삭제"
  ```
- **원인**: 두 가지.
  1. 패턴에 `지우`가 들어 있었으나, 한국어는 모음으로 끝나는 접미사 앞에서
     어간모음이 `우 → 워`로 변합니다. 실제로 사람들이 치는 명령형은
     **`지워줘`** 인데 `지우`는 그 문자열의 접두사가 **아닙니다**
     (`지우다` → `지워`: U+C6B0 → U+C6CC). 어간이 `지[우워]`여야 합니다.
  2. `제거`와 `재귀`(재귀적 = recursive)가 목록에 아예 없었습니다.
- **조치**: `src/agent/gate.ts` — `지[우워]|지뜻` 형태로 어간 매칭,
  `제거`·`재귀` 추가.
- **재발 방지**: `src/agent/gate.test.ts` 2개 테스트(한글 파괴 요청 + 한글 정상
  요청 오탐 방지) 추가.

### BUG-4 (제품 아님) — 취소 테스트가 4회 중 1회 흔들림

- **재현**: 전체 스위트 4회 실행 중 1회에서 실패
  ```
  not ok 144 - cancel() aborts an in-flight streaming chat() call, distinguishably from a timeout
  ```
- **원인**: 테스트가 `setTimeout(20ms)` 후 취소하고 곧바로
  `deltas.length > 0`을 단언했습니다. 첫 청크 도착을 **가정**한 것이지
  확인한 것이 아니어서, 606개 테스트가 함께 도는 부하 환경에서 20ms 안에
  첫 델타가 안 도착하면 실패했습니다. 제품 코드 결함이 아니라 **테스트의
  시간 기반 가정**입니다.
- **판단 근거**: 이 파일은 제가 건드린 파일이 아니며, 격리 실행 시 5/5 통과,
  제 변경을 stash한 기준선에서도 동일하게 간헐 실패했습니다.
- **조치**: `src/backend/openaiClient.test.ts` — 고정 대기 대신 **첫 델타가
  실제로 도착할 때까지** 대기(2초 상한). 어서션의 의도("스트리밍이 시작된 뒤
  취소가 도착한다")에 더 정확하고 결정적입니다.
- **결과**: 수정 후 전체 스위트 **6회 연속 606/606 통과**.

### BUG-5 — 읽기 전용 프로젝트에서 부트스트랩이 예외로 죽음 (무결성)

- **재현 입력**: 프로젝트 디렉터리 권한 `0555` (읽기 전용)
  ```
  Error: EACCES: permission denied, mkdir '.../proj/.llamacli'
      at writeConfig (src/setup/bootstrap.ts:592:3)
      at ensureLocalStack (src/setup/bootstrap.ts:469:5)
  ```
- **원인**: `ensureLocalStack` 안에서 **`writeConfig` 하나만이** 예외를
  잡아주는 `step()` 래퍼 밖에 있었습니다. 이 모듈 자신의 문서 계약은
  "bootstrap이 throw하면 동작하던 설치가 죽는다 — report를 반환하면 호출자가
 无论如何로든 시작할 수 있다"인데, 정작 그 계약이 지켜지지 않은 경로였습니다.
  즉 **문서가 약속한 것과 코드가 다른 부분**이었습니다.
- **영향**: 읽기 전용 마운트, 다른 소유자의 체크아웃, root가 아닌 컨테이너
  사용자 — 모두 도달 가능한 상태입니다. 이 경우 부트스트랩 전체가 reject되어
  세션이 시작되지 않습니다.
- **조치**: `src/setup/bootstrap.ts` — `writeConfig`를 `step()`으로 감쌌습니다.
  쓰기 실패는 조용히 삼키지 않고 **실패한 스텝 + error로 보고**합니다. 다음
  실행이 이 작업 전체를 다시 하므로, 그 사실이 사라지면 안 됩니다.
- **재발 방지**: `src/setup/reset.test.ts` 1개.

### BUG-6 — 같은 결함이 한 층 위에서 반복 (무결성)

- **재현 입력**: 동일한 읽기 전용 프로젝트에서 `llamacli` 실행
  ```
  Error: EACCES: permission denied, mkdir '.../proj/.llamacli'
      at loadConfig (src/config.ts:272:5)
  ```
- **원인**: BUG-5와 **정확히 같은 패턴**이 `config.ts`의 `loadConfig`에 있었습니다.
  파일이 없는 상황을 처리하는 `catch` 블록 **안에서** `mkdir` + `writeFile`을
  보호 없이 호출하고 있었습니다.
- **왜 더 나쁜가**: 이건 최초 기동이 아니라 **매번 실행**마다 나는 경로입니다.
  즉 읽기 전용 프로젝트에서는 `llamacli`를 아예 시작할 수 없었습니다.
- **조치**: `src/config.ts` — 저장 시도를 best-effort로 처리. 세션은 정상
  시작하고, 사용자에게는 스택 트레이스 대신 **정직한 메시지**를 보여줍니다
  ("not writable … in-memory defaults for this session only").
- **재발 방지**: `src/config.test.ts` 1개.
- **자신의 테스트에 대한 정정**: 이 두 테스트를 처음에는 읽기 전용 디렉터리를
  만드는 **탐침 `mkdir`이 `.llamacli`를 그대로 생성**해서 작성했습니다. 그
  결과 시스템이 실제로 읽기 전용을 강제하지 않으면(또는 mkdir이 성공하면)
  테스트가 **빈 공간에서 통과**했고, 수정 코드를 되돌려도 여전히 통과했습니다.
  탐침 이름을 바꿔야 했습니다. "테스트가 통과한다는 것"과 "테스트가 무언가를
  검증한다"는 다른 문제이며, 이번에는 직접 되돌려 확인했습니다.

### BUG-7 — 단색 터미널에 색상 이스케이프를 보냄 (안정성)

- **재현 입력**: `TERM=vt100` (Putty의 VT100 모드, `emacs`/`sh`의 기본값으로도 실용 중)
- **관찰**: 감지 결과 `colorDepth=4`. 코드 경로상 `48;2;0;0;0m`, `95m` 계열이
  **색상을 전혀 지원하지 않는 터미널로** 전송됩니다. 그 이스케이프는 화면에
  엉뚱한 문자로 렌더링됩니다.
- **원인**: `detectColorDepth`가 알려지지 않은 TERM에 대해 16색 기본값을
  반환하도록 되어 있고, `vt100`은 그 목록에 없었습니다. 코드 주석은
  "往上로 추측하면 `95m`이 엉뚱한 문자로 렌더링된다"고 경고하면서, 정작
  문제는 **보수적인 방향의 잘못된 추측**이었고 아무도 발견하지 못했습니다 —
  흔한 TERM은 전부 색상을 가지고 있기 때문입니다.
- **조치**: `src/tui/terminal.ts` — 단색 TERM(`vt100`, `vt220`, `vt320`,
  `vt420`, `sun`, `wy50` 등)을 명시적으로 depth 0으로 처리. **정확히 이름을
 matched**하는 것으로 한정했습니다. 모르는 TERM는 여전히 4로 떨어져야 합니다
  (모두에 색상을 빼는 방향은 이 코드가 알지 못하는 모든 터미널에서 색상을
  강제로 끄게 됩니다).
- **재발 방지**: `src/tui/terminalCapability.test.ts`

### BUG-8 — 대체 화면(alt screen)을 지원하지 않는 터미널에 활성화 명령 전송 (무결성)

- **재현 입력**: `TERM=tmux-256color`, `TERM=screen-256color`, `TERM=vt100`
- **관찰**: 감지 결과 `altScreen=true` → `?1049h` 전송.
- **원인**: `altScreen: ansi` — **대체 화면은 ANSI와 별개 능력**인데 둘을
  하나로 취급했습니다. 두 곳에서 틀립니다:
  1. `vt100` 계열은 대체 화면 기능 자체가 나중에 등장했습니다.
  2. **tmux와 GNU screen은 `alternate-screen`을 기본으로 꺼 둡니다.** 앱의
     스크롤백을 파괴하는 것이 바로 그 옵션의 존재 이유이기 때문입니다. 그런데
     내부 TERM은 여전히 `*-256color`이므로 ANSI 검사도 색상 검사도 통과해
     버립니다. 즉 **이 버그를 잡을 수 있는 다른 검사가 존재하지 않습니다.**
- **영향**: 사용자가 설정하지 않은 tmux 세션이 사용자가 요청하지 않은 버퍼로
  전환되고 스크롤백이 사라집니다.
- **조치**: `src/tui/terminal.ts` — `detectAltScreen()` 추가. 확실하지 않을 때
  는 **"없음"**으로 답합니다. 본문이 메인 버퍼에 보이는 것은 복구 가능한
  결과이고, 요청하지 않은 alternate buffer로 전환된 tmux 세션은 그렇지
  않기 때문입니다.
- **재발 방지**: `src/tui/terminalCapability.test.ts` (4개 테스트)

### BUG-9 — 20×10 터미널에서 팝업이 자기 컨테이너보다 높게 렌더링 (사용성)

- **재현 입력**: 20×10 터미널
- **관찰**: 로그 영역 5행, 메뉴는 아이템 4개 + 테두리 2 = **6행 필요**.
  팝업이 오버레이하는 공간보다 커서 **아래 테두리가 잘립니다.**
- **원인**: `menuVisibleRows`의 `Math.max(MIN_ROWS, …)` 하한이 무조건적으로
  적용되어, 컨테이너보다 큰 값을 그대로 반환했습니다.
- **조치**: `src/tui/SlashMenu.tsx` — 하한을 유지하되 **컨테이너 물리적
  상한으로 클램프** 추가. 최소 3개(2개면 테두리 사이에 항목 1개만 보여
  목록이 아니라 파편처럼 보입니다).
- **부수 판단**: 20×10에서 메뉴가 로그를 **완전히 덮는 것**은 그대로
  두었습니다. 크기가 그럴 땐 둘을 함께 담을 공간이 없고, 사용자가 메뉴를
  조작 중인 상황이므로 로그를 가리는 것이 올바른 동작입니다. 진짜 결함은
  "팝업이 자기 영역보다 크다"였기 때문입니다.
- **재발 방지**: `src/tui/terminalCapability.test.ts`

### 시뮬레이션에서 발견했으나 **제품 결함이 아니었던 것** (오판 정정)

시뮬레이션이 처음에 17건을 실패로 보고했습니다. 소스를 대조한 결과
**9건은 제 기대가 틀린 것**이었고, 그중 몇 건은 고쳤다면 오히려 버그를
만들었을 수 있습니다. 기록해 둡니다.

| 보고된 실패 | 실제 | 판단 |
|---|---|---|
| 클립보드에 SGR 이스케이프 잔존 | `App.tsx:1354`·`index.tsx:1136`이 이미 `stripAnsiForCopy(selectionText(...))` 순서로 호출 | **테스트 계약 오류.** `selectionText` 단독이 strip한다고 단정했고, 그에 맞춰 코드를 "고쳤다면" 이미 올바른 코드를 망가뜨렸을 것입니다 |
| altScreen 미탐지 | `altScreen: ansi` — 실제로 **버그** (BUG-8) | **제품 결함** |
| vt100 색상 깊이 | 알려지지 않은 TERM 기본값 누락 — **버그** (BUG-7) | **제품 결함** |
| `reset` 시퀀스가 비어 있음 | 비-ANSI 터미널에서는 의도적으로 빈 문자열. `reset`는 `caps.ansi`로 게이트됨 | **기대 오류.** 비-ANSI에 리셋을 요구하면 더티 파이프에 이스케이프를 쓰는 것 |
| `backgroundOff`가 항상 있어야 함 | `NO_COLOR`·단색 터미널에서는 배경을 아예 집지 않으므로 해제할 것도 없음 | **기대 오류.** 실제로는 "배경을 집었다면 반드시 해제할 수 있어야 한다"가 올바른 계약 |
| 100,000자 페이로드가 거부됨 | 상한은 **원문 길이가 아니라 base64 길이** 기준 (원문 × 4/3) | **단위 오류.** |
| 붙여넣기 오탐 | `isLikelyPaste`는 `useInput` **한 번의 청크**만 받음. 타이핑은 키마다 청크가 하나씩 도착하므로 합쳐진 문자열은 실제로 발생하지 않는 입력 | **모델 오류.** 타이밍을 추가해 "고쳤다면" 존재하지 않는 신호를 의존하게 됩니다 |
| OSC 52 없음 | 프로브가 `/tmp`에서 실행되어 `ink` 해석 실패. 오류 배너너비 측정 중이었고, **성공으로 보고될 뻔** | **하네스 결함** |
| 배경 미복원 | Ink의 `unmount()`만 호출해 앱의 실제 종료 경로(`exitAltScreen`)를 우회. 복원은 SGR **49**이지 **0m**이 아님 | **테스트 대상 오류.** `0m`을 요구했다면 사용자의 전경색까지 지우는 코드로 "고치게" 됩니다 |

각 항목은 실제 호출부·계약·단위를 소스에서 확인한 뒤 판정했습니다.
